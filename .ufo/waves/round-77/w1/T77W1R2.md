Readers can independently `git show PIN:PATH`, recompute SHA-256, verify section identity, re-run the recorded regex checks, and check committed trace/input correspondence. This is input-keyed re-read evidence, not independent proof of every behavioral assertion in a section.

But `REBIND OK sections=%d entries_added=%d ledger_before=%d` (327-329) only means no failures accumulated for the supplied plan at the supplied pin. It does not run `coldread`, prove that its plan is exactly the monitor's uncredited set, prove a complete historical input union, prove the newly written trace was committed, or test the landing revision. Without `--merge-ledger`, it can also print OK without updating the ledger. A later content edit can invalidate recorded hashes. Therefore C2 needs the post-landing portable line **and** JSON `65/65 / true`, successful probe and exit status, alongside exact-set/union checks. The frozen kill rules (ii)-(v), not `REBIND OK` alone, are the relevant safeguards.

Concrete trust-boundary hole to audit in any proposed batch: `specs = sec['union_paths']` at 161 is trusted; the tool never derives the all-entry input union itself. A plan omitting a drifted historical input can re-pin a smaller current subset. The frozen monitor checks each entry's **recorded** inputs (`measure.py:321-349`, 513-526), then credits if any matching entry passes and no current failure veto exists (627-641); it does not demand that an entry contain every older entry's inputs. Thus a reduced-union entry could credit a section while an omitted historical dependency remains stale. This is a bounded claim limitation, not evidence that the not-yet-reviewed R77 batch actually does so.
