## (b) Candidate primary source for a successor to `ledger-witness.py`

### The candidate

**Nándor Licker and Andrew Rice, "Detecting Incorrect Build Rules", ICSE 2019
(41st IEEE/ACM International Conference on Software Engineering), pages 1234–1244,
DOI 10.1109/ICSE.2019.00125.** The tool is **mkcheck**
(<https://github.com/nandor/mkcheck>, MIT). Author's manuscript, open access:

- URL: <https://api.repository.cam.ac.uk/server/api/core/bitstreams/306a073f-e1a0-4a49-93fd-2e3303c4c1ea/content>
- accessed 2026-11-06; PDF sha256 `ceff92a9c94e4332184632562f85eb83f8f98d62333398a6b6a2cc8294e72a4f`, 286638 B, 11 pages
- artefacts DOI: <https://doi.org/10.17863/CAM.35270>

### Why it is the right shape for a successor

mkcheck is the direct published precedent for the move `ledger-witness.py` makes: it
does **not** trust the build system's own account of what it did. It traces the build
at the syscall level with `ptrace`, infers the *actual* dependency graph from the
trace, and then checks the *declared* build rules against the inferred one. That is
precisely "bind the declared ledger to what the kernel observed, not to what the
runner prints", with the declared side being build rules instead of a mutation
ledger's leg table. Two of its own sentences carry the transferable argument:

Located quotes (page numbers from the PDF; word counts ≤ 25):

- **p. 1 (Abstract, 19 words)** — "These sets are determined using a dependency graph inferred by tracing the system calls executed during a clean build."
- **p. 3 (§II-B, 11 words)** — "dependency graphs defined by users of build tools cannot be trusted"
- **p. 4 (§III-A, 9 words)** — "Our inference method uses ptrace, targeting Unix-based build environments."

The p. 3 sentence is the one to cite: it states the epistemic position the witness
relies on — a declared graph is not evidence — and the p. 4 sentence supplies the
mechanism (ptrace, so the observation is the kernel's, not the subject's). The
p. 1 sentence is the method sentence (expected-change set derived from the traced
graph, not from the declaration).

Two further properties make it a good grounding for a *successor*, not just a
citation:

1. **It names the failure mode the successor will hit.** §III-B/§III-B "Overconstraining"
   / "Underconstraining" say the inferred graph "is only an approximation of all data
   dependencies" and warn that "even though we captured all interactions between a
   process and the operating system, some edges might be missing from the recovered
   graph". That is the published form of this round's declared limits L1–L4: a
   syscall-observed witness is a *witness*, not a proof, and the lane's L3 (state the
   trace does not carry — working directory, inherited fd table, signal dispositions,
   inherited rlimit) is the same gap mkcheck had to concede.
2. **It is a build system, so the declared-vs-observed binding is the same shape.**
   mkcheck's declared side is a Makefile's dependency graph; the witness's declared
   side is a runner's leg table. Both are "a subject's own claim about its work",
   checked against a trace.

Caveats to state if the L1 takes it: mkcheck's tracer is a bespoke `ptrace` tracer
that reconstructs the graph by interpreting `execve`/`open`/`read`/`write`/`pipe`/
`rename`/`unlink` (its Algorithm 1), not `strace(1)`'s text output; it infers
*dependencies*, not *verdicts*; and its object is build correctness, not mutation
survival. The lane already holds S058 (Build Systems à la Carte — "the
verifying-traces rebuilder"), so this row is distinct from it: S058 is the
*design* of a trace-verifying build, this is the *empirical* syscall-trace check
against a declared graph.

### Alternatives considered and why not recommended

| candidate | why not |
|---|---|
| **mkcheck2** (Saito, Sakamoto, Washizaki — "Efficient Build Dependency Verification Using eBPF and Incremental Analysis", ICSE 2026, DOI 10.1145/3744916.3773204; <https://github.com/katei-lab/mkcheck2>) | Closest in *mechanism* (build dependency tracer) and clearly the successor of mkcheck, but: eBPF, not ptrace/strace — so it does not ground a *strace-text-parsing* witness; the full text is behind the ACM DL paywall (only the repo README and press coverage are open), so a located, quotable passage from the paper itself is not verifiable from here; and its object is incremental-build dependency errors, further from a mutation ledger. Keep as a *pointer*, not the row. |
| **Lprov** (Wang, Kwon, Ma, Zhang, Xu — ACSAC 2018, <https://yonghwi-kwon.github.io/data/lprov_acsac18.pdf>, read in full this round) | Genuinely on-topic for "syscall trace as provenance", and its sentence "library provenance cannot be tracked by syscalls and mapping; whether a library function is called and how it is called within an execution context is invisible at syscall level" is a sharp limit. But its object is *attack* provenance (find the root cause of a compromise), not *verification* of a subject's own claims, and it needs a kernel module plus a customised loader. A weak grounding for a verification fixture. |
| **TraceCode toolkit** (<https://github.com/aboutcode-org/tracecode-toolkit-strace>) | `strace`-based build-graph reconstruction, so mechanism-adjacent, but it is a maintenance-archive tool for tracing software components between source and deployment trees — no verification claim, no published evaluation, and it duplicates what S060/S075 (strace as input observer) already cover for the lane. |
| **SLSA / in-toto provenance** (<https://slsa.dev/spec/v0.1/provenance>) | A *declaration* format, not a syscall-observed ground; it is what the witness refuses to trust. Useful background, wrong axis. |

### Recommendation

**ADMIT** (as a new registry row, id **S315**, type `paper`, tier A) — with the
§II-B sentence as the located quote:

> "dependency graphs defined by users of build tools cannot be trusted"
> — Licker & Rice, "Detecting Incorrect Build Rules", ICSE 2019, §II-B, p. 3
> (11 words; open manuscript, accessed 2026-11-06)

Reason: it is a peer-reviewed primary source whose *claim* is the claim this round's
tool exists to make — a declared account of work is not evidence; the trace is — and
whose *conceded limits* (§III-B over/under-constraining; "some edges might be
missing from the recovered graph") give the successor a published, citable form of
this round's L1–L4. It is distinct from every row the lane holds (S058 is the
design, S060/S075/S313/S314 are the strace/execve semantics), no fleet lane holds a
row for it (`grep` over `/home/vgpnk/Projects/shokunin/*/corpus/SOURCES.md` finds no
`mkcheck` / `Licker` / "Detecting Incorrect Build Rules"), and the next free id is
S315. The `used-by` cell should name the successor's knowledge note, not
`corpus/knowledge/kernel-witnessed-ledger.md` (which is this round's, already cited
by S313/S314) — the round-89 note itself is the successor's first carrier if the L1
opens it.

**Flip condition for the L1:** reject the row if the successor turns out to parse
`strace` *text* rather than observe syscalls directly — in that case mkcheck's
mechanism is a different instrument and the honest ground would be S314 alone. As
long as the successor consumes a syscall trace, the row holds.
