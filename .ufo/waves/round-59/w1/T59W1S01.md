## Can the frozen counter misclassify this cell?

Reviewed measure.py against this cell; findings:

1. **Mode-strictness risk (false fail).** Fixture blob mode is 100644. If the tool reads
   "executable-source" as "mode 100755 required", the equal cell falsely returns
   DRIFT. The claim's wording must be read as "regular blob source of the executor".
2. **Content-blind pass risk (false pass).** Candidate == trusted for this cell, so a tool
   that only checks commit resolvability then prints BOUND passes the equal cell without
   comparing blobs. The counter cannot catch that here; the changed/missing/symlink cells
   carry the discriminating weight.
3. **Token matching.** Counter accepts the token on stdout *or* stderr and does not check
   for absence of contradictory tokens; exit code is the primary signal.
4. **Environment.** Counter strips `GIT_*`, nulls global/system git config, forces
   `PYTHONDONTWRITEBYTECODE`, runs `python3 -I` with a 30 s timeout and TMPDIR inside
   `--work`. A tool needing user git config, site-packages, or repo writes fails.
5. **Determinism.** Cell fixture is byte-reproducible; blob-OID comparison is immune to
   commit-hash or timezone variance.

## Conclusion

Cell (tools/runner.py, equal) is operable and contract-consistent: the fixture yields a
regular blob at deterministic content, and the expected outcome is exactly exit 0 with
`EXECUTOR_SOURCE_BOUND`. Independent oracle agrees on original, changed, and unresolvable
states. Principal residual risks sit in the not-yet-staged tool (mode 100644 acceptance,
actual blob compare), not in the counter's handling of this cell.
