## Can the frozen counter misclassify this cell?

Reviewed axes; conclusion: **no, not for a tool that reads committed blobs.**

- The pass check is `returncode == expected and token in (stdout+stderr)` —
  conjunctive. A tool cannot false-pass on token text alone, and a wrong exit
  code fails even with the right token.
- The fixture's trusted/changed distinction is content-addressed: the blob ids
  above are identical for all four fixture paths in the frozen counter
  (verified by `git hash-object` on the same bytes), so no cross-path
  contamination and no timestamp dependence in the discriminating comparison.
- Env sanitization (`GIT_*` stripped, global/system config nulled) only removes
  crutches; it cannot flip a correct blob comparison to the wrong class.
- The leading-dash basename `tools/-runner.py` never appears as a dash-prefixed
  argv element (measure.py passes it as the value of `--path`), and git
  pathspec handling works with or without `--` (probed above).
- Residual (counter-inherent, not path-specific): a tool that reads the
  *working tree* instead of the committed blob would see whatever the last
  fixture commit left (a symlink) — for `changed` it would still exit 1/DRIFT,
  so this cell would pass coincidentally; that is a tool defect the other cells
  (`missing`, `symlink`) expose, not a counter misclassification of this cell.
- Timeout (30 s) is ample for a two-commit blob comparison.
