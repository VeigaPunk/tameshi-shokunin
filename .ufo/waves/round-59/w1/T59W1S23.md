## 3. Can the frozen counter misclassify this cell?

Counter per-cell check: `ok = (exit == 2) and ('EXECUTOR_SOURCE_UNAVAILABLE' in stdout+stderr)`.

**False-positive surface (counter weakness, demonstrated).** The token test is a substring match
over the *combined* streams with no exclusivity and no evidence that git was consulted.
`receipts/vacuity-and-anchor.txt` case D: a scratch probe that never touches git exits 2 with the
token, and the counter's exact check evaluates `ok=TRUE`. A tool that pattern-matches the 40-zero
candidate would pass this cell vacuously. This is a bound of the measurement (consistent with the
contract's "declared Git blobs only" trust boundary), not a scoring error.

**False-negative surface.** None found for this cell: env is `GIT_*`-scrubbed with config
neutralized, 30s timeout is ample, token matched on combined streams, `-I` isolation. The
leading-dash path is safe in the counter's own plumbing (all its git calls use `--`; probe A shows
git 2.56 `ls-tree` accepts the leading-dash pathspec even without `--`).

**Tool-side hazard observed (counter would score it correctly).** `git rev-parse --verify
<40-hex>` **without** `^{commit}` returns rc=0 and echoes the zeros (probe B), while
`cat-file -e <zeros>^{commit}` fails rc=128 (probe C). A tool that fails to anchor `^{commit}`
would "resolve" the unresolvable candidate and then misreport — the frozen counter would correctly
score `ok=False` (expects exit 2, tool emits 1/DRIFT). That is the counter working as intended,
not a counter misclassification.
