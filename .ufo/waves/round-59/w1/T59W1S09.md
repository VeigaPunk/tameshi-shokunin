## Misclassification review — can the frozen counter misclassify this cell?

1. **Counter-side mechanics: sound for this cell.** The counter passes `--path` via list argv;
   my stub under the exact invocation shows `'--path', 'tools/space name.py'` arrives as one
   element, so the space cannot split. Env scrubbing, per-path fixture repos, and pinned
   commits leave no ambient state. Expected mapping for `missing` (exit 1 + DRIFT) matches the
   contract exit_map and the observed object facts.
2. **True false-pass vector: mechanism blindness + coincidental on-disk state.** The counter
   checks only exit code + token, not the mechanism. At run time the worktree holds a dangling
   symlink at this path for *every* class, so a tool that inspects the **worktree** instead of
   the candidate commit tree would emit DRIFT(1) for `missing` — the expected verdict — and
   could pass this cell for the wrong reason. The full 24-suite still catches such a tool
   (equal/unrelated would DRIFT vs expected 0), but for this cell in isolation the frozen
   counter can false-pass a non-git-tree implementation.
3. **False-fail vectors (counter robust, tool-side hazards).** An unquoted `shell=True` lookup
   splits the rev:path (`git show b9c775df:tools/space name.py` → "path 'tools/space' does not
   exist", rc 128); a tool mapping any candidate-lookup git failure to UNAVAILABLE(2) would
   score 2 on `missing` (expected 1) and be failed by the counter. Pattern-matching git's
   misleading "exists on disk" stderr could similarly misroute. Both directions are caught, not
   passed, by the counter.
4. **Net:** for this cell the frozen counter cannot false-pass a wrong exit/token pair except
   via the worktree-coincidence in (2); it robustly false-fails shell-quoting and error-mapping
   bugs. Recommendation for the gate implementer: resolve `trusted`/`candidate` to commits with
   `rev-parse --verify …^{commit}`, look up each `--path` with `git ls-tree <rev> -- <path>`
   (argv list, no shell), treat absent entry or non-`blob`/`100644`→`100755` mode or differing
   blob sha at candidate as DRIFT(1), and treat only rev-resolution or trusted-source failures
   as UNAVAILABLE(2).
