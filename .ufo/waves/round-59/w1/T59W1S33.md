## Demonstration (scratch: `/fast/scratch/hyaku/tameshi-r59/T59W1S33`, now deleted;
full transcript in `receipts/evidence-transcript.txt`)

Git blob identity is content-only; the executable bit lives in the tree entry,
not the blob. Fixture A (trusted `100644` → candidate `100755`, byte-identical
content `print("real executor")\n`):

```
$ git ls-tree <trusted> -- tools/runner.py
100644 blob 74e4df76f9a60662749e2aaf076f67e311f66cdb  tools/runner.py
$ git ls-tree <candidate> -- tools/runner.py
100755 blob 74e4df76f9a60662749e2aaf076f67e311f66cdb  tools/runner.py
$ git rev-parse <t>:tools/runner.py  → 74e4df76…   (identical both sides)
$ git diff <t> <c>                   → (content-empty; mode change only)
```

Fixture B is the attack that matters operationally: trusted `100755` (executable
shebang source, the common case — base tree has 26× `100755` vs 12× `100644`
under `tools/`) → candidate `100644`, same blob. `./tools/runner.py` stops being
directly invocable while every byte of the blob is unchanged.

Two contract-correct reference implementations were built and both were run
through a scratch replica of the frozen 24-fixture matrix:

- `ref-blob-only.py` — compares blob hashes (`git rev-parse rev:path`).
- `ref-mode-strict.py` — compares full tree entries `(mode, type, oid)`
  (`git ls-tree rev -- path`).

Result: **both pass 24/24** (`REPLICA … passed=24/24 PASS=True`, receipt §5).
They diverge only on the exec-bit fixtures (receipt §6):

| case                         | ref-blob-only | ref-mode-strict |
|------------------------------|---------------|-----------------|
| A: 644 → 755, same blob      | exit 0 BOUND  | exit 1 DRIFT    |
| B: 755 → 644, same blob      | exit 0 BOUND  | exit 1 DRIFT    |
| control: identical entry     | exit 0 BOUND  | exit 0 BOUND    |

So the frozen counter cannot distinguish these two implementation classes: a
certified 24/24 evidences nothing about the mode dimension, and a blob-only
tool is certified while accepting exec-bit flips with exit 0 /
`EXECUTOR_SOURCE_BOUND`.

Adjacent same-root-cause observation (symlink surface, secondary): a symlink
whose target *string* equals the trusted file content hashes to the same blob
(`9d0045dc…`), so a blob-only tool passes a `120000` symlink as BOUND
(receipt §7) — the contract's symlink class expects DRIFT. The frozen fixture
only symlinks to `elsewhere.py` (content differs), so it too cannot catch the
content-equal variant. Same fix as below covers both.

## Is this inside the claim boundary?

**On the boundary line; the frozen text does not resolve it. Strict reading:
outside the boundary. Operational reading: inside.** Cited text:

- Exit 0: "all declared regular executable-source **blobs equal** trusted blobs."
- Trust boundary: "checks declared Git blobs only, **not execution** …"

Reading 1 (blobs-only): a Git blob is content-addressed; the mode is tree-entry
metadata, and execution semantics are explicitly out of scope. A mode-only flip
keeps blobs equal, so exit 0 is *correct by design*; the attack fails against
the claim, and the honest residual is documentation ambiguity plus the counter
coverage gap above.

Reading 2 (executable-source pin): the gate exists to bind *executor* source at
a trusted revision; the exec bit is precisely the property that makes a declared
source directly invocable. A 755→644 flip breaks invocation while the gate
stays green, which contradicts the reasonable operator reading of "regular
executable-source blobs equal trusted blobs." Under this reading a blob-only
implementation is unsound and the counter's 24 fixtures under-evidence the claim.

Either way there is a real, demonstrated defect class in the frozen artifacts:
if Reading 1 is intended, the claim should say "file mode is not pinned"; if
Reading 2 is intended, the counter has zero fixtures on the mode dimension and
cannot certify mode-strictness. This is a decision for L1; this seat does not
enlarge the claim.

## Proposed smallest sound behavior

Per declared path, resolve the full tree entry at both revisions —
`git ls-tree <rev> -- <path>` → `(mode, type, oid)` — and require: both entries
present, both `type == blob`, and `(mode, type, oid)` equal. Any deviation
(missing, nonregular, mode flip in either direction, content change) → exit 1
`EXECUTOR_SOURCE_DRIFT`; invalid/unresolvable inputs keep the contract's exit 2.

Why this is the smallest sound move:

- Same number of git invocations as `rev-parse`-per-path; no new machinery.
- Uniformly covers content, missing, nonregular (symlink), and mode — one code
  path instead of special cases.
- Consistent with the already-required symlink handling (type check is
  unavoidable for exit 1 on the symlink class).
- Strictly tighter than blobs-only and keeps every frozen fixture green (all
  fixture modes are constant `100644` except the symlink `120000`, which already
  expects DRIFT) — verified on the scratch replica for the mode-strict ref.
- Also closes the content-equal-symlink variant for free.

If L1 rules the exec bit out of boundary instead: keep blob-only comparison and
amend the claim wording to "blob content only; file mode is not pinned" — a
documentation fix only. A decision is required; the frozen text is ambiguous.

## Exact CLI test (staged at `stage/exec-bit-mode-probe.sh`)

```
python3 -I tools/executor-source-pin.py --repo "$REPO" --trusted "$T" --candidate "$C" --path tools/runner.py
```
with fixtures built by `git update-index --chmod=+x|-x` (mode-only commits,
content untouched). Three cases: 644→755 flip, 755→644 strip, identical-entry
negative control. Expected under mode-strict: exits `1, 1, 0` with DRIFT, DRIFT,
BOUND. Under blobs-only boundary: exits `0, 0, 0` plus amended claim wording.
The staged script was smoke-tested against both reference implementations
(mode-strict output reproduced exactly; receipts §6). It is a proposed test,
not a production patch; no production file was edited.

## Failed attacks (preserved)

1. **`core.filemode=false` as a defense** — fails: `git update-index --chmod=+x`
   records the mode flip in the tree even with `core.filemode=false`
   (receipt §4: `100644` → `100755` landed). The primitive is config-independent.
2. **Content diff as detection** — fails: `git diff` between the two commits is
   content-empty; only `--summary`/`ls-tree` reveal the mode change (receipt §2).
3. **"The symlink fixture already covers type confusion"** — fails for the
   content-equal variant: identical blob hash via symlink target string
   (`9d0045dc…`), blob-only ref returns BOUND (receipt §7).
4. **This attack against Reading 1 of the claim** — fails: if the boundary is
   blobs-only, exit 0 on a mode flip is correct-by-design; the finding then
   reduces to wording ambiguity + counter coverage, not a gate defect. Stated
   for honesty; the coverage gap stands under both readings.
