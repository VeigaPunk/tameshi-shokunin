## 5. Can the frozen counter misclassify this cell?

**No counter-side construction defect found for this cell.** Reasoning, with
evidence:

1. **Fixture is sound by construction.** For class `equal`, the candidate
   commit *is* the trusted commit; object graphs are identical, so a conforming
   blob-comparing gate cannot drift here. The only ways this cell fails are a
   non-conforming tool or a broken environment.
2. **Unicode path is safe.** Path bytes passed as argv, stored by git, and read
   back via plumbing are identical (`746f6f6c732f…`); CJK path is
   normalization-invariant (NFC==NFD), so no macOS-style NFD trap exists even
   hypothetically. Host is linux/ext4 anyway.
3. **Counter `ok` rule has a leniency, not an error, here.** The token test is
   a substring check over combined stdout+stderr with no exclusion of wrong
   tokens: a tool printing both `EXECUTOR_SOURCE_BOUND` and
   `EXECUTOR_SOURCE_DRIFT` while exiting 0 would pass this cell. Skipped work
   (a tool that never reads the path but prints the token and exits 0) is also
   undetectable *in this cell in isolation*. The 24-cell aggregate plus L1's
   separate skipped-work/always-accept controls are the compensating gate —
   outside my cell's scope.
4. **Worktree trap does not affect the equal cell's classification.**
   `measure.py` finishes fixture construction (ending with
   `tools/日本語.py` as a symlink to nonexistent `elsewhere.py`) before running
   any class. A tool that reads the worktree instead of commit blobs would fail
   this cell — but that is the counter *correctly failing a bad tool*, not
   misclassifying a conforming one. Blob-comparing tools are unaffected.
