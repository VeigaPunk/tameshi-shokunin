## Verdict

**NUL path handling is outside the frozen claim boundary, and it cannot be brought inside it.**
No counter defect found; no false-PASS path found. The NUL surface is closed at every
layer a path can traverse — harness argv, filesystem, and Git tree-object format — each
verified empirically in scratch (receipts below). The one observable candidate staged in
the wave (T59W1S49) already routes NUL paths to exit 2 + `EXECUTOR_SOURCE_UNAVAILABLE`,
which is exactly the smallest sound behavior; that guard is defense-in-depth and is
**untestable through the frozen CLI** because NUL cannot be delivered via `--path` argv.

## Attack surface, layer by layer (all probes observed; full transcript in receipts)

1. **CLI / argv layer — CLOSED.** `subprocess.run(["git","rev-parse","a\0b"])` and
   `os.execv("/bin/true", ["/bin/true","\x00"])` both raise `ValueError: embedded null byte`
   **in the harness before exec** (Python 3.14, posix_spawn). The tool process is never
   created, so no exit code is observable. Any harness that tries to hand the frozen tool
   a NUL `--path` fails on its own side of the fence. The frozen counter's `run()` helper
   has the same property.
2. **Filesystem layer — CLOSED.** `os.open`, `os.stat`, and builtin `open` all raise
   `ValueError: embedded null character/byte in path`. The counter's fixture construction
   (`f.write_text`) would fail the same way, before any tool invocation.
3. **Git object layer — CLOSED (structural).** A tree entry is `<mode> <name>\0<20-byte sha>`;
   NUL is the delimiter, so a name cannot contain it. Feeding
   `b"100644 a\x00b\x00"+sha` to `git hash-object -w -t tree --stdin` →
   `error: object fails fsck: badTree: cannot be parsed as a tree` /
   `fatal: refusing to create malformed object`. Feeding a NUL-laden line to `git mktree` →
   `fatal: input format error`. No committed fixture can therefore smuggle a NUL path,
   and no rev-parse/ls-tree pathspec can express one either.
