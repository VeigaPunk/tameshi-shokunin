## 4. Can the frozen counter misclassify this cell?

Empirically tested with two deliberately broken probe gates run through the
counter's exact cell shape and credit rule:

- **Probe A — naive gate mapping ANY git failure to UNAVAILABLE(2)**
  (`rev-parse candidate:path` fails → exit 2). On the missing cell it emits
  exit 2 → counter marks the cell **failed** (`expected 1, observed 2`).
  The cell does its job: it catches the realistic bug of collapsing
  "absent at candidate" into "unavailable". Rejecting direction: sound.
- **Probe B — worktree-reading gate** (`lstat` on `$REPO/tools/runner.py`).
  Because the counter leaves the worktree at the symlink checkout, the gate
  emits exit 1 DRIFT on the missing cell **without ever inspecting the
  candidate commit** → counter marks the cell **passed**. This is a genuine
  false-credit direction for this cell in isolation. It cannot scale to a
  false 24/24: the same gate is correctly failed on equal/unrelated (worktree
  symlink ≠ trusted blob → spurious DRIFT vs expected 0).

Additional structural leniencies (from reading `measure.py`, not exercised):
token is a substring match over `stdout+stderr` combined, so token text
printed for an unrelated reason with a matching exit code would be credited;
the counter checks exit+token only and cannot verify the gate compared
trusted vs candidate blobs. Both are bounded by the full 24-grid.

**Conclusion:** the frozen counter cannot be misled to 24/24 through this
cell alone. Its expectation for `tools/runner.py × missing` is
contract-correct and is precisely the discriminator between DRIFT(1) and
UNAVAILABLE(2) on a resolvable candidate with an absent declared source.
