## 2. Located semantics (object/blob type and content)

From git-cat-file(1) OPTIONS + gitrevisions(7), grounded by probe:

| Semantics | Doc location | Observed probe result |
|---|---|---|
| `-t` shows the object type identified by `<object>` | cat-file(1) OPTIONS, line 33-34 | `git cat-file -t <rev>:tools/runner.py` → `blob`, exit 0 |
| `-p` pretty-prints content of `<object>` by type | cat-file(1) OPTIONS, line 46-47 | `git cat-file -p <rev>:tools/runner.py` → exact file bytes `print("real executor")` |
| `<rev>:<path>` names the blob or tree at that path in the tree-ish | gitrevisions(7), line 230-236 | works with spaces in path (`tools/space name.py` → `blob`) |
| blob = contents of a file (glossary); committed regular file is a blob | gitglossary "blob object" | `hash-object` of the working file equals the committed blob id |
| symlink is stored as a blob whose content is the link target | (probe + git object model; cat-file(1) does not distinguish mode) | `-t` → `blob`; `-p` → `runner.py` (the target string) |
| missing path at a rev → fatal error, non-zero exit | cat-file(1) / probe | `fatal: path 'tools/absent.py' does not exist in '<rev>'`, exit 128 |
| unresolvable object (all-zero sha) → fatal error | cat-file(1) / probe | `fatal: git cat-file: could not get object info`, exit 128 |

Precision point for the tool builder: `cat-file -t` reports `blob` for **both** regular
files and symlinks — the regular-vs-symlink distinction lives in the tree entry mode
(100644 vs 120000, see git-ls-tree(1)), not in the blob type. A gate that must reject the
`symlink` fixture class cannot rely on `-t` alone; it needs the tree mode (e.g.
`git ls-tree <rev> -- <path>`) or an lstat-side check. This narrows what S289 can support.

     tree-ish object" — gitrevisions(7) `<rev>:<path>`, Git 2.56.0, fetched 2026-10-30.
  Proposed row staged at `stage/corpus/SOURCES.md` (append-only, NF=13 census-clean).
  L1 owns final integration and the S289 id collision check; this seat used the id
  only as proposed by the wave spec.

- **REJECT — adjacent candidate: "execution attestation inference."** Reason: the
  located docs define only object storage semantics (type, content, path resolution,
  error behavior). Byte-equal blobs at trusted and candidate revisions are a static
  content comparison; git's documentation makes no claim that equal content implies
  equal execution, and the gate never runs the code. Claiming C1 as execution
  attestation would contradict contract.json `trust_boundary` ("checks declared Git
  blobs only, not execution…") and would repeat the round-58 C2 overreach. Flip: only
  if a separate measured execution-attestation layer lands with its own source row —
  never by widening S289.
