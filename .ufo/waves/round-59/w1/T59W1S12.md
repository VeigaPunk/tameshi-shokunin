## Can the frozen counter misclassify this cell? — adversarial probes

Three stub "tools" run through scratch `measure.py` (`--tool` override), each exercised on all 24 cells:

| stub | behavior | my cell `ok` | run total | reading |
|---|---|---|---|---|
| `stub_drift` | always prints `EXECUTOR_SOURCE_DRIFT`, exit 1, no real check | **true (false pass)** | 12/24 | counter checks exit+token substring only; forged reasoning is invisible at cell level |
| `stub_lower` | lowercase `executor_source_drift`, exit 1 | false | 0/24 | token match is case-sensitive; forgery rejected |
| `stub_noisy` | exit 1 plus contradictory `DRIFT`/`UNAVAILABLE`/`BOUND` tokens | **true (false pass)** | 12/24 | contradictory/extra output not penalized |

Conclusions for this cell:
- **False-pass is possible at cell granularity** by any process emitting exit 1 + the exact token;
  the counter is black-box (exit code + token substring). The compensating control is the
  24-cell matrix aggregate — an always-DRIFT stub stops at 12/24 and never certifies. A tool
  conformant on the other 23 cells cannot be forged through this one cell alone in a way that
  changes the aggregate beyond its own conformance.
- **False-fail risk lives in tool implementations, not the counter**: the committed 120000 blob
  must map to DRIFT(1). A tool that dereferences the broken worktree symlink and reports
  UNAVAILABLE(2) would fail this cell even though the candidate commit is resolvable — the fixture
  deliberately leaves a broken relative symlink; correct tools must inspect the git object
  (mode/type), not the filesystem.
- Robustness note: even if a filesystem/git config collapsed the symlink to a regular blob
  (e.g. `core.symlinks=false` storing `elsewhere.py` as mode 100644), content still differs from
  trusted → same DRIFT(1) outcome. The cell's expected verdict is stable across those failure modes.
