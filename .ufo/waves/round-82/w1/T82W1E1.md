## Disagreements with the plan

**D-1 (record defect).** Plan R82-C1's before-bullet says
`c1-before-directory-closed.txt` shows the `tree-paths` directory row measuring
`state=closed detail=paths-present`, **exit 0**. The committed file (unchanged at
the landing tip `b6658e7a`) is:

```
# base instrument: a DIRECTORY satisfies a path row (cat-file -e accepts a tree)
defect-bind: blob-unresolvable:4dfc3181310088c2f32d51e87a4d82c047d05231:.ufo/evidence/round-81
DEFECT_BIND_ROW dir kind=tree-paths expect=closed state=closed detail=paths-present
exit=2
```

It carries a **setup refusal** (`blob-unresolvable`, which is exactly what the base
`tree-bytes` does on a directory, my A6), has **no `DEFECT_BIND:` summary line**,
and ends `exit=2` — not the plan's exit 0, and no row count to verify. The
receipt header also says "cat-file -e accepts a tree" while the printed error is
the `cat-file blob` refusal, conflating the two row kinds. My independent base run
(A5 above) shows the plan's prose is **true**; the artifact is what is unfaithful.
Route to the reissued-receipts list (same class as the round-81 closure item 1).
Suggested faithful receipt: the A5 three lines plus `exit=0`, and keep the
`tree-bytes`-on-a-directory refusal in its own file.

**D-2 (hardening defect, not a claim failure).** `--manifest-rev` is defeated by a
git replace ref: `git cat-file blob REV:PATH` resolves `REV` through
`refs/replace/`, so the "bytes committed at the declared revision" can be
different from the bytes of the object named by `REV`. Fixture proof (mktemp,
`git init`): C1 commits `m.json` with 3 rows; C2 commits `m.json` with 2 rows;
disk holds the 2-row bytes. Control without a replace ref:
`defect-bind: manifest-rev-mismatch:<C1>:m.json`, exit 2. Then
`git -C "$D" replace "$C1" "$C2"`:

```
plain  git cat-file blob <C1>:m.json           -> 2 rows   (replaced)
git --no-replace-objects cat-file blob <C1>:m.json -> 3 rows (true object)
$ python3 -I -X utf8 <declared-bytes> --repo "$D" --manifest m.json --manifest-rev <C1>
DEFECT_BIND_ROW r1 kind=tree-paths expect=closed state=closed detail=paths-present
DEFECT_BIND_ROW r2 kind=tree-paths expect=closed state=closed detail=paths-present
DEFECT_BIND: rows=2 closed=2 open=0 unexpected=0 manifest=bound
exit=0
```

`GIT_NO_REPLACE_OBJECTS=1` in the caller's environment does not help: `_git_env()`
strips every `GIT_*` variable, so the mitigation is unreachable from outside. The
tool must set it itself. I verified the one-line fix on a scratch copy (never the
lane): adding `env["GIT_NO_REPLACE_OBJECTS"] = "1"` to `_git_env()` makes the same
fixture read `defect-bind: manifest-rev-mismatch:<C1>:m.json`, exit 2. Severity:
requires repo write (a `refs/replace/` ref) — the same privilege class as
committing a narrowed manifest — so it does not fail the claim under its guarded
premise ("with the instrument, the manifest and the register's declared population
unchanged"), but it is a real gap in "bound to its declared revision" and a cheap
hardening.

**D-3 (declared-limit note on the counting command).** The counting command uses
`--manifest-rev HEAD`, and HEAD is caller-chosen. Two consequences measured:
(i) it binds at `4dfc3181` as well (manifest bytes identical), so a green bound
line does not by itself say the register is at the declaration; (ii) a narrowed
manifest that is **itself committed** at HEAD binds and certifies `rows=2 closed=2
open=0 unexpected=0 manifest=bound`, exit 0 (fixture C3b), while
`--manifest-rev <wide commit>` refuses the same disk bytes with
`manifest-rev-mismatch`. The plan's kill rule presumes the register unchanged, so
this is not a predicate failure; for any reissued kill-rule check, pass the frozen
declaration sha (or the landing commit) rather than `HEAD`, and/or compare
`git rev-parse <rev>:tools/defect-bind.json` against `d92d6bea`. (The L1's reissued
`manifest-binding.txt` already pins an explicit rev — that is the right shape.)

**D-4 (semantic, consistent with the plan).** Without `--manifest-rev` the counter
still prints a green six-row line with `manifest=unbound`. The plan's kill rule
names this case, so the flag must be present verbatim in the counting command.

**D-5 (semantic, by design).** The binding pins the denominator, not each row's
revision. Fixture: HEAD deletes `f2.txt`; a bound manifest at HEAD whose row 2 says
`"rev": "<C1 sha>"` where `f2.txt` still exists reads
`DEFECT_BIND: rows=2 closed=2 open=0 unexpected=0 manifest=bound`, exit 0
(`f2` absent at HEAD confirmed). The declared register's rows are all
`"rev": "HEAD"`, so the register does not exploit this.

**D-6 (base nuance for item (f)).** At the base bytes a directory under
`tree-bytes` is a **setup refusal** (exit 2, no row), not a `min-bytes-met`
certification; `min-bytes-met` is unreachable there for a different reason than
the declared instrument's `not-regular-file`. Worth one clause if the plan's
before/after table is reissued.

Also checked: `tools/defect-bind.json` carries no conversion attributes —
`git check-attr text eol filter -- tools/defect-bind.json` prints `unspecified`
three times and `git ls-files --eol` shows `attr/` empty, so the S311 declared
limit's premise holds for this path and exact byte equality is legitimate.
