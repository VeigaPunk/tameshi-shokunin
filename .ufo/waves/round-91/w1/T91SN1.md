## F1 — HIGH — the C2 counter runs the candidate's own measuring tool

`c2/measure-c2-v91.sh:33`:

```sh
db=$(cd "$R" && python3 -I -X utf8 tools/defect-bind.py --repo . --manifest "$WORK/manifest.json" 2>&1); dbrc=$?
```

`$R` is the **clone of the candidate tree** at `REV`. `tools/defect-bind.py` is
read from that candidate worktree, so the artifact that decides the `rows`
conjunct is the very artifact under test. The plan's predicate binds the
repair to *"what the repairs do"* (QUALITY 141) and requires the `rows` conjunct
to be a **measurement**; a candidate that ships a stub emitting the expected
summary line converts the conjunct into an assertion.

**Exploit path (executed, end-to-end).** In a scratch clone of the lane at the
C2 instrument commit `048c3f30`, replace `tools/defect-bind.py` with a stub that
prints the three `DEFECT_BIND_ROW` lines and `DEFECT_BIND: rows=3 closed=3
open=0 unexpected=0` and exits 0. The committed docs are **not** touched:

```
committed note   'not admitted' count: 0
committed lesson 'receipt addendum'  : 0
counter exit=0
toolpin=ok expect=0839f5875a7a3baf694d993316a2cca6b38b449561a76e0bf54dd1988ebf8d37 src=ff7a4b06
C2_SUMMARY rev=576d86350ea6178de95d462bf1a64b14e89be814 manifest=pinned
            rows=ok argv=ok toolpin=ok blobrun=ok defect_bind_exit=0
C2_R91_PASS=true
```

The note lacks the marker the manifest row `R90-1-not-admitted-marker` demands
and the lesson lacks the round-91 receipt addendum, yet the counter certifies
`closed=3 open=0`. This is kill-rule (a) for R91-C2 — *"a committed state
reaches `C2_R91_PASS=true` while a non-author reading finds item 1 or 2 not
actually repaired"* — met by the counter itself, not by an attacker.

Note the contrast with C1: `measure-v91.py` runs **no** candidate-supplied
tool. Its gate is the fleet's `scripts/sources-census.sh` fetched from the
fleet repo at a **sha256-pinned** commit, and the note/spec are read as git
objects. C1's measurement path is closed; C2's is open.

**Impact.** The R91-C2 claim ("the round-90 closure's routed items 1-2 closed
over committed bytes") is not currently falsifiable by the counter that is
supposed to certify it. A landing revision that ships a stubbed
`tools/defect-bind.py` reaches `C2_R91_PASS=true` with the repairs absent.

**Smallest remediation.** Execute the measuring tool from a **pinned blob**, not
from the candidate worktree — the same shape C1 already uses for its gate:
fetch `tools/defect-bind.py` by full commit id from a known-good revision into
`$WORK` and run that copy against `$R`. Alternatively pin the tool's sha256
alongside `MANIFEST_SHA` and verify before executing.

## F2 — HIGH — `toolpin` is a self-comparison that can never fail

`c2/measure-c2-v91.sh:59-62`:

```sh
git -C "$R" show "ff7a4b06:tools/ledger-witness.py" > "$WORK/blobrun-ledger-witness.py" 2>/dev/null || true
expect=$(sha256sum "$WORK/blobrun-ledger-witness.py" 2>/dev/null | cut -d' ' -f1)
pinned=$(sha256sum "$WORK/blobrun-ledger-witness.py" 2>/dev/null | cut -d' ' -f1)
[ -n "$expect" ] && [ "$expect" = "$pinned" ] && toolpin=ok
```

`expect` and `pinned` are both computed from the **same file**. The comparison
is `x == x`. The `|| true` also swallows a failed `git show`, in which case the
redirect leaves a **zero-byte** file; `sha256sum` of that is
`e3b0c442…`, a non-empty string, so the `-n "$expect"` guard passes too.

**Evidence (P1):**

```
expect=e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
pinned=e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
RESULT: toolpin would be OK even for a MISSING/EMPTY blob
```

The plan's predicate says: *"the row's tool blob hashes to the sha256 its
`source:` pin names"* — the registry row names `source:
tools/ledger-witness.py@ff7a4b06:1-60`, and the counter must compare the
fetched bytes against **that pin**. It compares them against themselves. The
`toolpin` conjunct carries no information: it cannot distinguish the pinned
blob from any other blob, including an absent one.

**Impact.** The conjunct advertised in the receipt line
`toolpin=ok expect=<hash> src=ff7a4b06` is decoration. Whatever bytes the
`git show` yields are hashed and compared to themselves.

**Smallest remediation.** Hash the fetched file once and compare it against a
**literal pinned digest** (the value the plan freezes, i.e. the sha256 of the
blob at `ff7a4b06`), failing the conjunct on a mismatch — and treat an empty
or unreadable blob as a hard failure rather than a hash of zero bytes.

## F3 — HIGH — the "pinned" blob is fetched by an abbreviated rev, shadowable by candidate refs

`c2/measure-c2-v91.sh:59` fetches the witness tool with
`git -C "$R" show "ff7a4b06:tools/ledger-witness.py"`. `ff7a4b06` is an
**8-hex abbreviation**, resolved by git against the refs present in `$R` — the
**candidate's** clone. A candidate that creates a branch or tag named
`ff7a4b06` makes the name ambiguous; git then resolves it to the candidate's
object, and the counter extracts the attacker's bytes as "the pinned blob".

**Evidence (P2 / P2b):**

```
true pinned blob sha (lane @ff7a4b06): 0839f5875a7a3baf694d993316a2cca6b38b449561a76e0bf54dd1988ebf8d37
shadowing tag resolves to        : warning: refname 'ff7a4b06' is ambiguous.
```

and end-to-end through the counter, with a candidate tag `ff7a4b06` pointing at
a two-line stub that prints `LEDGER_WITNESS_SELFTEST: 21/21 pass` and exits 0:

```
toolpin=ok expect=98f352ccb2e3da9baf53b9504744f48f45ca29c2ce9e0bec9a09123c21fc9836 src=ff7a4b06
C2_SUMMARY ... rows=fail argv=ok toolpin=ok blobrun=ok
```

Note `expect=98f352cc…` — **not** the pinned `0839f587…`. The blobrun conjunct
still passed because it only greps the output for the literal
`LEDGER_WITNESS_SELFTEST: 21/21 pass`. F2 and F3 compound: the pin is not
checked, and the source of the bytes is candidate-controllable.

**Impact.** The plan's predicate requires the selftest to run *"from the pinned
blob (never the candidate tree)"*. As written, the blob is selected by a
candidate-controlled namespace, so that requirement is not met.

**Smallest remediation.** Use the **full 40-hex** commit id
(`ff7a4b06` → the full id) so resolution is object-id-exact and no ref can
shadow it, and combine with F2's literal-digest comparison.

## F4 — MEDIUM — the C2 counter applies no git seal and no `replace` refusal

`c2/measure-c2-v91.sh` contains **zero** occurrences of `GIT_NO_REPLACE_OBJECTS`
or `GIT_CONFIG_*`, and **zero** occurrences of `replace`. Every git call in it
(clone, checkout, `show`) inherits the ambient environment.

Contrast `c1/measure-v91.py`, which was sealed for exactly this in round 91:

- `measure-v91.py:38-42` — `sealed_env()` sets `GIT_NO_REPLACE_OBJECTS=1`,
  `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, and pops `HOME`;
- `measure-v91.py:169-174` and `:181-186` — a non-empty `git replace -l` in the
  lane repo **or** the fleet repo refuses setup (`replace-refs-present:<label>`).

The C2 counter has neither. The V4 control receipt in the frozen evidence shows
the C1 behaviour working as designed:

```
control=V4-replace rev=ff5382e… replace_l=ff5382e…
C1_SETUP replace-refs-present:lane
C1_R91_PASS=false
exit=2
```

**Evidence that the ambient env leaks.** With the exact `sealed_env()` replica,
`git config --list --show-origin` sees **only** `file:.git/config` — no global
`credential.helper`, no `safe.directory`, no user identity (P11). That
isolation is present in C1 and absent in C2.

**Impact.** The C2 counter inherits ambient `GIT_*` state: `GIT_DIR`,
`GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, and
`GIT_CONFIG_GLOBAL` all steer it. A `refs/replace` in the lane repo is not
refused (the manifest read at `:27` is sha256-pinned, so that specific read is
caught by `MANIFEST_SHA`; the tool-blob and blob reads are not, see F3). The
asymmetry also means the round's own QUALITY 139 discipline covers one of the
two counters it ships.

**Smallest remediation.** Give `measure-c2-v91.sh` the same treatment C1 got: a
`sealed_env`-equivalent (`GIT_NO_REPLACE_OBJECTS=1`,
`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, unset `HOME`) for every
git invocation, plus a non-empty `git replace -l` refusal for the lane and the
fleet repos before setup.

## F5 — MEDIUM — ambient `GIT_DIR` defeats the "toplevel" guard

`c2/measure-c2-v91.sh:24` and `c2/controls-c2-v91.sh:23`:

```sh
[ "$(git -C "$R" rev-parse --show-toplevel)" = "$R" ] || { echo "C2_SETUP toplevel"; …; exit 2; }
```

This guard is the driver's only assertion that the clone is its own toplevel —
the check the 2026-11-06 fleet incident (`git -C ""` falling back to the fleet
root) exists to provide. It is defeated by an ambient `GIT_DIR`.

**Evidence (P5):**

```
plain   : git -C p5/clone rev-parse --show-toplevel -> …/probeout/p5
GIT_DIR : git -C p5/clone rev-parse --show-toplevel -> …/probeout/p5/clone
GIT_DIR : 'git -C p5/clone checkout' rc=0 (operates on the injected GIT_DIR, not the clone)
```

With `GIT_DIR` set, `--show-toplevel` reports the *current directory* (so the
guard's `= "$R"` comparison is satisfied) while every actual git operation —
`checkout`, `show`, `rev-parse HEAD` — acts on the **injected** repository.
`GIT_WORK_TREE=/tmp/evil` likewise makes `--show-toplevel` report the injected
tree. The same idiom in `c2/controls-c2-v91.sh:23` compares against
`$(realpath -- "$r")` and has the same weakness.

**Impact.** The containment assertion that these drivers rely on does not
establish which repository git is operating on. Under the seat's own host guard
the process CWD is the fleet root, so a mis-set `GIT_DIR` silently redirects
the "scratch clone" work at another repository while the guard reports success.

**Smallest remediation.** Assert the clone's identity from the **object store**,
not from `--show-toplevel`: after the clone, verify
`git -C "$R" rev-parse --git-dir` resolves inside `$R` **and**
`git -C "$R" rev-parse HEAD` equals the expected commit, and scrub `GIT_DIR`
/ `GIT_WORK_TREE` / `GIT_INDEX_FILE` from the environment first (F4).

## F6 — MEDIUM — ambient git env steers the mutating fixture writes

The mutating calls in the controls drivers run with the ambient environment:

- `c1/controls-v91.py:98` (`git clone`), `:116` / `:168` (`git -C repo add -A`),
  and the commits that follow;
- `c2/controls-c2-v91.sh:22` (clone), `:26` (`add -A` + `commit`).

Both drivers *do* assert the clone's toplevel (`:100-101` in C1, `:23` in C2) and
both use an explicit fixture identity — those are correct. But the surrounding
environment is not scrubbed, so:

**`GIT_INDEX_FILE` (P6).** `git add -A` writes its index to the ambient path
instead of the clone's own:

```
ambient index written outside the clone: -rw-r--r-- 1 vgpnk vgpnk 3387160 … p6.ambient.idx
```

A write lands **outside** the scratch directory — the exact property the
assignment asks about ("no write can land outside the scratch dir").

**`core.hooksPath`.** The `git commit` at `c2/controls-c2-v11.sh:26` sets
`-c user.name/-c user.email` but not `core.hooksPath`, so an ambient
`core.hooksPath` executes a **hook** during the fixture commit. Verified
locally: the hook ran, and a file it wrote landed outside the repository. A
hook is arbitrary code execution in the driver's context.

**Impact.** Under a hostile or merely unusual ambient git configuration, the
fixture commits and the C2 counter's own `git clone`/`checkout` can be
redirected or can execute code outside the scratch tree. The toplevel assertion
does not cover the index or the hook path.

**Smallest remediation.** Scrub `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`,
`GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG_GLOBAL`
and `GIT_CONFIG_NOSYSTEM` for every git invocation in both controls drivers, and
pass `-c core.hooksPath=/dev/null` on the fixture commits.

## F7 — MEDIUM — `fixes-v91.py --target` can forge corpus files in an unintended tree

`c2/fixes-v91.py:78-79` resolves `--target` with `os.path.realpath` and
derives two paths under it; `append()` at `:68-69` opens with mode `"a"`:

```python
def append(path, text):
    with open(path, "a", encoding="utf-8") as f:
```

Mode `"a"` **creates** the file if it is absent. There is no check that
`--target` is a git worktree, that the files exist, or that the target is the
lane rather than a sibling.

**Evidence (P8).** Pointed at a directory shaped like a sibling lane
(`corpus/knowledge/` + `corpus/lessons/` present), it **created**:

```
./corpus/knowledge/other-note.md
./corpus/knowledge/mutation-case-fleet-sources-census.md      <-- created
./corpus/lessons/round-90.md                                  <-- created
--- head of the forged note:
## Admission status (appended round 91)
```

i.e. it wrote a "not admitted" admission marker for R90-C1 into a tree that
never ran R90-C1. Pointed at a fleet-root-shaped tree (no `corpus/`), it fails
cleanly with `FileNotFoundError` and creates nothing (exit 1) — so the hazard is
precisely the "plausible-looking sibling" case.

**Impact.** The L1 is to land these repairs by running this generator. A
mistyped `--target` (a sibling lane, or any tree with the same shape) silently
**creates** a plausible-looking case note and lesson addendum rather than
refusing. The C2 counter then measures the forged bytes and reports them as a
genuine repair — the same "fabricated provenance" shape as F1.

**Smallest remediation.** In `fixes-v91.py`, refuse unless `--target` is a git
worktree whose `rev-parse --show-toplevel` equals the resolved target **and**
both destination files already exist; open with `"r+"` (or read-then-write) so
a missing file is an error rather than a creation.

## F8 — LOW — empty `--repo` / `--rev` fall back to the CWD and to the index

`c1/measure-v91.py:161-163`:

```python
repo = os.path.realpath(a.repo)
rev  = a.rev
```

- `--repo ''` → `os.path.realpath('')` is the **process CWD**. Under the seat's
  host guard the CWD *is* the fleet root — the 2026-11-06 incident shape
  (`git -C ""` falling back to the fleet root) reproduced at the argument
  boundary. **Evidence (P4):**
  `realpath('') = /home/vgpnk/Projects/shokunin` and
  `git -C '' rev-parse --show-toplevel: /home/vgpnk/Projects/shokunin`.
  Mitigating: the counter then refuses with `C1_SETUP replace-list-failed:lane`
  in this environment, because the fleet root is not itself a worktree — but
  that is incidental, not an assertion.
- `--rev ''` → `blob()` at `:53-56` builds `f"{rev}:{path}"` = `":path"`, which
  git resolves against the **index**, not a commit. **Evidence (P9):** the index
  blob carried 1 occurrence of a staged marker the HEAD blob did not. So the
  "committed bytes" property of the C1 counter silently degrades to "staged
  bytes" for an empty rev. (`git cat-file blob :path` → index; `HEAD:path` →
  commit.)

**Impact.** Low — both require an empty argument, and the frozen counting
commands always pass a real rev. But the guards are absent rather than
refusing, and the `git -C ""` → fleet-root behaviour is the recorded fleet
incident.

**Smallest remediation.** Refuse an empty `--repo`/`--rev` explicitly (and
assert `repo` is the expected lane), and use `f"{rev}:{path}"` only after
asserting `rev` is a full 40-hex commit id.

## F9 — LOW — scratch is not removed on the failure paths

- `c1/controls-v91.py:95` and `:126` — `shutil.rmtree(d)` runs only on the
  **success** path of `run_ctl`/`run_real`; `raise SystemExit` at `:101` (toplevel
  mismatch) and the `sh()` failure at `:27` leave the clone behind.
- `c2/controls-c2-v11.sh:22-26` — four `|| exit 3` paths abandon `$d`
  (clone + `fixes.log` + work dir) without removing it; only `:30` cleans up on
  success.
- `c2/measure-c2-v91.sh` — no `trap`, no cleanup: the clone at `$WORK/repo` and
  `$WORK/tmp` persist after the run (the caller owns `$WORK`, so this is by
  design, but a caller that points `--work` at a scratch dir gets it back
  populated).
- `c1/measure-v91.py` — no `trap` either; `--work` is likewise left populated
  (by design), but the gate's own `mktemp -d` under `TMPDIR` (`env_for(work)`
  at `:59-62`) is inside `--work`, so it is contained.

**Impact.** Low. Under normal operation the drivers clean up their own
subdirectories. On the failure paths a `--shared` clone plus its work dir is
left in the scratch area, and there is no `trap` to remove it if the process is
interrupted (the round-90/91 counters are long-running; the observed
`controls-v91.py` run exceeded 300 s).

**Smallest remediation.** Wrap the per-control bodies in a `try/finally` (or
`trap ... EXIT`) that removes the control directory, and add the same to
`controls-c2-v91.sh`'s `fixture()`/`real()`.

## Checks that came back clean

  drops `HOME` and pins `GIT_CONFIG_GLOBAL=/dev/null` +
  `GIT_CONFIG_NOSYSTEM=1`; under that exact env `git config --list --show-origin`
  reports **only** `file:.git/config` — the user's global
  `~/.config/git/config` (which contains `credential.helper = …gh auth
  git-credential` and `credential.helper =
  /usr/lib/git-core/git-credential-libsecret`) is **not** visible (P11). The
  C2 counter does not seal (F4), but it makes no network call and reads no
  credential file, so no credential is exposed today — the gap is the config
  surface, not a live leak.
- **The C1 counter's `replace` refusal works.** `measure-v91.py:169-186` refuses
  a non-empty `git replace -l` in both the lane and the fleet repo; the frozen
  `V4-replace.out` receipt shows `C1_SETUP replace-refs-present:lane` / exit 2.
  Also confirmed: `git clone --shared` does **not** copy a source repo's
  `refs/replace` into the clone, so a lane replace ref does not reach a clone's

- **The C1 counter's tar extraction is traversal-safe.**
  `measure-v91.py:70` uses `t.extractall(dest, filter="data")` — the
  Python 3.14 `data` filter, which refuses absolute paths, `..` traversal and
  out-of-tree links.
- **The C1 counter reads committed bytes, not the worktree.** `blob()`
  (`:53-56`) and the spec/note/SOURCES/README reads all go through
  `git cat-file blob <rev>:<path>` under the sealed env, and the spec is
  sha256-pinned (`SPEC_SHA`). The defect-bind rows it drives are therefore
  measured over committed bytes — the property F1 shows C2 lacks.
- **The C1 controls driver asserts the clone's toplevel before any commit**
  (`controls-v91.py:100-101`, `:157-159`) and commits under an explicit fixture
  identity (`-c user.name=r90-fixture -c user.email=r90-fixture@invalid`); the
  C2 controls driver does the same (`:23`, `:26`). No `git -C ""` and no
  empty-variable path reaches `git -C` in either driver: the C1 driver builds
  `repo` from `os.path.join(d, "repo")` under its scratch dir, and the C2 driver
  from `$SC/c2fx-$1/repo`.
- **C2's manifest read is pinned.** `measure-c2-v91.sh:29-30` compares the
  manifest bytes to the frozen `MANIFEST_SHA`
  (`cfb58144…61a`), which matches the lane's
  `tools/defect-bind-r91.json` — so substituting the manifest is caught even
  though the C2 counter does not refuse replace refs (F4).
- **No lane or fleet file was written by this seat.** `git status --porcelain` in
  the lane shows only the untracked wave directory
  (`.ufo/waves/round-91/w1/`). The probe writes exclusively under
  `/fast/scratch/hyaku/tameshi-r91/T91SN1/`.
