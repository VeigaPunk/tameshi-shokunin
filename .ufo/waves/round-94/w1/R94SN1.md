## F1 — HIGH — the C2 checker has no git seal; replace-refs and ambient `GIT_DIR` substitute the graded bytes

**Where:** `.ufo/evidence/round-94/conjunct-disposition-v94.py`, `main()`:

```python
blob = subprocess.run(["git", "-C", lane, "cat-file", "blob",
                       a.rev + ":" + a.counter], capture_output=True)
...
mb = subprocess.run(["git", "-C", lane, "cat-file", "blob", a.rev + ":" + a.manifest],
                    capture_output=True)
```

Neither call passes `env=`. The ambient environment therefore reaches git, so
`GIT_DIR`, `GIT_WORK_TREE`, `GIT_OBJECT_DIRECTORY` and `refs/replace/*` all apply.

The C1 counter is sealed (`sealed_env()` sets `GIT_NO_REPLACE_OBJECTS=1`,
`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`) and additionally refuses
setup when `git replace -l` is non-empty in the lane or the fleet repo
(`measure-v94.py:378,392`). **The C2 checker has neither.** It is the only
round-94 instrument that reads git objects without the seal, and it is the
instrument that produces the C2 claim's verdict.

**Exploit path (both verified end-to-end against the committed rev-3 checker):**

1. *Replace-ref.* Plant `refs/replace/<manifest-blob>` in the lane repo pointing at
   a manifest whose every row is `{"state":"pos-real","mode":"conjunct-false"}`.
   Plain `git cat-file blob REV:manifest` then returns the **replaced** blob, so the
   checker grades the forged manifest:

   ```
   $ git -C fx.lane replace <real-manifest-blob> <forged-manifest-blob>
   $ python3 -I conjunct-disposition-v94.py --lane fx.lane --rev $REV --min-falsifiable 17
   DISPOSITION rows=19 falsifiable=19 unfalsifiable=0 findings=0     <-- forged passes
   $ GIT_NO_REPLACE_OBJECTS=1 python3 -I conjunct-disposition-v94.py --lane fx.lane --rev $REV --min-falsifiable 17
   DISPOSITION rows=19 falsifiable=17 unfalsifiable=2 findings=0     <-- honest
   ```

   The forged verdict is precisely the A4 cheat the round exists to close: 19/19
   "falsifiable", 0 "unfalsifiable", `findings=0` — a green PASS on a manifest that
   asserts nothing is unfalsifiable. The honest reading of the same repository under
   the C1 counter's seal is `falsifiable=17 unfalsifiable=2 findings=0`. The seal is
   the only difference.

2. *Ambient `GIT_DIR`.* With `GIT_DIR=<other repo>/.git GIT_WORK_TREE=<other repo>`
   exported, `git -C lane cat-file` reads the **other** repository's objects. The
   checker prints `rows=19 falsifiable=19 unfalsifiable=0 findings=0` from the
   attacker repo's counter and manifest while the `--lane`/`--rev` arguments still
   name the real lane. Note this vector survives `GIT_NO_REPLACE_OBJECTS=1`
   (verified) — only scrubbing the whole `GIT_*` namespace, as `sealed_env()` does,
   stops it.

**Impact:** the C2 claim ("every conjunct is falsifiable by a committed battery
receipt, or declared with a state/digest reason") can be certified from bytes that
were never committed at the named revision. The claim's own kill rule (d) — "the
checker or manifest blob at the named revision differs from the sha256 named here" —
is exactly the property this breaks, and the checker never verifies it.

**Smallest remediation:** give the C2 checker the same seal the C1 counter has —
one `sealed_env()`-equivalent used by all three of its `subprocess.run` calls
(`GIT_NO_REPLACE_OBJECTS=1`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`,
and no inherited `GIT_*`) — and refuse setup when `git -C lane replace -l` is
non-empty, mirroring `measure-v94.py:374-392`. Also print and pin the manifest
blob's sha256 so kill rule (d) is checkable from the checker's own output.

## F2 — HIGH — the C2 checker grades receipts from the working tree, not from `--rev`

**Where:** `conjunct-disposition-v94.py:247`

```python
rdir = os.path.join(lane, a.receipts)
```

The counter and the manifest are read from `a.rev` through git; the **receipts are
read from the filesystem under `--lane`**. `a.rev` does not constrain the evidence.

**Exploit path (verified):** take the real lane content in a scratch clone and
edit one receipt in the working tree only, leaving it uncommitted:

```
$ python3 -I conjunct-disposition-v94.py --lane $LC --rev HEAD --min-falsifiable 17
DISPOSITION rows=19 falsifiable=17 unfalsifiable=2 findings=0     <-- green
$ # edit only pins-mutated.out: pins=false -> pins=true   (uncommitted)
$ git -C $LC status --porcelain
 M .ufo/evidence/round-94/pre-freeze/controls/pins-mutated.out
$ python3 -I conjunct-disposition-v94.py --lane $LC --rev HEAD --min-falsifiable 17
DISPOSITION_FINDING no-flip pins: receipt shows pins=True on state pins-mutated
DISPOSITION rows=19 falsifiable=17 unfalsifiable=2 findings=1     <-- flipped
```

**Second, structural consequence.** The receipts are not even present at the
frozen revision:

```
$ git ls-tree -r --name-only 7084358c... .ufo/evidence/round-94/pre-freeze/ | wc -l
0
$ git ls-tree -r --name-only HEAD    .ufo/evidence/round-94/pre-freeze/ | wc -l
55
```

The receipts were added by `33279f40`/`4dc919ac`, which are **descendants** of the
frozen rev. So a checker run with `--rev 7084358c...` against a rev-pinned clone
finds **no receipts at all** and prints `findings=17`; the green `findings=0`
verdict is reachable only against the *live* lane working tree. The frozen
predicate `DISPOSITION rows=19 falsifiable=17 unfalsifiable=2 findings=0` is
therefore not reproducible from the frozen revision — it is a statement about
whatever is on disk now.

**Impact:** the C2 verdict is not pinned to any revision. Any party who can write
into the lane working tree can change the C2 verdict without a commit, and the
"frozen rev" in the predicate does not bind the evidence.

**Smallest remediation:** read each receipt from `git cat-file blob <rev>:<receipts>/<state>.out`
(the same way the manifest and counter are read) and die at setup when a named
receipt is absent at `a.rev`. The receipts must be committed *before* the revision
the claim names, or the claim must name the revision that contains them.

## F3 — HIGH — the C2 checker accepts hand-written receipts; the counter never has to run

**Where:** `conjunct-disposition-v94.py`, `check()` — the receipt body is parsed
for a `C1_CONJUNCTS` line and the named conjunct's boolean:

```python
body = open(path, encoding="utf-8", errors="replace").read()
conj = receipt_conjuncts(body)
if k not in conj: ... elif conj[k] is not False: ...
```

There is no binding between a receipt and the counter bytes that produced it. The
driver writes `CONTROL_INSTRUMENT sha256=...` to **stdout only**, and only the
mutant (D01-D05) receipts carry a `counter_sha=` line (verified: **40 of 45**
committed receipts have no `counter_sha=`).

**Exploit path (verified):** in a scratch fixture lane, write the receipt set by
hand — 16 files, each a single line
`exit=1\nC1_CONJUNCTS selfpin=false pins=false ... n_min=false` — with no clone,
no counter invocation, no counter bytes anywhere:

```
$ python3 -I conjunct-disposition-v94.py --lane fx.fab --rev $REV --min-falsifiable 17
DISPOSITION rows=19 falsifiable=17 unfalsifiable=2 findings=0     <-- green
```

Contrast: the same checker on the same manifest with the *real* receipts present
also prints `findings=0`. The checker cannot tell the two apart.

**Impact:** the C2 claim asserts each conjunct is falsified "by a named committed
battery receipt". The checker verifies only that a file with the right text exists
at the right path. A receipt set authored by hand satisfies the claim as
certified. Combined with F2 (receipts are not rev-pinned) the claim's evidence
chain is: an unpinned, unattested text file.

**Smallest remediation:** require each receipt to carry the producing counter's
sha256 (the driver already computes it as `CONTROL_INSTRUMENT`), the driver
sha256, and the parent rev, and have the checker verify all three against the
revision it is auditing. The plan's own amendment list already asks for
`counter_sha=` in every `run_ctl` receipt — that amendment is unimplemented.

## F4 — MEDIUM — the receipt grader reads the highest-index `.rerun-N.out`, contradicting the driver's own docstring

**Where:** `controls-v94.py`, `receipt_path()` (writer) vs the grading loop in
`main()` (reader).

The writer picks the **lowest** unused index:

```python
n = 1
while os.path.lexists(os.path.join(outdir, "%s.rerun-%d.out" % (name, n))):
    n += 1
return os.path.join(outdir, "%s.rerun-%d.out" % (name, n))
```

The reader keeps the **last** match in an ascending scan, i.e. the **highest**
index present:

```python
for cand in [n + ".out"] + ["%s.rerun-%d.out" % (n, i) for i in range(1, 50)]:
    p = os.path.join(a.outdir, cand)
    if os.path.lexists(p):
        found = p          # <-- no break: the LAST match wins
```

The driver's own docstring asserts the opposite:

> "A planted higher-index `<name>.rerun-9.out` no longer outranks a fresh receipt:
> the counter picks the lowest unused index atomically."

**Exploit path (verified against the committed driver, imported as a module):**

```
writer run1 -> ctlX.out
writer run2 -> ctlX.rerun-1.out        (correct: lowest unused)
GRADER reads-> ctlX.rerun-9.out         (WRONG: a planted stale file)
GRADER content: STALE-PLANTED
```

The writer and the grader disagree about which file is authoritative. Planting
`ctlX.rerun-9.out` — one file, one line — makes the summary grade stale content
while the fresh receipt sits unread beside it.

**Impact:** the summary (`C1-summary.txt`, the durable receipt of the battery)
can be made to grade a stale or planted receipt instead of the one just produced.
The plan's kill rule (d) — "the driver's summary counts a state it did not write" —
is defeated by exactly this.

**Smallest remediation:** make the reader pick the same file the writer picked.
Have `receipt_path()` return the chosen path and carry it in the receipt itself
(e.g. a `receipt=` line), or have the reader take the **first** match in ascending
order (`break` on first hit) and make the writer's index allocation agree — the
simplest consistent rule is: reader takes the first existing candidate in
ascending order, writer takes the lowest unused; a fresh run then always lands on
the file the reader picks.

## F5 — MEDIUM — the grader follows symlinks; `O_NOFOLLOW` protects only the write

**Where:** `controls-v94.py`, `write_receipt()` vs the grading loop.

`write_receipt()` is correctly hardened:

```python
fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL | getattr(os, "O_NOFOLLOW", 0), 0o644)
```

But the **grader** then opens the selected file with a plain `open()`:

```python
body = open(found, encoding="utf-8", errors="replace").read()
```

`open()` follows symlinks. `os.path.lexists` in the reader deliberately does *not*
follow them — so the reader detects the symlink and then dereferences it anyway.

**Exploit path (verified):**

```
== symlink at ctlZ.out -> external file ==
  writer chooses            : ctlZ.rerun-1.out
  grader picks              : ctlZ.out
  content graded            : EXTERNAL-PLANTED

== symlink at the highest-index candidate (ctlA.rerun-9.out) ==
  grader picks              : ctlA.rerun-9.out
  reads                    : exit=0 | C1_R94_PASS=true   (from OUTSIDE the outdir)
```

The M9 write-side hardening therefore protects the write and not the read: the
**content that decides MATCH/MISMATCH** can come from a file outside `--outdir`.

A related writer-side note: `write_receipt` with `O_EXCL` refuses to write over an
existing symlink (verified: `OSError EEXIST` on a symlinked `.out`), and the
`receipt_path` `lexists` scan skips a symlinked `.rerun-1.out` (verified: it
selects `.rerun-2.out`). Those two properties are correct.

**Smallest remediation:** open the graded receipt with
`os.open(path, os.O_RDONLY | os.O_NOFOLLOW)` and `open(..., "r")` on the resulting
fd, or refuse (raise) when `os.path.islink(found)`. Apply the same to
`conjunct-disposition-v94.py`'s `open(path, ...)` on receipts.

## F6 — MEDIUM — `make-pins94.py`: symlink-following write, and `--lane ''` resolves to the fleet root

**Where:** `.ufo/evidence/round-94/c1/make-pins94.py:74-77`.

```python
out = os.path.join(lane, PINS_PATH)
os.makedirs(os.path.dirname(out), exist_ok=True)
with open(out, "w", encoding="utf-8") as f:
    json.dump(derived, f, indent=1, sort_keys=True)
```

No `O_EXCL`, no `O_NOFOLLOW`, no atomic rename.

**Exploit path 1 — symlink followed (verified):** with
`.ufo/evidence/round-94/c1/pins.json` a symlink to a file outside the lane, the
script writes *through* it:

```
$ ln -s $S/mp-outside.txt .ufo/evidence/round-94/c1/pins.json
$ python3 -I make-pins94.py --lane $FX --rev $R
$ cat $S/mp-outside.txt
{  "fixtures": "scripts/fixtures/sources-census", "gate_com   <-- the symlink target was overwritten
```

**Exploit path 2 — the fleet incident shape (verified):** `--lane` is
`os.path.realpath(a.lane)`, and `os.path.realpath("")` is the **process CWD**,
which the host guard pins to the fleet root `/home/vgpnk/Projects/shokunin`:

```
$ cd /home/vgpnk/Projects/shokunin      # the host-guard cwd
$ python3 -c 'import os;print(os.path.realpath(""))'
/home/vgpnk/Projects/shokunin
-> write target: /home/vgpnk/Projects/shokunin/.ufo/evidence/round-94/c1/pins.json
$ git -C /home/vgpnk/Projects/shokunin rev-parse --is-inside-work-tree
true
```

Verified in a scratch fixture: `make-pins94.py --lane '' --rev "$R"` reported
`PINS_WRITTEN /fast/.../fx.empty/.ufo/evidence/round-94/c1/pins.json` — it wrote
into the CWD, not into any lane. Run from the host-guard cwd (the fleet root) the
same invocation writes `pins.json` **into the fleet root**, which is a git repo.
This is precisely the 2026-11-06 pattern ("`git -C ""` fell back to the fleet root
and committed there"), in the write path rather than the git path.

**Impact:** the pin generator can write outside the lane, and can write through a
symlink to an arbitrary path, overwriting whatever is there.

**Smallest remediation:** refuse an empty `--lane`; resolve it and assert
`git -C lane rev-parse --show-toplevel` equals it; write the pins file with
`O_CREAT|O_EXCL|O_NOFOLLOW` to a temp file in the same directory and `os.replace()`
it into place.

## F7 — MEDIUM — `--rev` is unvalidated; an empty `--rev` reads the git index

**Where:** `measure-v94.py` `main()`: `rev = a.rev`, then
`blob(repo, rev, path)` → `git cat-file blob f"{rev}:{path}"`. With `rev == ""`
the expression becomes `":<path>"`, which git resolves against the **index**
(staged content), not a commit. `controls-v94.py` has the same pattern
(`a.rev + ":" + COUNTER_PATH`).

**Exploit path (verified):** stage a note whose verdict cells are all inverted,
without committing it, and run the counter with `--rev ''`:

```
index blob: 7d2f4fdfcd28bbf4988cb6b535d5e77fb564d461
HEAD  blob: 96ac98375d451631e12a3d4bbd322817ef5b79ab
--- counter with --rev '' (index) ---
C1_SUMMARY rev= n=12 ... mismatched=7 ...
C1_R94_PASS=false
--- counter with --rev HEAD (commit) ---
C1_SUMMARY rev=HEAD n=12 ... mismatched=0 ...
C1_R94_PASS=true
```

The empty-rev run silently graded the staged (uncommitted) bytes and produced a
different verdict from the committed bytes — and the summary line prints `rev=`
(empty), so the run is not self-identifying.

**Impact:** an unvalidated `--rev` is a way to make the counter grade bytes that
were never committed, while the receipt records an empty or misleading revision.
Combined with F2 (the C2 checker also ignores `--rev` for receipts), the whole
evidence chain has an "uncommitted bytes" path.

**Smallest remediation:** reject a `--rev` that is not a full 40-hex object id
(`re.fullmatch(r"[0-9a-f]{40}", rev)`), and refuse `--rev` values that resolve to
the index. The counter already re-derives the rev into the summary line; make it
print the resolved 40-hex sha.

## F8 — LOW — instrument hygiene

1. **Name mismatch.** The plan/task name `make-pins.py`; the round-94 file is
   `make-pins94.py` (and its docstring still says "Round-93 pin generator" and
   "Usage: python3 -I make-pins.py"). The docstring is stale relative to the file
   it documents.
2. **No self-pin on the C2 checker.** `measure-v94.py` and `controls-v94.py` each
   carry a `SELF_SHA256` line and verify it on their own bytes; the C2 checker
   (rev 3) has **no** self-pin (verified: `grep -c 'SELF_SHA256 = "'` → 0). The
   C1 counter pins itself; the C2 instrument does not, even though the plan
   asserts an operative sha256 for it in prose.
3. **40 of 45 receipts carry no `counter_sha=`.** Only the D01-D05 mutant receipts
   do. The plan's own amendment list asks for exactly this field in every
   `run_ctl` receipt; it is not implemented, which is the mechanical cause of F3.

## F9 — LOW — `controls-v94.py --canary-selftest` allocates on the default `/tmp`

`canary_selftest()` calls `tempfile.mkdtemp(prefix="r94-canary-")` with **no
`dir=`**, so it lands in the platform default temp dir (`/tmp` on this host;
`TMPDIR` unset) rather than under the caller-supplied `--work`. Every other
allocation in the driver is correctly scoped (`dir=scratch`, `dir=work`). Verified:
the directory is created and removed (`shutil.rmtree` in the same function) and no
`/tmp/r94-canary-*` was left behind, so this is a containment/hygiene issue, not a
leak. Remediation: `tempfile.mkdtemp(dir=work, prefix="r94-canary-")`, or accept
`--work` as an argument to the canary mode.

## What I verified as sound (so the L1 does not re-open it)

- **Mutating git calls are toplevel-asserted.** `controls-v94.py:clone_at()` runs
  `git -C dest rev-parse --show-toplevel` and compares `realpath` against `dest`
  before any write, and every mutating call (`git add -A`, `git commit`,
  `git replace`, `git hash-object -w`) targets that clone. Verified in a fixture:
  a commit and a `git replace` inside a `--shared` clone left the **source repo's
  objects and refs unchanged** (`SOURCE OBJECTS UNCHANGED`, `SOURCE REFS
  UNCHANGED`); the clone's `refs/replace` was local to the clone.
- **`git -C ""` cannot reach the fleet root through `measure-v94.py`.** Its
  `sealed_env()` replaces the whole environment, so no ambient `GIT_DIR` reaches
  git; and `git -C ""` from the fleet root resolves to the fleet root but is
  only used for read-only `cat-file`/`archive`/`replace -l`. The fleet-incident
  write path is closed *in the counter*; it is open in the C2 checker (F1) and
  in `make-pins94.py` (F6).
- **The counter refuses setup on replace-refs.** `measure-v94.py:374-392` checks
  `git replace -l` in both the lane and the fleet and dies with
  `replace-refs-present`. Verified the C1 side is sealed; F1 is the C2 side.
- **The counter's seal works.** With `GIT_NO_REPLACE_OBJECTS=1` a planted replace
  ref is ignored (verified: `REAL-MANIFEST` vs `FORGED-MANIFEST`).
- **The counter's gate-identity anchor works.** `GATE_COMMIT`/`GATE_SHA256` are
  constants in the self-pinned bytes and the counter dies with
  `gate-identity-mismatch` before executing a foreign gate (QUALITY 163).
- **The counter's tar extraction is hardened.** `t.extractall(dest, filter="data")`
  is the correct Python-3.12+ filter and rejects absolute/traversing member paths.
- **`git archive` rejects a traversing pathspec.** `git archive HEAD ../..` →
  `fatal: '../..' is outside repository`; `git cat-file blob HEAD:a/../../b` →
  `fatal: path ... does not exist`. So a hostile `fixtures` slug in the spec
  cannot make the counter read outside the fleet repo.
- **The counter pins the gate bytes, not a path.** `GATE_SHA256` is compared
  against the blob read from the pinned fleet commit, so the executed gate is
  byte-verified regardless of path.
- **The driver cleans its own scratch.** Every `run_ctl` clone lives under a
  `tempfile.mkdtemp(dir=scratch)` and is removed in a `finally`
  (`shutil.rmtree(d, ignore_errors=True)`). The `--work` and `--outdir` trees are
  the caller's to clean. `--work` is asserted empty
  (`work-not-empty` → `SystemExit`), so a stale tree cannot be silently reused.
- **The disposition `--selftest` uses a `TemporaryDirectory` as a context
  manager** in both places (`with tempfile.TemporaryDirectory() as d:`), so it is
  removed on exit and on exception. Verified by AST-level count: 2 context-managed
  sites, 0 bare `TemporaryDirectory()`.
- **The `--canary-selftest` leaves nothing behind** (verified: no
  `/tmp/r94-canary-*` delta), and its canary HEAD is unchanged across the run.
- **The receipts reproduce.** Re-running the committed driver against the frozen
  rev with `--only pos-real` and `--only pos-honest-a13` produced `MATCH exit=0`
  for both, with `CONTROL_INSTRUMENT sha256=a22563b0…` matching the pinned
  counter. The receipts are genuine instrument output.
- **The counter passes at both the frozen rev and HEAD** (verified in scratch
  clones at `7084358c…` and `HEAD`): `C1_R94_PASS=true`, `mismatched=0`,
  `badrows=0`, `verdict_tables=1`, exit 0.
- **The C2 checker passes honestly on the current lane** at both `HEAD` and the
  frozen rev: `DISPOSITION rows=19 falsifiable=17 unfalsifiable=2 findings=0`,
  and `--selftest` reports 9/9. The findings above are about *how that verdict can
  be reached*, not about the verdict being wrong today.
