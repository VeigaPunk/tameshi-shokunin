## 2. Quote table — located in the tag-stripped text

Three strip models are reported, because the lane's own artifacts use different
ones and the line numbers depend on the choice:

* **Model A** — per-line tag strip (tags removed, no space), every original
  source line kept: GFM 14 001 lines, CommonMark 13 335 lines.
* **Model B** — the reader's own `norm_text`
  (`.ufo/evidence/round-94/c1/measure-v94.py:330`) applied per line:
  `<script|style>` blocks → space, tags → space, entities unescaped,
  `’‘“”` → `'`/`"`, `—–` → `-`, NBSP → space: GFM 13 890 lines,
  CommonMark 13 221 lines.
* **Model C** — `<script|style>` removed (content included), tags removed
  without a space, all lines kept: same line counts as B.

**The reader's actual comparison is line-insensitive.** `norm_text` ends with
`re.sub(r"\s+", " ", s).strip()` over the whole document, so it returns a
**single line** (0 newlines, 165 548 chars for S321; 158 365 for S322). The
`source` conjunct therefore matches a quote against one collapsed line and can
never be defeated or satisfied by a line-number shift. The line numbers below are
reported for human traceability of the *anchor*, not because the instrument uses them.

## 3. The GFM spec's own width rule (the reader's width rule, QUALITY 165)

The reader enforces a delimiter-vs-header cell-count rule and a remainder-row
policy. Both are grounded in the page itself — verified verbatim in
`.ufo/evidence/round-94/sources/s321.html` (and in the committed `.txt`):

| GFM sentence (verbatim) | model A lines | model B lines | model C lines | in round-94 `s321.txt` |
|---|---|---|---|---|
| "The header row must match the delimiter row in the number of cells.  If not, a table will not be recognized:" | 4674–4677 | 4563–4566 | 4565–4568 | **yes** |
| "The remainder of the table’s rows may vary in the number of cells.  If there are a number of cells fewer than the number of cells in the header row, empty cells are inserted.  If there are greater, the excess is ignored:" | 4693–4696 | (not found — the curly `’` in "table’s") | 4584–4587 | **yes** (curly apostrophe) |

Consequences for the reader's stated rules:

* The **width rule** the reader implements ("a delimiter whose width differs from
  the header adds a `delim:` finding") is grounded in GFM's own sentence: the
  header row must match the delimiter row in the number of cells, or the table is
  not a table at all. The reader's refusal of `sharp-delim-5-4` is therefore
  *stricter-but-grounded* — GFM says such a table "will not be recognized", and
  the reader refuses to key it. Consistent.
* The **remainder-row policy** ("missing cells are empty, excess ignored") is
  verbatim GFM: "empty cells are inserted" and "the excess is ignored". The
  reader's pad/truncate of a GFM-legal remainder row, and its refusal only when
  the verdict-bearing cells are ambiguous, is the GFM rule plus a disambiguation
  guard. Grounded.
* The GFM remainder sentence uses a **curly apostrophe** ("table’s"). The
  round-94 lesson quotes it with a **straight** apostrophe
  ("The remainder of the table's rows may vary…"). Under the reader's `norm_text`
  (which folds `’` → `'`) both sides fold identically, so the match holds —
  verified: the reader's own `norm_text` finds that sentence exactly once in the
  snapshot, and the lesson's straight-apostrophe form folds onto it. Not a
  defect in the instrument; a note for any future source-sentence check written
  against this page that does *not* fold.

The round-94 lesson's S321 row quotes **three** GFM sentences, and the reader
finds all three as candidate quotes on that line and all three HIT the snapshot:
the 15-word quote, the 13-word quote, and the 13-word width rule
"The header row must match the delimiter row in the number of cells." (verbatim
at model B line 4566 / raw HTML line 4677).

## 5. Findings and discrepancies

**F1 — the two rounds' committed `.txt` snapshots use different line models
(observation, not a defect).** `round-93/sources/s321.txt` is 173 412 B / 13 890
lines; `round-94/sources/s321.txt` is 166 143 B / **0 newlines** (a single
collapsed line). Same for `s322.txt` (165 371 B / 13 221 lines vs 158 954 B /
0 newlines). They are not byte-identical: collapsed, they differ at the
whitespace level (model C removes tags without inserting a space, so the round-93
text reads `1Introduction` where the round-94 text reads `1 Introduction`;
collapsed lengths 164 881 vs 165 548 for s321). Both are valid whitespace-collapsed
views of the same HTML, and **both contain every quote verbatim** (verified
per-file). The practical consequence is only that the **round-94** lesson rows
carry **no** `s321.txt:NNNN` / `s322.txt:NNNN` line anchor while the **round-93**
lesson rows do — consistent with the round-94 `.txt` being single-line and a
line anchor being meaningless there. The round-94 lesson anchors itself by quote
text instead, which is what the reader's `source` conjunct checks. Verified: with
the round-94 lesson the reader finds **3** candidate S321 quotes and **1** S322
quote, and every one HITs the snapshot; with the round-93 lesson, **2** and **1**,
all HITs. `source` is not a tautology on either lesson.

**F2 — the reader's source check is line-insensitive, so the line-model
difference above cannot move the `source` conjunct.** `norm_text` collapses the
whole snapshot to one line before the substring test. This closes the one path
by which F1 could have mattered, and it means the round-93 lesson's line anchors
are documentation, not instrument input.

**F3 — no claim in my scope is falsified.** Every observable the plan freezes
about these sources holds: the snapshots are byte-identical to a live re-fetch;
the three quotes occur verbatim, exactly once each, with the recorded word
counts; the S321/S322 registry rows are 11-column rows with `status=mined` and a
`used-by` naming `corpus/lessons/round-93.md`; and the GFM page states, in its
own words, both the header/delimiter cell-count rule and the remainder-row
policy that the reader's QUALITY 165 rules implement.
