## 2. Class A — static provenance audit of a control/recorder call site

**Nearest: kotodama `tools/harness/receipt_guard_adoption.py`.** It is a static AST census over
filed runners: "every in-place write whose target statically resolves to that runner's own
receipt" (`:12-13`), "whether such a call dominates the receipt write in the same statement
block" (`:19-20`), an adoption class `guarded-refresh / unguarded-in-place /
guard-referenced-only / no-receipt-write / could-not-evaluate` (`:22-23`), and "Unknowns are
`could-not-evaluate` rows with a named reason — the tool has no green path for a mechanism it
cannot resolve" (`:28-29`). It returns node kinds `"literal"`, `"fstring"`, `"concat"`,
`"join"`, `"os.path.join"` for the write-target path expression (`:180,195,202,206,247`) —
literal-ness of a *path*, not of a recorded code.

Tameshi (`tools/control-assertion-audit.py`): `RUNNERS = {"run", "sh", "git", "subprocess.run"}`
(`:42`); `classify` returns `"measured", "returncode-of-runner"` only when the value is a
`returncode` of a runner call or a name bound to one (`:121-138`), `"literal", "constant"` for a
constant (`:123`), and prints `CONTROL_ASSERT sites=%d measured=%d literal=%d unmeasured=%d`
(`:186`). It reads the driver "as a blob at --rev through `git cat-file`, never from the
worktree" (`:25-26`), implemented at `:263`.

**Verdict: diverges.** Mechanism converges (AST walk over recorder/call sites, class per site,
`could-not-evaluate`-style honesty). Rule diverges: kotodama measures whether a *guard call
dominates a receipt write*; tameshi measures whether the *recorded code expression derives from
a runner call*. Neither subsumes the other; no duplication.

Secondary surfaces checked, all diverging:

  clause" (`:4`), an AST enumerator of recorder append sites (`ast.parse` `:135`, `ast.walk`
  `:137-145`), but the rule is clause → decision-table row → selftest case and a deletion-kill of

## 4. Class C — registry cell-mutability checker

**Nearest: mori `tools/mori-sources-appendonly.py` — the same rule.** "Only the columns
`status`, `recheck` and `used-by` may change in place; every other column is immutable" (`:9-10`),
immutable keys compared by header name in canonical order (`:37-38`), rows keyed by id (`:37-38`), and
`MUTABLE = ("status", "recheck", "used-by")` (`:65`). Beyond the endpoint it measures
`round_changed` — "ids whose immutable cells changed, or which were deleted, in any commit of
REV..<rev> that touches the path. An id edited and then edited back inside the range is listed
too: the change is a fact of the round even when the endpoint matches" (`:23-26`), implemented at
`:403-419`, printed at `:441-446`.

Tameshi (`tools/registry-cell-immutability.py`): same rule (`:5-6`), same 11 columns and
`IMMUTABLE` map excluding status/recheck/used-by (`:34-35`), `compare(old, new)` per id, findings
`REGISTRY_CELL <id>:<column> changed` / `REGISTRY_ROW removed <id>` (`:64-79`). Main reads exactly
two blobs, `--from` and `--to` (`:151-181`), and prints
`REGISTRY_IMMUTABLE from=.. to=.. shared=.. changed=.. removed=.. added=..` (`:183`).

**Verdict: duplicates the cell rule; diverges on range.** The mutable set, row identity (id),
header-name comparison and allowed-cell list are the same rule as mori's; the new tool is a
fourth implementation, not a new rule. Its scope is narrower: endpoint pair only.

## 6. Connector move (one bounded proposal)

**Move.** In the round-98 record, make the D-1 closure's registry statement match what its
instrument measures: (i) declare in the closure and in `tools/registry-cell-immutability.py`'s
declared limits that it compares **two blobs only** (`shared/changed/removed/added` at
`--from`/`--to`) and cannot see an immutable-cell edit that is reverted inside the range;
(ii) cite `mori-sources-appendonly.py` `round_changed` (`:23-26,403-419`),
`kama append-only-audit.py` `permitted` (`:9-14`) and `kaidoku registry-immutable.sh` (`:2-5`)
as the existing implementations of the same rule; (iii) route a history sweep
(`round_changed`-style) to a later round rather than widening this round's closure. No claim
wording changes; the two registry controls (`registry-red-r96-r97` on `0b19af5f..29734beb`,
`registry-green-r97-instr` on `29734beb..d32043ec`) stay exactly as frozen.

**Why non-obvious.** The new tool is presented as closing a class the census did not catch (D-1),
but the same rule already exists three times in the fleet, and two of those are history-wide
where tameshi's is endpoint-only. The round's own mined mistake is an in-place cell edit; an
edit-then-revert would be invisible to the new tool and would leave the closure's sentence
("the new registry audit measures the class") true only for edits that survive to the endpoint.

**Axes affected.** Calibration improves: the closure's assertion becomes a function of the
measured scope instead of a wider phrase. Adjacency improves: the first named sibling convergence
is recorded (mori/kama/kaidoku), so the capability is not re-declared as novel. Operability is
untouched; no manufacturer/runtime surface is invoked.

**Risks.** (a) It can read as reopening D-1; the mitigation is to keep both registry controls
byte-frozen and state that the residual is prospective — the actual control ranges contain no
reverted edit (red range has two SOURCES commits, green range zero; receipt §instrument identity,
`git log --numstat`). (b) It invites scope creep into a new instrument; the mitigation is "route,
do not build": the next round either adopts mori's `round_changed` semantics or keeps the
endpoint tool with its narrowed limit.
