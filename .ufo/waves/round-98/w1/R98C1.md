### 2.2 Attack A — **kill rule (a) is reachable** (hard; frozen text does not exclude it)

`collect_assigns` keys assignments by bare name (`out.setdefault(tgt.id, …)`, audit
L81) and `resolve` takes the last assignment by source line across the whole module
(`cand = …; max(cand, key=lambda r: r[0])`, L105–L108). It tracks neither scope nor
reachability. Two drivers in scratch:

**Literal kill (a) hit — the recorded code is a `Name` bound to the constant 0:**

```python
def main():
    rc = 0                              # the site's own binding: a constant
    def helper():                       # a different scope, never called
        p = subprocess.run(["/usr/bin/true"])
        rc = p.returncode
        return rc
    add("name-bound-constant", rc, "body", 1)
```

```
CONTROL_ASSERT_SITE line=14 name=name-bound-constant measured=yes class=measured detail=returncode-of-runner-name
CONTROL_ASSERT sites=1 measured=1 literal=0 unmeasured=0
rc=0
$ python3 driver.py  →  RECORD name-bound-constant code=0 want=1
```

**Dead-store variant — every executed assignment is the constant:**

```python
    rc = 0
    if False:                                     # dead store
        rc = subprocess.run(["/usr/bin/true"]).returncode
    add("dead-store-constant", rc, "body", 1)
```
→ `measured=yes class=measured detail=returncode-of-runner`, rc 0; the driver records
`code=0`. A third variant (`p = Result(0)` in the site scope, a nested scope assigning
`p = subprocess.run(…)`) reproduces it with an attribute, not a name.

Kill rule (a) as frozen: *"a constant, or a name bound to a constant, is reported
`measured`"*. Both drivers report a name bound to a constant as measured. None of the
five declared limits (including the pre-wave A1/A2 additions: worktree path, runner
matched by call name) mentions scope or reachability, so **the frozen text does not
exclude this**. The claim's predicate on `controls98` is unaffected (that driver has no
shadowing and no dead store), so what falls is the classifier sentence and kill (a), not
the `sites=15` line.

Smallest safe correction — a wording narrowing in claims.json/plan C1 plus a declared
limit row (the audit itself is frozen and sha-pinned; changing it invalidates the 12
pre-freeze controls):

> limit: "name resolution is by source line across the module, not by scope or
> reachability: a same-named assignment in a nested function, or an assignment in a
> branch that never executes, is chosen over the site's own binding, so a name bound to
> a constant can report measured (`R98C1-c1-kill-a-shadow.txt`). The classifier's
> 'constant bound through a name' clause holds only for the site's own scope and for
> reachable assignments. A scope-aware resolver is a routed defect."

and in the wording clause: *"…is unmeasured (same-scope, reachable assignments only)"*.

not apply. Smallest correction: add the declared limit (exact sentence in §5).

Ranked by what the canonical judge would have to reject.

### 6.1 C1 — kill rule (a) is reachable; a name bound to a constant reports `measured`

- **Counterexample:** `c1-shadow3` (a `rc = 0` in the site's scope, a nested scope
  assigning `rc = p.returncode`) and `c1-dead` (`if False: rc = subprocess.run(…).returncode`).

  `code=0`; the resolver is scope-blind and reachability-blind (audit L81, L105–L108);
  no declared limit covers it. Receipt `R98C1-c1-kill-a-shadow.txt`.
- **Impacted axis:** calibration (C1). The `sites=15` predicate is unaffected; the
  classifier sentence and kill (a) are.
- **Smallest safe correction:** narrow the clause to same-scope, reachable name chains
  and add the limit sentence (§2.2); route a scope-aware resolver to round 99. Do not
  edit the sha-pinned audit at R.

### 6.2 C2 — the After clause promises a transcript the instrument does not emit

- **Counterexample:** the battery's own output at the freeze rev: one line
  (`GUARD_REFUSALS classes=6 refused=6 wrong=0 positive=ok`), no per-class line; the
  committed receipt is identical; `observations` is collected and never printed; on the
  red arm the substituted class is `continue`d, not graded.
- **Evidence:** my re-run at `764aca97` (rc 0; red rc 1), the print-site list, the
  committed receipts. Receipt `R98C1-c2-transcript.txt`.
- **Impacted axis:** operability (C2) — the capability is real (6/6 refusals, each on a
  distinct branch), the *observability* sentence is not.
- **Smallest safe correction:** either add one `GUARD_REFUSALS_RUN <class> rc ok` line
  (receipt then shows the six runs) or amend the After sentence to: "the summary line at
  R, exit 0, with no `GUARD_REFUSALS_MISS` line; the red line and exit 1; the six runs are
  asserted by the counters, not itemised".

### 6.3 C2 — "every declared guard refusal class" is 6 of the tool's 13

- **Counterexample:** the frozen tool emits 13 `GUARD_SETUP` tokens; the battery's
  `CLASSES` names 6; the seven argument/manifest pre-checks have no fixture, no receipt

  round-97 already declared), i.e. receipts for D-6, not a new declaration.
- **Evidence:** token census and branch map, `R98C1-c2-classes.txt`.
- **Impacted axis:** operability (framing only; no claim counter is wrong).
