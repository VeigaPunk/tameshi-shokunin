## Findings

**F1 (material, falsifies the classifier sentence / kill rule b).** The audit reports `measured` for
a site whose value is a constant bound in the site's own scope when a nested function defined
*earlier* in the file binds the same name from a runner call (case k1). This is exactly kill rule
b ("a `returncode` attribute on a value not assigned from a runner call is reported `measured`"),
and, for the runnable fixture, kill rule a as well (the site records the constant `0`). Mechanism:
`collect_assigns` records assignments from every AST scope, and `resolve()` picks the last
same-named assignment with a smaller line number — no scope tracking; case k2 (nested def after the
call) flips the result to `unresolved`, so the outcome depends on definition order alone.
Two readings are possible and the L1/critic must pick one:
- *site-scope reading* (the value the site actually records): the classifier contradicts the frozen
  sentence → kill rule b is met;
- *file-global name-chain reading*: the classification is what the tool declares, but then the
  declared limits must add that the "name chain" silently crosses scopes, because the current
  limit text only says provenance ≠ command identity.
The two pinned drivers are unaffected: neither has this shape at any of its 15 sites, and steps 1–2
still print the exact predicate. R98C1's independent receipt (`.ufo/waves/round-98/w1/R98C1-c1-kill-a-shadow.txt`)
reaches the same boundary with a different fixture; k1/k2 additionally isolate the line-order mechanism.

**F2 (limit gap, not a kill rule as written).** A driver can define `add` twice, the second
definition shadowing the first and ignoring `code`; the audit sees only the call expressions and
passes (`measured`, exit 0, case f) while the live recorder never receives the grade. The declared
limits name a *differently named* recorder as the zero-site/vacuous hole, not a shadowed same-name
`add`. Notably, this is **not** what the assigned fixture wording asks for in substance: the call's
recorded expression does derive from a runner call, so the static sentence holds.

**F3 (limit gap).** A recorder invoked as `r.add(...)` is not an `ast.Name` call, so it produces
`sites=0` and exit 0 (case l). Literal reading of the frozen wording ("static `add(...)` call
sites") excludes attribute calls, and the declared zero-site limit covers the same vacuity by
analogy; kill rule d ("a call site is skipped") could be read to cover it. No fixed driver uses
this form.

**F4 (conservative, per the letter).** An attribute written from a runner after construction
(`p = P(); p.returncode = subprocess.run(...).returncode`) is reported `unresolved` (case j). The
letter of the wording ("a `returncode` attribute on a value not assigned from a runner call") agrees,
but a legitimate driver that stores the rc in an attribute rather than rebinding the name would be
marked unmeasured.
