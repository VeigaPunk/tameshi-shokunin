The `could-not-evaluate` token inside the selftest row is exactly such a near-miss, and I judged it not to be a map because it is scoped to the TMPDIR fallback.

I verified BASE contains no `.ufo/evidence/round-57/` at all, so there was no round-57 surface to have closed the item. My verdict is about BASE, so it stands either way — but a repair wave will need new round-57 instruments, not edits to round-56's.
3. **R56.7's target wording is partly in the fleet root.** The lane's lesson is lane-owned and lane-fixable; the fleet-root report at `7438ee1` is an immutable past commit. If the repair scope is taken to be "correct the report", the operator owns that half. I did not rule R56.7 declined, because the same false claim stands in the lane's own lesson at `corpus/lessons/round-56.md:319`, which the lane can correct append-only — and the closure routed it as a lane item ("self-defects ride this queue"). If the L1 reads the item as fleet-only, R56.7 should move from open to split-open/operator, and that is a scope reading, not a factual dispute about the bytes.
4. **Panel-vs-ledger disagreement budget.** The C1 counter compares the panel arm against each row's `status_at_base` with a ≤5-disagreement tolerance. My three verdicts are all "open". If the ledger records R56.6 or R56.7 as closed at base, those are disagreements to be explained by the ledger's side, not by mine — and the explanation would have to name a commit after the spot-check file was added, which for R56.5/6/7 means after `5e35699` itself.
5. **No runtime was executed.** These are byte-and-history verdicts; no gate, counter or test was run. Nothing here claims a measured pass.
