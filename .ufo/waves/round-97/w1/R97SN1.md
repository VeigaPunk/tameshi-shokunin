## Findings

### F-HIGH-1 — the digest pins are optional: omitting `--driver-sha` / `--checker-sha` / `--manifest-sha` still prints the frozen predicate line

**Attack.** Run the counter with the pin flag left out entirely.

```
$ python3 -I battery-bind.py --lane <clone> --rev <newrev>              # no --driver-sha
BATTERY states=50 matched=50 mismatched=0 missing=0            exit 0
$ python3 -I guard-inertia.py --lane <clone> --rev <newrev>              # no --checker-sha, no --manifest-sha
GUARD_INERTIA rows=10 killed=8 limits=2 survived=0 unmet=0      exit 0
```

**Exploit path.** At a revision where the attacker controls the lane content, the *unpinned* reader is
trivially forged:

* substitute the driver blob `.ufo/evidence/round-96/c1/controls-v96.py` with a module whose
  `grade(name, code, out, want)` returns `True` unconditionally and whose `states()` returns the 50 state
  names;
* rewrite all 50 receipts under `.ufo/evidence/round-96/pre-freeze/controls/` as
  `counter_sha=<counter digest>\nexit=0\nC1_R96_PASS=true\n`.

```
$ python3 -I battery-bind.py --lane <clone> --rev <forged-rev>            # --driver-sha OMITTED
BATTERY states=50 matched=50 mismatched=0 missing=0            exit 0
$ python3 -I battery-bind.py --lane <clone> --rev <forged-rev> --driver-sha 88bcca86…
BATTERY_SETUP driver-sha-mismatch                              exit 2
```

The reader *executes* the driver blob it reads at `--rev` (`load_driver()` writes the blob to a scratch file
and `exec_module`s it — `battery-bind.py:95-102`). With the pin present the forgery is refused; with the pin
absent the same tree yields the frozen predicate verbatim.

**Evidence.** `R97SN1-attacks.txt` rows F4, F5, F6, F9, F10. Reproducer:
`R97SN1-receipts/attack5.py` (F1/F1b) and `R97SN1-receipts/attack2.py` (P4/P7/P8).

**Impact.** The predicate line `BATTERY states=50 matched=50 mismatched=0 missing=0` is not, by itself,
evidence that the committed driver was the oracle. A verifier who runs the counter from the plan's
`RECORDS_REV` but drops the pin gets a green line on forged content. The same asymmetry exists for C2: with
`--manifest-sha` omitted, a tampered manifest at a new rev is *not* refused at setup — the tool runs it and
reports `unmet=1`/exit 1 only because the row's `expect` flipped (row F12); a coherent substitute manifest
(rows merely reordered) with the pin omitted still prints the exact frozen summary (row F13).

**Relation to the frozen wording.** The claims file states the *counter* with the pins present
(`--driver-sha 88bcca86…`, `--checker-sha 02a5482a…`, `--manifest-sha 9de0b7e9…`), so the counter as
written is pinned and this is not a falsification of the frozen sentence. It **is** a gap between the
sentence and the instrument: the wording promises that "a 64-hex value unequal to the driver blob's sha256 is
refused", and it is — but nothing says the pin may be *absent*, and the instrument silently degrades to
unpinned instead of refusing. The C2 wording's `GUARD_SETUP manifest-sha-mismatch` clause likewise describes
only the unequal case, not the absent case.

**Smallest remediation.** Make the pins mandatory rather than optional: refuse `BATTERY_SETUP driver-sha-absent`
/ `GUARD_SETUP checker-sha-absent` / `GUARD_SETUP manifest-sha-absent` (exit 2) when the flag is not supplied,
so a green predicate can only be produced under a pin. This is an instrument change, so it must be landed
pre-data with a new `instrument_sha256` pin.

### F-MED-1 — C1 grades a symlink receipt's *target text* as if it were the receipt body

**Attack.** Replace a receipt with a symlink entry (mode `120000`) whose blob content is a forged receipt:

```
$ git commit-tree  (adds .ufo/…/controls/pos-real.out as 120000 with body
                     "counter_sha=<real counter digest>\nexit=0\nC1_R96_PASS=true\n")
$ python3 -I battery-bind.py --lane <clone> --rev <rev> --driver-sha 88bcca86…
BATTERY states=50 matched=50 mismatched=0 missing=0            exit 0
```

**Exploit path.** `blob_at()` reads the path with `git cat-file blob rev:path`, which for a symlink entry
returns the *link target string*, and the reader then parses that string as the receipt body
(`parse_exit`/`parse_counter_sha`/`grade`). A symlink whose target text happens to be a well-formed receipt is
therefore accepted as a passing receipt. The reader never checks the mode.

**Evidence.** `R97SN1-attacks.txt` row E3. Reproducer `R97SN1-receipts/attack3.py` (S1).
Contrast: a symlink to an unrelated path (`elsewhere/x`, row E4), a tree object (E5) and a gitlink (E6) are all
correctly reported missing — only the *content-shaped* target passes.

**Impact.** Low in practice (an attacker who can commit to the lane can also commit a forged regular file, and
the driver-shared receipt digests still bind the counter line), but it is a genuine class confusion: a receipt
that is not a file is graded as a receipt. The declared limit F1 ("a hand-written receipt carrying the right
counter_sha= and payload cannot be distinguished from a real run") arguably covers hand-*written* receipts but
does not name the mode confusion.

**Smallest remediation.** In `blob_at()`, reject a receipt path whose tree entry mode is not `100644`
(inspect the tree entry mode before `cat-file blob`), and count it `missing`.

### F-MED-2 — a hostile tree or an unusable scratch root makes both tools exit 1 with an *empty* stdout, colliding with the "mismatched" exit code

**Attack / observation.** Five distinct hostile inputs each raise an uncaught exception:

| input | tool | observed | exit |
|---|---|---|---|
| `HYAKU_SCRATCH` = a regular file | C1 | `NotADirectoryError: Not a directory: '<file>/tameshi-r97'` (traceback), stdout empty | 1 |
| `HYAKU_SCRATCH` = a regular file | C2 | same | 1 |
| `HYAKU_SCRATCH` = a read-only dir | C1 | `PermissionError: Permission denied: '<dir>/tameshi-r97'` | 1 |
| `HYAKU_SCRATCH` = a read-only dir | C2 | same | 1 |
| tree at rev contains an absolute symlink (`120000` → `/etc/passwd`) | C1 | `tarfile.AbsoluteLinkError: 'evil' is a link to an absolute path` | 1 |
| NOTE at rev replaced with `garbage` (breaks the driver's 12-row premise) | C1 | `fixture-premise-failed: pos-honest-a13 does not parse to 12 rows` | 1 |

**Exploit path.** `sealed_env()` calls `os.makedirs(tmp, exist_ok=True)` unguarded
(`battery-bind.py:53`, `guard-inertia.py:50`), and `checkout_lane_at()` pipes `git archive` into
`tarfile.extractall(dest)` with Python 3.14's default `data` filter, which rejects absolute links. Neither
site converts the exception into a setup refusal.

**Impact.** Exit 1 is the *data-failure* code: the wording assigns exit 1 to "any mismatched/missing" and
exit 2 to setup refusal. A verifier that keys on the exit code alone cannot distinguish "the hostile
environment broke the tool" from "the battery mismatched". With an empty stdout, no `BATTERY`/`GUARD_INERTIA`
line is printed either, so the usual line-presence check also fails — but the exit code is the wrong signal.
Note that the *scratch-root* variants are the seat's own environmental precondition, not an attacker action:
the wave-1 operator sets `HYAKU_SCRATCH` to a private directory and a read-only or non-directory path turns
every run into a crash.

**Evidence.** `R97SN1-attacks.txt` rows D1–D6. Reproducers `R97SN1-receipts/attack3.py` (S4a/S4b/S4c) and
`R97SN1-receipts/attack7.py` (P-c, P-d).

**Relation to the frozen wording.** Neither C1's nor C2's wording names scratch-root failure, so this is a
gap *not* covered by a frozen sentence — it is a robustness/observability defect, not a wording falsification.
(Contrast F21/F22 below, where the freeze instrument *did* crash on a hostile manifest and the current
instrument does not.)

**Smallest remediation.** Wrap `sealed_env()`'s `makedirs` and `checkout_lane_at()`'s extraction in
`try/except` and return `BATTERY_SETUP scratch-unusable` / `GUARD_SETUP scratch-unusable` (exit 2); convert
`SystemExit` from the driver's premise assertion into the same setup-refusal channel.

### F-LOW-1 — a malformed or deleted `counter_sha=` line is counted `missing`, not `mismatched`

**Attack.** Two edits of the `counter_sha=` line on `pos-real.out` (no `mutant=D<nn>` line on that receipt):

```
value replaced by 64 zeros  ->  BATTERY_ROW pos-real:MISMATCH(counter-sha)   mismatched=1 missing=0   exit 1   [correct]
value replaced by 'nothex'  ->  BATTERY_ROW pos-real:MISSING(no-counter-sha)  mismatched=0 missing=1   exit 1
line deleted                ->  BATTERY_ROW pos-real:MISSING(no-counter-sha)  mismatched=0 missing=1   exit 1
```

**Exploit path.** `parse_counter_sha()` returns the raw value; the reader then requires
`SHA_RE.fullmatch(got_sha)`. A value that is not 64 hex fails the *shape* test before the digest comparison,
so the receipt is classed `missing` instead of `mismatched`.

**Impact.** Low. The verdict is still nonzero and the exit code is still 1, so no forged verdict is produced.
The divergence is only in *which counter* is non-zero.

**Relation to the frozen wording.** The C1 wording (as amended at A3/A5) says: "a `counter_sha=` edit on a
receipt that does not carry a `mutant=D<nn>` line, an `exit=` edit, and a `C1_R96_PASS=true` payload edit on a
`__pass` receipt each print a nonzero **`mismatched`** count and exit 1". A malformed or deleted
`counter_sha=` line prints a nonzero **`missing`** count and `mismatched=0`. This is a **falsifies-wording
candidate** — the same shape as the already-recorded A1 (which moved the de-index case from `mismatched` to
`missing`). It is a wording-narrowing candidate (add "a malformed or absent `counter_sha=` line is counted
`missing`"), not an instrument defect: the instrument's behaviour is self-consistent and fail-closed.

**Evidence.** `R97SN1-attacks.txt` rows E7, E8, E9. Reproducer `R97SN1-receipts/final.py` (V1, V2, V3).

**Smallest remediation.** Amend the C1 wording pre-data to name the field per edit, as A1 already did for the
de-index case: "a `counter_sha=` edit that keeps the value 64 hex prints a nonzero `mismatched` count; a
malformed or absent `counter_sha=` line prints a nonzero `missing` count".

### F-LOW-2 — the counter blob at `--rev` is read as the oracle's `counter_sha=` reference but the *declared* `counter_sha256` pin is never enforced

**Attack.** Substitute the counter `.ufo/evidence/round-96/c1/measure-v96.py` at a new rev (keeping
`parse_note` intact) and rewrite every receipt's `counter_sha=` line to the forged counter's digest. The
driver pin stays valid.

```
$ python3 -I battery-bind.py --lane <clone> --rev <forged-rev> --driver-sha 88bcca86…
BATTERY states=50 matched=50 mismatched=0 missing=0            exit 0
```

**Exploit path.** `bind()` computes `counter_sha = sha256(counter_blob)` from the blob at `--rev` and
compares it to each receipt's `counter_sha=` line — a self-consistent pair always matches. The claims file
names `counter_sha256 = 69ee68b6…`, but the tool never compares against that pinned value: it accepts any
counter whose digest the receipts agree with. (The forged counter without `parse_note` is refused at setup —
row E13 — so the exploit needs a counter that still parses the note.)

**Impact.** Low-to-medium, and mostly *already declared*: C1's limit #2 says "a hand-written receipt carrying
the right `counter_sha=` and payload cannot be distinguished from a real run without re-executing the state
(round-96 F1, unchanged)". Substituting the counter as well as the receipts is the same limit, one level up.
It is listed here because the *declared* `counter_sha256` pin gives a false impression that the counter blob
is anchored, when in fact the counter is anchored only by the receipts it authenticates.

**Relation to the frozen wording.** Covered by a declared limit (F1). Not a falsification.

**Smallest remediation.** Either add a `--counter-sha` pin (mirroring `--driver-sha`) and refuse
`BATTERY_SETUP counter-sha-mismatch`, or amend the claims file to drop the unenforced `counter_sha256` field
so it stops reading as a pin.

### F-LOW-3 — C2's matrix reads the manifest at `--rev` but the *manifest digest* only guards the file, not the row semantics

**Attack.** A coherent substitute manifest — the same ten rows, merely reordered — committed at a new rev,
with `--manifest-sha` set to *its own* digest:

```
$ python3 -I guard-inertia.py --lane <clone> --rev <rev> --checker-sha 02a5482a… --manifest-sha <substitute digest>
GUARD_INERTIA rows=10 killed=8 limits=2 survived=0 unmet=0      exit 0
```

A tampered manifest (one row's `expect` flipped) at the same rev is refused at setup
(`GUARD_SETUP manifest-sha-mismatch`, exit 2) when the *original* digest is pinned — that path is correct.

**Impact.** The manifest's *choice of rows* is not bound by any digest; the digest only fixes which file is
read. A substitute manifest with different rows can yield the identical summary line.

**Relation to the frozen wording.** This is a **declared limit** (C2 limit #3, added at A12–A14):
"the manifest's choice of rows is a human declaration; the tool measures the declared edits and the
`--manifest-sha` pin fixes which rows are measured, not whether each edit is a guard (R97C1 §2: a coherent
substitute manifest yields the same line when its digest is passed)". Correctly declared; listed so the record
is complete.

**Evidence.** `R97SN1-attacks.txt` rows F11, F12, F13.

## Attacks that were correctly refused (highlights)

Every refusal below was measured with the exact command and output in `R97SN1-attacks.txt`.

* **Lane resolution** (A1–A10). `--lane ''` → usage, exit 64. `--lane .` outside a repo, `--lane <non-repo>`,
  `--lane <a different repo>`, `--lane /` → `rev-unresolvable`, exit 2. `--lane <lane>/.ufo` (a repo whose
  *toplevel differs*) → C1 refuses with `BATTERY_SETUP driver-unusable` (the archived tree is the `.ufo`
  subtree, so the driver's NOTE is absent), exit 2; C2 resolves the same objects and prints the correct
  predicate. `--lane <lane>/.git` → correct predicate.
* **Rev resolution** (B1–B10). `master`, `''`, `HEAD` and an abbreviated sha → `rev-not-a-commit-id`, exit 2;
  a dead 40-hex → `rev-unresolvable`, exit 2. Identical for both tools.
* **Hostile `git` shim earlier in `PATH`** (C1, C2). The shim was never invoked: both tools call
  `GIT = "/usr/bin/git"` by absolute path and re-pin `PATH` to `/usr/local/bin:/usr/bin:/bin` in
  `sealed_env()`. Predicate unchanged.
* **Exported `GIT_DIR` / `GIT_WORK_TREE` / `GIT_OBJECT_DIRECTORY`** (C1, C2). `sealed_env()` returns a
  fresh dict rather than mutating `os.environ`, so the inherited values never reach the child `git`. Predicate
  unchanged.
* **`refs/replace` present in the lane clone** (C1, C2). With a real replace ref mapping the driver blob to a
  forged one, the pinned run still reports the correct verdict (`GIT_NO_REPLACE_OBJECTS=1` in `sealed_env()`),
  and the unpinned run does not pick up the replacement either. C2's own manifest row `replace-refs` measures
  the same property from the checker side.
* **Inherited `TMPDIR=/tmp`, CWD outside the lane, and the documented counter form `--lane .` from the lane
  root** (C10, C11, C8, C9). All produce the correct predicate; `sealed_env()` re-pins `TMPDIR` and `HOME`
  under the scratch root.
* **Receipt objects** (E1, E2, E4, E5, E6). 49 receipts → `missing=1`, exit 1. 51 receipts (an extra
  `.out` naming no state) → the correct predicate (the state count comes from the driver's `states()` +
  `EXPECT_EXTRA`, not from a directory listing). A receipt as a tree object, a gitlink, or a symlink to an
  unrelated path is `missing`.
* **Path traversal through `--receipts`** (E14–E16). `../../../etc`, `/etc`, and a `..`-laden relative path
  all resolve to `missing=50`; the reader never escapes the tree.
* **Pin validation** (F1–F3, F6–F8, F11, F14–F20). Empty / non-hex / wrong-64-hex pins are refused with
  `driver-sha-invalid`, `driver-sha-mismatch`, `manifest-sha-invalid`, `manifest-sha-mismatch`,
  `checker-sha-mismatch` (exit 2). The manifest refusal set is complete at HEAD: `edit-no-op`,
  `edit-ambiguous:<row>:<count>`, `state-unbuildable:<row>:…`, `limit-mechanism-missing:<row>`, `manifest-empty`.
* **Hostile tree content** (D7). A `.gitattributes` with `export-ignore` on the NOTE makes the driver's import
  fail → `BATTERY_SETUP driver-unusable`, exit 2.
* **Base-rev clauses** (G1–G3). `git grep -c 'GUARD_INERTIA'` at `07e50d6d` → rc 1, no output;
  `git grep -c 'BATTERY states='` → rc 1, no output; `git cat-file -e 8ed9c526:…/C1-summary.txt` → rc 128
  (the wording already says 128 after A6).

## Instrumentation note — the freeze instrument crashed on two hostile manifests; HEAD does not

At the freeze commit the C2 instrument had no `state-unbuildable` and no `limit-mechanism-missing` guard, so two
hostile manifests crashed it or passed silently:

| hostile manifest | freeze instrument `[FRZ]` | HEAD instrument `[HEAD]` |
|---|---|---|
| row `state: "no-such-state"` | `RuntimeError: unknown state: no-such-state` traceback, stdout empty, **exit 1** | `GUARD_SETUP state-unbuildable:rev-hex:unknown state: no-such-state`, **exit 2** |
| `limit` row with `limit_mechanism` removed | **exit 0**, prints `GUARD_INERTIA rows=10 killed=8 limits=2 survived=0 unmet=0` — the missing mechanism is silently accepted | `GUARD_SETUP limit-mechanism-missing:verify-quiet`, **exit 2** |

Both were repaired pre-data by A11 (`6f080522`) and the instrument digests re-pinned. Against the *current*
frozen wording (HEAD claims.json) the current instrument is correct: both refusals fire with exit 2
(rows F15, F16). This is recorded so the wave's re-grade knows the freeze-era instrument and the current one
differ; **neither** of these is an open finding against the current wording.

## What I did not get to

I did **not** run the C1/C2 `--selftest` batteries, and I did **not** attempt the remaining exotic object
classes my spec listed but that I ran out of time to instrument: a FIFO or device node as a receipt (git
cannot store either — only `100644`, `100755`, `120000`, `160000` and `040000` are representable, and I
covered `120000`, `160000` and `040000`), a `--receipts` directory that is a symlink *at* the rev (the
receipts path is always read through `rev:<path>`, so a symlinked directory at that path is a blob read, not
a filesystem read), and a symlinked `--outdir`/`--work` (neither tool has an `--outdir`/`--work` flag; C1
writes only under `$HYAKU_SCRATCH/tameshi-r97/battery-bind-*` and C2 under
`$HYAKU_SCRATCH/tameshi-r97/guard-inertia-*`, both created by `mkdtemp` inside a `mkdtemp`-created root, so
no attacker-chosen path is followed — this I established by reading the code, not by running it).

I also did not exhaustively re-run the C1/C2 `--selftest` at HEAD, and did not measure the C2 fixture store's
behaviour when `HYAKU_SCRATCH` is unset (the shared `/fast/scratch/hyaku/tameshi-r96` path is used by the
round-96 checker inside C2's subprocess; C2 passes its own `sealed_env()` to the checker, which does **not**
include `HYAKU_SCRATCH`, so the checker falls back to the shared default — I verified the run still passes
with a private `HYAKU_SCRATCH` set, row P-e, but did not test with the shared directory absent or read-only).
