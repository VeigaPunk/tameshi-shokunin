## Checked negative — is the `git-absolute` `limit` an artifact of the harness?
Hypothesis: `run_checker` launches both runs with `env = sealed_env(); env.update(...)`
(guard-inertia.py:179-183), so the bare `git` would resolve the same binary no matter what
the checker's own pin does.
Refuted by the code:
- guard-inertia.py:167-175 `hostile-path` returns
  `{"PATH": shim + ":/usr/local/bin:/usr/bin:/bin"}` as the env override, i.e. the checker
  process DOES see the exit-99 shim first.
- conjunct-disposition-v96.py:66-79 defines its own `sealed_env()` (PATH pinned to
  /usr/local/bin:/usr/bin:/bin) and every audit-path git call passes that env
  (:84-86 wrapper; :144, :157, :396, :407). The checker therefore discards the harness's
  hostile PATH for its own git calls.
- The checker's own selftest has the arm "hostile-path-cheat" (:350-367) asserting identical
  output under a hostile PATH — the guard the row edits.
So the `limit` is caused by the checker's guard, and removing the pin too (the two-edit
combination the plan excludes) would kill it. No finding. The manifest's `limit_mechanism`
sentence is accurate.
