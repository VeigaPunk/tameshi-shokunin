## 4. The `limit` class

Both limit rows are honest measured outcomes; neither is an escape hatch
(`07`).

- **verify-quiet.** At the git level the forms differ — `git rev-parse
  --verify --quiet --end-of-options deadbeef…^{commit}` → rc 1, empty;
  without the two tokens → rc 128, `fatal: ambiguous argument` on stderr and
  the argument on stdout. The checker tests only `returncode != 0` and prints
  its own `rev-unresolvable`, so both checker runs are exit 2 with the token:
  identical verdict. The declared mechanism names exactly that collapse; its
  parenthetical "(rc 128)" describes the mutant form, while the pristine form
  is rc 1 — an imprecision, not a misclassification.
- **git-absolute.** One edit (`GIT = "git"`) is identical (both exit 0)
  because `sealed_env()` pins PATH; the two-edit combination (`GIT = "git"` +
  moving the sealed PATH under the shim) makes the mutant exit 2
  (`DISPOSITION_SETUP rev-unresolvable`) against the pristine 0. The guard is
  observable only with the combination — precisely the declared one-edit limit.

The tool never reads `limit_mechanism` (only the prose docstring mentions it),
so kill rule d is a manifest-content rule, not a tool check. Both frozen rows
name a mechanism, so the rule holds on the committed bytes; a future
mechanism-less limit row would print `limit` unnoticed.

## 5. The oracle trust

C1 verifies receipts against the committed driver, and the driver is the
producer's own oracle: the receipts were produced by running it. A hand-written
`pos-real` body with the right `counter_sha` and `PASS=true` is counted

therefore the re-derivability of the *summary* from committed bytes (D-a), not
receipt provenance: the reader proves "the 50 receipts satisfy the driver",
not "the battery ran". The strongest counter-argument — same producer, same
oracle, so a tautology — is the declared limit and does not defeat the
predicate; the mutant-receipt carve-out is an additional, undeclared hole in
the same family.
