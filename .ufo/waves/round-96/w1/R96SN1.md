# R96SN1 — security attack on the round-96 frozen instruments

Seat: `R96SN1` (sentinel). Wave w1, round 96.
Freeze under attack: `be6c22b6d8a94f07eee6b0fa79edab7df228c0b0` (instruments),
instrument rev `10d8fa5d52c0674038beb2eb2328e42162bb4b56`, base `c8de77f3de0fd4bf619ebe78fa0b28adaf320d3e`.

**Method.** Read-only against the lane. Every fixture is a scratch clone under
`/fast/scratch/hyaku/tameshi-r96/R96SN1/`. Hostile `PATH` attacks were run inside
`bwrap --ro-bind / / --bind <fakebin> /usr/local/bin` so that `/usr/local/bin/git`
is shadowed without touching the real `/usr/local/bin` (the checker's absolute
`GIT=/usr/bin/git` never consults `PATH`, so the shadow only proves the point for
the instruments that resolve `git` **by name**).

Every finding below was reproduced; the reproduction command and the observed
output are inline, and the raw receipts are in `R96SN1-runs/`.

## 1. Findings

### F1 — HIGH — counter-sha binding: the entire 17-receipt set can be hand-written (round-95 F9, still live)

**Class:** counter-sha binding.

**What the plan declares.** C1 kill rule (e): "a receipt that exists only in the
working tree, **or carries a wrong `counter_sha=`**, is accepted" is a kill. The
checker therefore binds each receipt to the counter blob by sha256.

**Reproduction** (`R96SN1-runs/F1-forged-receipts.txt`). Clone the lane at the
freeze, hand-write one receipt per manifest state row, copying the honest
counter blob's sha256 (which is public — it is the sha256 of a committed blob)
and forging the `C1_CONJUNCTS` body. Commit them. Run the checker. **No clone,
no counter invocation, no counter bytes anywhere:**

```
$ python3 -I R96SN1-runs/f9_forge.py
honest counter blob sha256 = e0da99351018793767c9b5035f8668b3feb6cbb0eba796ca59a71a5ed86113a1
wrote 16 forged receipts
forged rev = b4e24f2c5e83dfaad186870006c633ba518205d5
=== checker output ===
DISPOSITION_INSTRUMENT sha256=e0da99351018793767c9b5035f8668b3feb6cbb0eba796ca59a71a5ed86113a1 conjuncts=19
DISPOSITION_ROW canary unfalsifiable
...
DISPOSITION rows=19 falsifiable=17 unfalsifiable=2 findings=0
CHECKER EXIT = 0
```

**Observed.** `findings=0`, exit 0, `falsifiable=17` — the frozen positive
predicate — from a receipt set that was typed by hand. The `counter_sha=` line
proves only *which counter version the receipt claims to describe*; it does not
prove the counter ran. The honest sha256 is derivable from the committed blob by
anyone, so it carries no secret.

**Expected.** Either (a) the plan should say plainly that the C1 predicate
certifies *a committed text file asserts the conjunct is false*, not *a counter
run moved it*; or (b) the receipt must carry provenance a forger cannot invent —
e.g. the driver's own digest plus the parent revision and the stdout hash of the
run that produced it, and the checker must recompute the expected
`counter_sha=` from the **mutant** counter blob each state actually ran (the
D01–D05 receipts already carry the mutant's digest; the `run_ctl` receipts carry
the frozen counter's digest, which is the same public value for all 17 rows).

**Smallest fix.** Beyond the declared limit: require each receipt to carry
`driver_sha256=` (the sha256 of the `controls-v96.py` blob at `--rev`) and
`run_sha256=` (the sha256 of the counter blob that the state actually executed —
the mutant digest for D01–D05, the frozen digest otherwise), and have the checker
compare `run_sha256=` against the **state's own expected counter blob** rather
than against one global counter. The D01–D05 receipts already record the mutant
digest at `R96SN1-runs/F5-d01-d05-regression.txt`; the `run_ctl` receipts do not
record which counter was run at all.

**Note.** Round-95's sentinel already filed this as F9 and the round-95 plan
declared it a limit. Round 96 changed the counter's *path* (F8 below) and the
driver's *read side* (F4 below) but left the binding itself unchanged, so F9
survives into v96 unchanged.

### F2 — HIGH — git seal: alternates are not scrubbed, so a lane with zero commits of its own grades green

**Class:** git seal / identity.

**What the plan declares.** C1 kill rule (g): "a hostile `git` earlier in `PATH`
changes the verdict from findings to green" is a kill; C1 *Declared limits*: "the
seal covers the inherited environment and the PATH directory, not the kernel."
The sealed env scrubs `GIT_NO_REPLACE_OBJECTS=1`, `GIT_CONFIG_NOSYSTEM=1`,
`GIT_CONFIG_GLOBAL=/dev/null` and no inherited `GIT_*`.

**Reproduction** (`R96SN1-runs/F2-alternates.txt`). Build an *empty* git repo —
**no commits at all** — and point its object store at an attacker-controlled
store via `.git/objects/info/alternates`. Commit the forged receipts in the
attacker store. Run the checker against the empty lane:

```
$ git init -q $S/alt/lane
$ echo "$S/alt/attacker/.git/objects" > $S/alt/lane/.git/objects/info/alternates
$ git -C $S/alt/lane log --oneline
fatal: your current branch 'main' does not have any commits yet
$ python3 -I .ufo/evidence/round-96/conjunct-disposition-v96.py \
      --lane $S/alt/lane --rev 573fbe2ab05565a02c69814d73dda4c06f3cfcc8 \
      --min-falsifiable 17 --counter .ufo/evidence/round-96/c1/measure-v96.py
DISPOSITION_ROW witnessed state=witness-same mode=conjunct-false
DISPOSITION rows=19 falsifiable=17 unfalsifiable=2 findings=0
EXIT=0
```

**Observed.** `findings=0`, exit 0, from a lane whose own history is empty. The
object store the checker reads is not the lane's; it is whatever
`objects/info/alternates` points at. `GIT_NO_REPLACE_OBJECTS=1` and
`GIT_CONFIG_*` are irrelevant to alternates. Note also
`GIT_ALTERNATE_OBJECT_DIRECTORIES=""` does **not** disable an
`objects/info/alternates` file (measured: `git cat-file -t` on the alternates
object still returns `commit` with the variable set to the empty string), so the
env-var route cannot close it either.

**Expected.** A verdict of "the lane at revision R contains receipts proving X"
must be about *the lane's own objects*. The sealed env should neutralize
alternates for every git call, and the checker should verify the audited lane
has the audited revision as **its own** object — not merely as an object
reachable through an alternate.

**This is not a contrived artefact.** The round's own driver creates alternates
routinely: `clone_at()` uses `git clone -q --shared`, and every fixture clone
it makes carries `.git/objects/info/alternates` pointing back at the lane's
object store (measured: `find $S/drv5/work -name alternates -path "*/objects/info/*"`
returns one per fixture clone, each containing the lane's `.git/objects` path).
So an `objects/info/alternates` file in a repo under audit is a *normal* state
in this ecosystem — a checker that treats "the objects I read are the lane's
own" as an invariant has to check it explicitly, because its own tooling
creates the very file that would break it.

**Smallest fix.** In `sealed_env()` (all four instruments), set
`GIT_ALTERNATE_OBJECT_DIRECTORIES` to a directory that cannot contain objects
**and** have the checker refuse if `<lane>/.git/objects/info/alternates` exists
or is non-empty (or, more robustly, resolve every object through
`git -C <lane> cat-file` with the alternate store explicitly excluded and the
lane's own object directory asserted to contain the audited revision).

### F3 — HIGH — `make-pins96.py` resolves `git` by name: a hostile `/usr/local/bin/git` forges `pins.json`

**Class:** pin/identity / git seal.

**What the plan declares.** C2 wording: "`make-pins96.py --lane <lane> --rev
<40-hex>` writes `PINS_WRITTEN …`, exit 0, and the written bytes equal the five
derived values at that revision". C1's seal uses an absolute
`GIT = "/usr/bin/git"`.

**Reproduction** (`R96SN1-runs/F3-hostile-git-pins.txt`). Shadow
`/usr/local/bin/git` inside `bwrap` with a shim that answers `cat-file blob`
from forged bytes:

```sh
#!/bin/sh
case "$3" in
  *census-mutants.json) printf '{"gate":{"repo":"…","commit":"f47ad6ba…","path":"scripts/sources-census.sh","sha256":"FORGED…","fixtures":"…"}}'; exit 0;;
  *sources-census.sh)  echo "FORGED-GATE-BYTES"; exit 0;;
esac
exec /usr/bin/git "$@"
```

```
$ bwrap --ro-bind / / --bind $S/hostile/usr-local-bin /usr/local/bin … \
    python3 -I .ufo/evidence/round-96/c1/make-pins96.py --lane $S/lane --rev be6c22b6…
PINS_WRITTEN /…/lane/.ufo/evidence/round-96/c1/pins.json
PINS_DERIVED … gate_sha256=95a586dd33686a8c7d29e770e588f484450b8d673d95eed9d33ae20a2e8ffa66 …
WRITE_EXIT=0
--- pins.json content after hostile write ---
{
 "fixtures": "scripts/fixtures/sources-census",
 "gate_commit": "f47ad6ba8d306f8125597401cb2ce45c1297a593",
 "gate_path": "scripts/sources-census.sh",
 "gate_sha256": "95a586dd33686a8c7d29e770e588f484450b8d673d95eed9d33ae20a2e8ffa66",
 "spec_sha256": "9dcd46606b6f6088655bfa02291364237c5672acdaee948bdcec5261afc831b6"
}
```

**Observed.** `PINS_WRITTEN`, exit 0, and the file on disk carries the **forged**
`gate_sha256` / `spec_sha256`. The `--check` path likewise reported
`PINS_CHECK DRIFT spec_sha256,gate_sha256` from forged bytes. The four
instruments resolve `git` in three different ways:

| instrument | how `git` is resolved | hostile `/usr/local/bin/git` reached? |
|---|---|---|
| `conjunct-disposition-v96.py` | absolute `GIT = "/usr/bin/git"` | **no** — held (see §2) |
| `make-pins96.py` | `subprocess.run(["git", …])`, `PATH=/usr/local/bin:/usr/bin:/bin` | **yes** |
| `controls-v96.py` | `sh("git", …)` → same sealed PATH | **yes** |
| `measure-v96.py` | `subprocess.run(["git", …])`, same sealed PATH | **yes** |

`/usr/local/bin` is **first** in the sealed PATH, so a hostile shim there wins
over the real `/usr/bin/git`. The C1 checker is the only instrument that names
the binary absolutely.

**Expected.** The seal should be uniform: if `GIT=/usr/bin/git` is the intended
binary, every instrument must name it absolutely, and the PATH entry order must
not offer a writable shadow that precedes it.

**Precondition (stated plainly).** On this host `/usr/local/bin`, `/usr/bin`
and `/bin` are all `root:root` and not writable by an unprivileged user
(measured: `drwxr-xr-x root:root /usr/local/bin`). So the realistic attacker
for this vector is a **root-level foothold or a hostile package install**
that drops a `git` into `/usr/local/bin` — which is exactly what
`/usr/local/bin` exists for, and exactly where a `pip install`/`npm install`
`-g` of a wrapper-named package would land. That is a weaker precondition than
round-95's F1 (which only needed a writable PATH directory), but the
*inconsistency* is the defect: three of four instruments trust `PATH` order
while the fourth does not, so the round's own "sealed environment" claim is
true for the checker and false for the rest of the suite.

**The driver is exposed too.** The same shim driving `controls-v96.py`
intercepted **6 of the driver's own git calls** — `cat-file`, `clone`,
`rev-parse --show-toplevel`, `checkout --detach`, `add -A`, and the fixture
`commit`. The run then failed with `error: pathspec 'D05' did not match any
file(s) known to git` — i.e. the driver's git surface is fully
attacker-controlled; this shim *broke* it, a forging shim would *forge* the
whole battery.

**Smallest fix.** Give all four instruments one shared helper that always
invokes `/usr/bin/git` by absolute path (the checker already does) and drop
`/usr/local/bin` from the sealed PATH, or place it *after* `/usr/bin`.

### F4 — HIGH — the driver's "lowest index wins" fix is defeated by planting index 0

**Class:** driver read-side (the F3 fix of round 95).

**What the plan declares.** C2 wording: "the driver grades the lowest-index
receipt (`<name>.out` wins over any planted `<name>.rerun-9.out`)".

**Reproduction** (`R96SN1-runs/F4-planted-index0.txt`). Plant `<name>.out`
**before** the driver runs, then run the driver on that state:

```
$ printf 'control=D01\ncounter_sha=deadbeef\nexit=0\nC1_CONJUNCTS valid0=false trivial0=false\nC1_R96_PASS=true\n' > $S/drv/out/D01.out
$ python3 -I .ufo/evidence/round-96/c1/controls-v96.py --lane $S/lane --rev be6c22b6… \
      --base c8de77f3… --work $S/drv/work --outdir $S/drv/out --only D01
CONTROL_INSTRUMENT sha256=e0da99351018793767c9b5035f8668b3feb6cbb0eba796ca59a71a5ed86113a1
D01 MATCH exit=0
C1_CONTROLS states=1 matched=1 mismatches=0 missing=0
$ ls -l $S/drv/out/
-rw-r--r-- 1 vgpnk vgpnk  98 D01.out            <-- PLANTED, graded
-rw-r--r-- 1 vgpnk vgpnk 163 D01.rerun-1.out    <-- the driver's OWN receipt, ignored
$ cat $S/drv/out/D01.rerun-1.out
mutant=D01 state=renamed-result
counter_sha=5519931c963c330b03ff6f30112267a5784678bff15fffdd0ab28663a48c9e6b
exit=2
C1_SETUP rev-not-a-commit-id
```

**Observed.** The driver wrote its genuine receipt to `D01.rerun-1.out` — which
records `exit=2`, a **mismatch** — while the grader read the **planted**
`D01.out`, which records `exit=0` and `C1_R96_PASS=true`, and reported
`D01 MATCH`. The grader's rule "lowest index wins" is applied *before* any
content validation, so index 0 is the best place to plant.

The planted body also carries a bogus `counter_sha=deadbeef`, and the driver
**never validates `counter_sha=` on the receipts it grades** — `grade()`
(line 422) inspects only the exit code, the `C1_R96_PASS=true` /
`C1_SETUP <token>` markers, and the `C1_CONJUNCTS` values. The driver *writes*
`counter_sha=` into every receipt but never *checks* it on the read side.

Note the round-95 F3 was "the driver grades the **highest** `.rerun-N.out`"; the
v96 fix inverted the order to "lowest". The inversion is correct in the
pre-registered case (a planted `.rerun-9.out` next to a fresh `.out`) but it
still grades **whatever is at the lowest index**, including a file the driver
did not write and did not verify.

**Expected.** The grader must grade **the receipt the driver itself wrote in this
run**, not "the lowest-index file that happens to be present". The driver's write
path already knows which path it used (`receipt_path` returns it); that path
should be recorded and graded.

**Smallest fix.** Have `write_receipt` return the path it wrote and keep a
`{name: path}` map in the driver; grade exactly that path (and treat "the driver
wrote no receipt for this state" as MISSING). This also subsumes F9 below: with
an explicit path there is no name-index search to confuse.

### F5 — HIGH — the v96 driver passes `--rev HEAD` to a v96 counter that rejects it: 6 of 50 states can never match

**Class:** operability (C2 battery).

**What the plan declares.** C2 predicate: "driver `C1_CONTROLS states=50
matched=50 mismatches=0 missing=0`". The plan's §Implications: "the F3/F4 fix is
read-side only. The state set is unchanged (50)".

**Reproduction** (`R96SN1-runs/F5-d01-d05-regression.txt`,
`R96SN1-runs/F5-full-battery-50-states.txt`). The **full** 50-state battery on
an honest run:

```
$ python3 -I .ufo/evidence/round-96/c1/controls-v96.py --lane $S/lane --rev be6c22b6… \
      --base c8de77f3… --work <fresh> --outdir <fresh> --jobs 6
CONTROL_INSTRUMENT sha256=e0da99351018793767c9b5035f8668b3feb6cbb0eba796ca59a71a5ed86113a1
D01 MISMATCH exit=2
D02 MISMATCH exit=2
D03 MISMATCH exit=2
D04 MISMATCH exit=2
D05 MISMATCH exit=2
coverage-absent MATCH exit=1
… 43 further states all MATCH …
replace-honest MISMATCH exit=2
…
C1_CONTROLS states=50 matched=44 mismatches=6 missing=0 [D01,D02,D03,D04,D05,replace-honest]
EXIT=1
```

The six failing receipts all carry the wrong token:

```
[D01.out]              exit=2  C1_SETUP rev-not-a-commit-id  C1_R96_PASS=false
[D05.out]              exit=2  C1_SETUP rev-not-a-commit-id  C1_R96_PASS=false
[replace-honest.out]   exit=2  C1_SETUP rev-not-a-commit-id  C1_R96_PASS=false
```

The isolated six-state run gives the same result
(`states=6 matched=0 mismatches=6`).

**Observed.** All six mismatch. Root cause: round-96's counter added a 40-hex
rev guard at `measure-v96.py:418` (`if not re.fullmatch(r"[0-9a-f]{40}", rev):
die("rev-not-a-commit-id")`), but the round-96 **driver** still invokes the
counter with a symbolic rev in two places:

* `controls-v96.py:576` — `--rev "HEAD"` for the `replace-honest` state;
* `controls-v96.py:608` — `--rev "HEAD"` for every D01–D05 mutant.

The counter now dies `C1_SETUP rev-not-a-commit-id` (exit 2) before it ever
inspects the replace refs or the mutant's rule removal, so the receipts cannot
carry `C1_SETUP replace-refs-present` (what `EXPECT_EXTRA` demands for
`replace-honest`) nor `C1_R96_PASS=true` (what it demands for D01–D05). Every
one of the six receipts records the wrong token:

```
$ grep -h "C1_SETUP" $S/drv5/out/D01.out $S/drv5/out/D05.out $S/drv5/out/replace-honest.out
C1_SETUP rev-not-a-commit-id
C1_SETUP rev-not-a-commit-id
C1_SETUP rev-not-a-commit-id
```

**This is a clean v96 regression, not a pre-existing defect.** The two drivers
are byte-identical on this point —

```
$ grep -n '"--rev", "HEAD"' .ufo/evidence/round-95/c1/controls-v95.py
568:  … "--rev", "HEAD",      # replace-honest
600:  … "--rev", "HEAD",      # D01–D05
$ grep -n '"--rev", "HEAD"' .ufo/evidence/round-96/c1/controls-v96.py
576:  … "--rev", "HEAD",      # replace-honest
608:  … "--rev", "HEAD",      # D01–D05
```

— while the **counter** changed: round-95's `measure-v95.py` has **no** rev
guard at all (`measure-v95.py:417` is just `rev = a.rev`, then straight to the
work-dir check), whereas round-96's `measure-v96.py:417-425` resolves the rev
and requires 40 hex. Round-95's committed receipts confirm the states used to
work: `round-95/pre-freeze/controls/D01.out` records `exit=0` with
`C1_R95_PASS=true`.

So the C1 rev guard (which correctly kills round-95's F2/F7) **broke the C2
battery**: the frozen C2 predicate `states=50 matched=50 mismatches=0 missing=0`
is **unreachable on an honest v96 driver run** — the very predicate the round's
claims.json names.

**Expected.** Either the driver resolves the symbolic rev to a 40-hex id before
invoking the counter (it already has `crev` available for `run_ctl`), or the
counter accepts a symbolic rev and resolves it itself.

**Smallest fix.** In `controls-v96.py`, replace both `--rev "HEAD"` with the
already-resolved 40-hex commit id (`crev` / `git -C <clone> rev-parse HEAD`),
matching what `run_ctl` does at line 389. That single change restores D01–D05
and `replace-honest` and re-enables the 50/50 predicate.

### F6 — MEDIUM — `DISPOSITION_SETUP rev-unresolvable` is dead code

**Class:** rev identity.

**What the plan declares.** C1 wording: "the checker refuses with exit 2 and
`DISPOSITION_SETUP rev-not-a-commit-id` when `--rev` is not a 40-hex object id
and with `DISPOSITION_SETUP rev-unresolvable` when the id does not resolve".

**Reproduction** (`R96SN1-runs/F6-rev-unresolvable.txt`):

```
$ git rev-parse deadbeefdeadbeefdeadbeefdeadbeefdeadbeef   # in a real repo
deadbeefdeadbeefdeadbeefdeadbeefdeadbeef
rc=0
$ git rev-parse --verify deadbeefdeadbeefdeadbeefdeadbeefdeadbeef
deadbeefdeadbeefdeadbeefdeadbeefdeadbeef
rc=0
$ git cat-file -t deadbeefdeadbeefdeadbeefdeadbeefdeadbeef
fatal: git cat-file: could not get object info
rc=128
```

```
$ python3 -I .ufo/evidence/round-96/conjunct-disposition-v96.py --lane $S/lane \
      --rev deadbeefdeadbeefdeadbeefdeadbeefdeadbeef --min-falsifiable 17 …
DISPOSITION_SETUP counter-absent-at-rev
EXIT=2
```

**Observed.** `git rev-parse` **echoes back** a 40-hex string it cannot resolve
and exits 0 — even with `--verify` (git 2.56.0). The checker's guard

```python
_res = git(a.lane, ["rev-parse", a.rev], sealed_env())
if _res.returncode != 0:
    sys.exit(die("rev-unresolvable"))
```

therefore never fires; `_res.stdout` is the input hex, the second
`re.fullmatch(r"[0-9a-f]{40}", a.rev)` passes, and the run continues to
`counter-absent-at-rev`. The same pattern is in the counter at
`measure-v96.py:420` and in `make-pins96.py` (which has no resolve check at
all). **The token `DISPOSITION_SETUP rev-unresolvable` is never printed by any
code path.**

**Expected.** The plan's C1 wording promises a token the instrument cannot
emit. Either the wording is amended, or the guard is made to work.

**Smallest fix.** Resolve with `git -C <lane> rev-parse --verify --quiet <rev>`
and treat a non-zero exit or a non-40-hex stdout as `rev-unresolvable`; or
verify with `git -C <lane> cat-file -e <rev>^{commit}` first. The `--verify`
alone is not sufficient on git 2.56 (measured above) — the object must be
checked with `cat-file -e`.

### F7 — MEDIUM — the resolved revision is never printed, so a green verdict cannot be attributed to a revision

**Class:** rev identity.

**What the plan declares.** C1 wording: "it prints the resolved id in the
`DISPOSITION_INSTRUMENT` line".

**Reproduction** (`R96SN1-runs/F7-no-rev-printed.txt`):

### F10 — MEDIUM — the manifest blob is not pinned to `claims.json`'s `manifest_sha256`

**Class:** manifest trust / identity.

**What the plan declares.** C1 kill rule (d): "the checker or manifest blob at

with `manifest sha256 now = 84894f439cfc5f3342b531706f40ec9c8b92931e1fffa3c6366b4d9c3c6906a4`
against `claims.json manifest_sha256 = 31e4667b…`. The checker neither refuses
nor reports the mismatch; the verdict is indistinguishable from an honest one.

*Coarser form* — rewriting every row to `unfalsifiable` needs no receipts at
all and is caught only by the `--min-falsifiable` guard, which the checker
defaults to **0** (`ap.add_argument("--min-falsifiable", type=int, default=0)`):


**Observed.** The instrument never checks the manifest's identity. Kill rule (d)

instrument itself does not perform — and, as the sharp form shows, a
*partial* remap that keeps `falsifiable=17` sails through the claim's own
command with a manifest that is provably not the frozen one.

**Expected.** The manifest is the *specification* the checker grades against;

**Smallest fix.** Add `--manifest-sha256` (defaulting to the frozen value) and
compare `hashlib.sha256(manifest_blob).hexdigest()` against it, refusing with
`DISPOSITION_SETUP manifest-sha-mismatch`. The same treatment already applies to
the counter via the receipts' `counter_sha=` line, so the manifest is the odd
one out.

### 2.14 A counter whose `SELF_SHA256` was recomputed for a malicious edit → **accepted by design; say so**

**Class:** pin/identity. This is the seat spec's explicit question.

```
$ python3 - <<'PY'   # edit measure-v96.py's die() to print C1_R96_PASS=true, then recompute SELF_SHA256
norm = PIN.sub(b"", b2); h = hashlib.sha256(norm).hexdigest()
b2 = PIN.sub(('SELF_SHA256 = "%s"\n' % h).encode(), b2, count=1)
PY
$ python3 -I .ufo/evidence/round-96/c1/measure-v96.py --conjuncts
C1_CONJUNCT_KEYS selfpin pins spec pin green canary valid0 trivial0 inconclusive0 unstable0 note verdict_tables ids mismatched0 figure witnessed source coverage n_min
C1_R96_PASS=keys-only
EXIT=0
```

**Accepted.** The self-pin is a **self-referential** digest: it certifies that
the file's bytes match the digest *the file itself carries*, so whoever edits
the counter can re-derive the digest. This is round-95's F10 and it is
**accepted by design** — the plan's C1 *Declared limits* and the manifest's
`"unfalsifiable"` rows say the self-pin "certifies one and only one pin line",
not that it certifies provenance. It is **not** fixed in v96.

**Why it does not by itself produce a green C1 verdict (measured).** The
checker's own binding is the receipt's `counter_sha=` line, and the counter blob
is read **from the object store at `--rev`** — so a malicious counter committed
at a *new* revision changes the expected `counter_sha`, and the receipts must
carry the *malicious* counter's digest. Measured end to end:

```
$ python3 -I …/conjunct-disposition-v96.py --lane . --rev a7dd1558… --counter .ufo/evidence/round-96/c1/measure-v96.py
DISPOSITION rows=19 falsifiable=17 unfalsifiable=2 findings=0
EXIT=0
```

So a malicious counter **plus** matching forged receipts does produce green —
but that is F1 (the receipts are the forgeable half), not a break of the
self-pin. The self-pin is what stops an *honest-but-modified* counter from
silently changing behaviour; it is not, and cannot be, an authenticity
mechanism.
