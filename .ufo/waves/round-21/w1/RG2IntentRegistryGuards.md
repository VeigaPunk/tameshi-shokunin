## 1. Strictly positive finite timeout

**Intent / invariant.** `timeout_s` is a configuration bound, not just a value passed to `Popen.communicate`. At the frozen base, `registry_errors` rejects bools/non-numbers and requires `math.isfinite(ts) and 0 < ts <= MAX_TIMEOUT_S` (`tools/registry-check.py:238-255`). Invalid registry input is a could-not-evaluate result; it must be rejected before launching a row. The upper bound was added because a finite timeout at or above 2,147,484 seconds overflows `communicate()`'s C timeout conversion; round 18 chose one day as an ample cap. The strict lower bound preserves the positive-timeout contract: zero is invalid, not an immediate execution timeout.

R17-TIMEOUT was broader than this boundary: round-17's spotcheck disclosed both NaN/Infinity parsing and `setsid` escape as tool-operability debts, expressly “not proofs of baseline-row regression” (`corpus/lessons/round-17-verifier-spotcheck.md:440-443`). The earlier R17 numeric finding measured Python JSON accepting NaN/+Infinity (and `1e400` becoming infinity), which passed the old `ts <= 0` check and caused uncaught `ValueError`/`OverflowError` during `communicate`; the checker exited 1 and a sleeping row child remained (`.ufo/waves/round-18/w1/S09NonFiniteSweep.md:31-63`). Round-18's C2 P09 discriminator checks NaN and Infinity and requires exit 2, the row name and `timeout_s` in the diagnostic, and no traceback (`.ufo/evidence/round-18/defect-probes.py:566-603`). That P09 probe does **not** cover zero.

Timeout enforcement is a separate R17-TIMEOUT leg, not a substitute for the numeric validation guard. The old group kill could be escaped with `setsid`/`setpgid`; an escaped process retaining a pipe could make the post-timeout `communicate()` unbounded (`.ufo/waves/round-18/w1/S10TimeoutEscapeSweep.md:7-20`). C2 P10 uses a one-second row timeout and tests setsid and setpgid escapes, requiring an observed row timeout and no surviving marked process (`defect-probes.py:662-787`). The wave-1 repair instead uses a subreaper, process-identity/ancestry checks and pidfds, and bounds pipe draining (`tools/registry-check.py:503-524, 648-725`). These defects and tests explain the R17 timeout history, but they do not demonstrate the strict zero boundary.

**Evidence and divergence.** The round-18 wave-2 timeout-cap change is `9ee1c80`; its diff adds `MAX_TIMEOUT_S = 86400`, the finite positive upper-bound validation, and too-large/huge-float cases (`git show` evidence below). The exact frozen C1 mutant R02 changes only `0 < ts` to `0 <= ts` (`.ufo/evidence/round-21/c1-mutants.json:91-95`). Its ancestor M02, “accept-zero-timeout-boundary,” survived: mutated owning selftest exit 0, `SELFTEST: PASS (46 cases)` (`.ufo/waves/round-18/w2/MutateRegistryCheck18.md:64-78`). The report notes the 46-case fixture set covered NaN, infinities, overflow, bool, and large values but not zero; its expected detector was absent (`MutateRegistryCheck18.md:263-264`). Current source likewise has those cases, including `timeout-too-large` and `timeout-float-huge`, but no zero case (`tools/registry-check.py:1500-1525`).

**Faithful kill.** Keep the single `> 0` → `>= 0` mutation. Add a named zero-boundary selftest discriminator that supplies a registry row with `timeout_s: 0` and requires the checker to return could-not-evaluate (exit 2) with that row and `timeout_s`/positive-timeout validation identified, before row execution. Use a launch-observation side-effect canary as additional evidence that validation happened before execution. The pristine selftest must exit 0; the mutant selftest must exit nonzero *because this named case observes the accepted-zero behavior*, not because another timeout case failed. Testing only NaN/Infinity (P09) or another finite upper-bound value does not kill R02.

## 2. `baseline_children` exclusion

**Intent / invariant.** Before starting each row, `_direct_child_identities()` snapshots the checker's existing direct children as `(pid, starttime)` pairs (`tools/registry-check.py:456-465`; called before `Popen` at `:672-684`). When an ancestry walk reaches a process whose parent is the checker, `_row_identity_is_owned()` accepts it only if that identity is *not* in the snapshot (`:468-489`). A newly orphaned row descendant adopted by the subreaper can therefore be owned; a checker child that predated this row, and descendants whose ancestry leads through it, remain outside this row's cleanup scope. The invariant is to signal/reap only this row's process tree, never an unrelated pre-existing checker child/tree.

The wave-1 history introduced this snapshot with the explicit comment “Snapshot pre-existing children so cleanup never claims another row,” along with the ancestry-based descendant walk (`58e5d53` diff). Mutant M05 removes the membership exclusion and returns `True` for any child of the checker. It survived the 46-case selftest, exit 0 (`.ufo/waves/round-18/w2/MutateRegistryCheck18.md:116-130`). The round-18 survivor analysis says there was no named unrelated/pre-existing-child case and routes a fixture containing a pre-existing direct child and descendant, identified in `baseline_children`, that must remain unowned/alive while a new row is cleaned (`:265`). The frozen C1 R05 repeats exactly this mutation (`.ufo/evidence/round-21/c1-mutants.json:98-102`).

**Faithful kill.** In an isolated selftest fixture, start an unrelated checker child (and a child of that process) *before* the row begins, record their PID/start-time identities, then start a row with a newly created child that cleanup is expected to terminate. Exercise actual row cleanup, not just a text/source assertion. Require the unrelated baseline identities and their subtree to remain alive and unsignalled/unreaped while the row-owned child is terminated/reaped; then explicitly clean up the fixture's unrelated processes. The pristine selftest must pass, and the M05 mutant must fail a named preservation case because it claims/signals/reaps a baseline identity. Merely showing that a row child is killed, or testing a checker with no pre-existing child, cannot establish this exclusion.

## 3. Post-`pidfd_open` `in_row_scope()` recheck

**Intent / invariant.** `_signal_process_identity()` first verifies that `/proc` still reports the expected start time and that `in_row_scope()` is true. It then opens a pidfd, re-reads the process stat, and repeats both checks before `pidfd_send_signal()` (`tools/registry-check.py:503-524`). The pidfd anchors the signal to a process identity rather than a bare PID; the second ownership check makes sure that identity is still within this row's ancestry scope after the open/revalidation window. A valid start time alone is insufficient: a process can cease to be owned by the row while still having the same PID/start-time pair. This is a race-window guard, not a claim that ancestry cannot change after the second check.

The wave-1 landing diff added the before/after `in_row_scope()` checks as part of the row-owned pidfd cleanup (`58e5d53`). The existing `pidfd-revalidates-starttime` selftest only changes the fake start-time result from 1234 to 1235 and passes `lambda: True` for ownership (`tools/registry-check.py:1566-1589`). M06 demonstrates that this start-time discriminator kills removal of the post-open start-time comparison. It does not exercise the second ownership check. M07 removes only that post-open `not in_row_scope()` and survived: exit 0, `SELFTEST: PASS (46 cases)` (`MutateRegistryCheck18.md:151-167`). The report identifies the missing case as post-pidfd ownership-change rejection and specifies stable identity with ownership changing `True` to `False` (`:266`). Frozen C1 R07 removes the same second check (`c1-mutants.json:104-107`).

**Faithful kill.** Add a named deterministic unit fixture around `_signal_process_identity`: have `read_stat` return the same expected PID/start-time both before and after `pidfd_open`; mock pidfd open to return a valid fake descriptor; make `in_row_scope()` return `True` on the first call and `False` on the post-open call. Require a false return, zero `pidfd_send_signal` calls, and descriptor closure. First verify that the fixture's mutant outcome would reach the fake signal call when the second scope guard is removed; then require the pristine selftest to pass and that mutant selftest to fail on this named case. Existing stale-starttime rejection with ownership fixed `True` is not a faithful kill of R07.
