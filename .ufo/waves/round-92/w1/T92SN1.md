## Checked and clean (no finding)

- **No hardcoded `/tmp`** in either driver (`grep -n '/tmp'` → no hits). The counter sets `TMPDIR=<work>/tmp` and `HOME=<work>` for the gate subprocess (`measure-v92.py:86-91`), and the fleet gate's own `mktemp -d "${TMPDIR:-/tmp}/…"` therefore lands inside `--work`.
- **No credential or host-setting access** in either driver: no reads of `~/.ssh`, `id_rsa`, shadow, api keys, no `sysctl`/`ulimit`/`setuid`/`chown`, no writes to `/etc`. The counter's `sealed_env()` (:68-71) sets `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1`, so global/system git config cannot influence it.
- **Counter env hygiene is good**: `sealed_env()` *replaces* the environment (it is passed as `env=`), so ambient `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`/`GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` are dropped for every counter-side git call. This is exactly the property the driver lacks (F3/F5).
- **Tar extraction is hardened**: `t.extractall(dest, filter="data")` (`measure-v92.py:98`) — Python 3.14's `data` filter blocks absolute paths, `..` traversal and unsafe links.
- **The counter refuses non-empty `--work`** (`:206-207`) and refuses a non-empty `git replace -l` in the lane repo (`:209-215`).
- **`git clone --shared` does not leak writes back to the source**: `hash-object -w` and `commit` inside a `--shared` clone write to the clone's own object store; the source's loose-object count and its `replace -l` are unchanged (`src loose objects before=3 after=3`, `src replace -l: []`). This was the main worry about the driver's clone strategy and it is sound.
- **The driver asserts the clone toplevel** (`:199-201`) — the assertion is correct for the no-ambient-`GIT_DIR` case (F3 is about its *coverage*, not its logic).
- **No write of the driver or counter into the lane or fleet repo**: driver writes are confined to the scratch clone, the counter copy in `--work`, and `--outdir`; the lane and fleet repos are only ever read (`git clone`, `cat-file`, `rev-parse`) in the normal path.
- **The counter never executes a lane-supplied gate**: the gate bytes come from the fleet repo at the commit named by the spec, and the gate's own sha256 is checked (`pin`, `measure-v92.py:231`) — but see F1, the *spec* that names the commit is not enforced.

## Assessment

Both committed drivers are **read-only with respect to the lane and fleet repos on the normal path** — no `git add`/`commit`/`replace`/checkout ever targets the lane or the fleet root, every clone is asserted to be its own toplevel, no `/tmp` is hardcoded, no credentials or host settings are touched, and the `--shared` clone strategy provably does not write back to its source. The counter's own environment sealing is genuinely strong.

The residual risk is that the counter's **spec pin is advisory rather than enforcing** (F1/F2). Because the spec names both the repository and the blob that the counter subsequently `bash`-executes, a spec that fails `SPEC_SHA` still selects and runs code and still writes outside `--work`. The battery contains a `spec-mutated` control, but it perturbs only `mutants[i].new` — it never exercises `gate.repo`/`gate.path`/`witness.dirs`/`witness.files`, so the control set does not cover the consequence of an unpinned spec. The `git -C ""` fallback (F2) is the same defect the fleet already paid for once on 2026-11-06, reproduced here inside the instrument itself.

The driver's weaknesses are environmental rather than structural: it inherits the ambient git environment (F3/F5), so a mutating call can land in a repository other than the one it asserts — and the assertion it does have cannot detect that case; it also scores receipts it never wrote (F4), which is the property the plan's kill rule (d) rests on.

Neither finding falsifies the round's committed receipts: all 25 committed receipts are well-formed, the summary matches them, and the counter bytes are identical across `84904d41`…`dae295de`. These are **containment and provenance weaknesses in the instruments**, not evidence that the battery mis-scored. The smallest fixes are local: make `spec_pinned` a setup refusal, reject an empty/unvalidated repo path, give the driver one sealed environment, and derive the summary from the receipts the run actually wrote.
