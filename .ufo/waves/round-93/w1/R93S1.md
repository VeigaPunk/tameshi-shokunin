## 4. The GFM cell-count rule the reader's width rule claims

`s321` stripped lines 4566–4567 (and `s321.txt:4566`):

> The header row must match the delimiter row in the number of cells.  If not,
> a table will not be recognized:

This is the **header-vs-delimiter** rule, and it is exactly what the reader enforces at
`.ufo/evidence/round-93/c1/measure-v93.py:270-271`
(`if delim and len(delim) != len(header): bad.append("width:…")`). Verified as present
verbatim in the committed `s321.html` bytes, not only in the stripped text.

**Observation (not a kill, and not a disagreement with the claim).** Immediately after
that rule, GFM states the opposite for *data* rows (`s321` lines 4585–4587, `s321.txt:4585`):

> The remainder of the table's rows may vary in the number of cells.  If there
> are a number of cells fewer than the number of cells in the header row, empty
> cells are inserted.  If there are greater, the excess is ignored:

The reader is stricter than GFM here: `measure-v93.py:275-276` refuses any data row whose
cell count differs from the header (`bad.append("width:%d:cells=%d")`), where GFM says such
a row is a valid table with padded or ignored cells. I confirmed the behaviour by
importing the frozen counter's `parse_note` and feeding it two synthetic notes:

- row with fewer cells (`| C02 | a | b | KILLED |`, 4 cells under a 5-cell header) →
  `badrows=1, bad=['width:4:cells=4']`
- row with more cells (6 cells) → `badrows=1, bad=['width:4:cells=6']`
- row with an explicit empty cell (`| C02 | a | b | KILLED | |`) → `badrows=0`

Two readings, and I report both without adjudicating:

1. *Benign for the claims.* The committed note's verdict table is uniform 5 cells in every
   row (lines 68–81: header 5, delimiter 5, twelve data rows 5), so the strictness never
   fires on the committed note, and none of the plan's declared limits depends on it.
   The GFM quote the lesson actually cites ("The table is broken at the first empty line…")
   is the *table-bounding* rule, which the reader does implement exactly
   (`tables()` stops a table at a blank/non-pipe line and at a delimiter row mismatch).
2. *A candidate scope observation for the L1.* The reader's data-row width check is
   stricter than the cited source, and the plan's declared-limits list does not name a
   "ragged data row" class. Under QUALITY 154/156 the instrument refuses on *content*, and
   a row whose trailing cell is omitted is a presentation class a human author can produce
   in good faith. It is not in the plan's kill rule (a) list, and no control state in the
   round-93 battery exercises it (the battery's positive states all use uniform-width
   rows), so this does not falsify R93-C1 or R93-C2 as frozen. I flag it as an
   unstated-strictness note for the L1, not as a kill attempt: the reader is refusing a
   table that GFM itself says is well-formed, and the honest-note side of the claim
   ("the reader refuses on verdict content, never on id shape") does not cover it.

Confidence: high on the byte-identity, the three quote locations, the word counts, the

a live re-fetch. Medium on the scope reading in (2), which is a judgement about what the
