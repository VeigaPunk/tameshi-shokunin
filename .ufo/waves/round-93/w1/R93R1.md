## Findings, by severity

### 1. (MEDIUM) Header/delimiter width is never checked — the width guard reads the wrong row (measure-v93.py:269)
`tables()` starts data rows at `i+2`, so `drows[0]` is the **first data row**, not the delimiter row. The check `if delim and len(delim) != len(header)` therefore compares header width to first-data-row width (already covered by the per-row check at :275), and the true delimiter's column count is validated only by `DELIM_RE` (>= 2 columns, >= 3 dashes each). Probe output: header 5 columns over delimiter `|---|---|---|` with 5-column data rows → `bad=[]`, row keyed. So a GFM-invalid table (S321 header/delimiter cell-count rule) is still keyed. What the false-green is: a committed note whose verdict table has a short/long delimiter still prints `C1_R93_PASS=true` provided the verdict cells themselves are correct — the cells are still the true selftest verdicts, so the verdict-content claim survives, but the declared GFM shape (S321, cited in the `tables()` docstring :204–208 and the plan's "header row + delimiter row") is not certified. Severity is held at MEDIUM, not HIGH, because the plan's claim sentence is about the twelve verdict cells. `VERDICT: findings:5` counts this.
Note `drows[0][1]` for an **empty** table is unreachable (guarded by `if delim`), so no crash.

### 2. (MEDIUM) `coverage` ignores fenced blocks in corpus/README.md (measure-v93.py:481–489)
The last-row scan matches `line.lstrip().startswith("|")` and a path **substring**, with no `block_lines` fence handling, unlike the note reader and the `measured:` read. A fenced appended row naming the note therefore counts as the last row: a fenced *assertion* after a committed denial flips `coverage` to true (false-green — denial defeated by literal fence text the reader would skip everywhere else), and a fenced *denial* flips it to false (false-red). Probe (`R93R1-probe4.py`) confirms the fence-aware note reader and this README scan disagree. Related substring issue: `in line` also matches a longer filename (`...census.mdx`) — an innocent longer-name row is graded as the note's row. Severity MEDIUM because the control `coverage-denial` only appends an unfenced row; a fence-wrapped variant of the same cheat is uncaught.

### 3. (LOW-MEDIUM) `block_lines` fence tracking: 4-space indented and list-nested fences are visible (measure-v93.py:64, 185–200)
`FENCE_RE = ^ {0,3}` follows CommonMark (0–3 spaces), but a list item indented 4 spaces whose fenced example contains `| C01 | ... | KILLED |` is **not** treated as a fence, so its content is visible and the stray-verdict scan refuses the note (`bad=['stray-verdict:2:...']`, `R93R1-probe2.py`). In CommonMark a fence inside a list is indented relative to the list, so this is a genuine false-red for an honest note that fenced an example inside a list. Similarly `tables()` requires consecutive original indices (`vis[i+1][0] == oi+1`, :213) — a fence between header and delimiter splits the pair, safe direction. The **unclosed fence** case was probed both ways: an unclosed ``` or ~~~ swallowing the verdict table yields `rows=0, bad=[], verdict_tables=0` — the note then fails `verdict_tables`/`ids` (safe direction: refusal, not false-green). Tilde/backtick mismatch and closing-junk (` ``` extra ` does not close) behave correctly per S322, and a close longer than the open closes — all verified by probe. Findings 1–2 above, not this one, are the fence-related defects; this is the residual honest-note refusal risk.

### 4. (LOW) Self-pin normalisation accepts byte-different files with extra `SELF_SHA256` lines (measure-v93.py:47–48, 70–78)
`re.sub(SELF_PIN_RE, b"", b, flags=re.M)` strips **every** line matching the pin pattern, so appending a duplicate `SELF_SHA256 = "..."` line (with any 64-hex value) leaves the normalised digest unchanged — verified by probe (`dup-append same digest? True`, `diff-hash append same digest? True`). Why this stays LOW rather than a false-green of the certificate: (i) an extra pin line alone changes no behaviour — Python re-assignment of the same value, runtime `SELF_SHA256` is the last assignment, and for `self_pin_ok` to pass its value must equal the digest, which the attacker must already know; (ii) any *other* edit (a second code line) changes the normalised digest and is refused; (iii) the plan's kill rule (c) additionally pins the counter blob by full-file sha256 (`18903602...`), so a byte-different counter file is caught independently of selfpin. But strictly, `selfpin` alone does **not** certify byte-identity — it certifies "rest-of-file + some pin line". A moved pin line is likewise invisible. Also fragile: a CRLF copy / `core.autocrlf` working tree makes the pin line fail `...\n`, the normalisation keeps it, and the counter dies at setup (false-red for an honest clone on Windows; not reachable on this Linux lane where git checks out LF). Severity LOW, design note for round 94: anchor the digest to byte-exact pin-line count (exactly one).

### 5. (LOW) `split_cells`, `DELIM_RE`, stray-scan and `measured:` — honest-note refusal surfaces (measure-v93.py:157–178, 65, 257–262, 454–456)
Verified by probe:
- **Escaped-backslash before pipe** (`| a | C:\\|x | KILLED |`): in GFM `\\` is a literal backslash and the following `|` separates, but the scanner consumes `\\|` as a literal pipe, merging cells → width shift → refusal. An `edit` cell containing a literal backslash before a pipe (e.g. a regex) refuses an honest note. The simple `\\|` case also correctly keeps one cell (probe confirms) — only doubles are wrong.
- **Delimiter needs >= 3 dashes**: `|-|-|` is false per `DELIM_RE`, though GFM accepts one dash; an honest table written with `|-|` / `| :-: |` style is not a table at all to the reader (its rows then trip stray-verdict). The committed note uses `---`, so unreachable here.
- **Stray scan** (:257–262) keys any out-of-table line with >= 2 raw `|` and a whole-cell `KILLED`/`SURVIVED` token, including prose with two pipes — the plan *declares* this class ("a verdict word in prose with fewer than two pipes is not a table row" ⇒ >= 2 pipes is keyed), so this is declared, not a finding; but note `split_cells` has no code-span handling, so an inline `` `| KILLED |` `` mention in prose trips `width`/`stray-verdict` (probe). Declared-by-generous-reading; recorded so the L1 knows the breadth.
- **`measured:` regex** (`^measured: (\d+)/(\d+) killed\s*$`, :455, on visible lines only) — correctly ignores a fenced `measured:` (declared limit), requires exactly one match, lowercase `killed`, no leading space. A leading-space or `KILLED` variant in an honest note is refused; the committed note uses the exact form.
- **Header `verdict` detection** uses `norm_cell` (strips `` * `` and backticks): `**verdict**`, `Verdict`, `verdict␣␣` all count (probes confirm), consistent with QUALITY 155; a data cell exactly `verdict` in a non-verdict table does not create a header (probes: `pos-honest-verdict-cell` behaviour).
- **Verdict cells are exact tokens**: `killed` lowercase and `**KILLED**` both refuse (`no-verdict`), which matches the note's plain-token format.
- **`located_quotes` / `source`** (:307–319, 461–480): a quote counts for `sid` if it sits in double quotes on any line naming that sid (the quote itself need not name the sid), is 1–25 words, and `norm_text(q)` occurs anywhere in the normalised snapshot. A short common phrase (`"the table"`) would pass by accidental occurrence — a mechanism-level false-green for `source`, not reachable with the committed lesson whose S321/S322 quotes are long and distinctive. Similarly `row_ok` splits `corpus/SOURCES.md` on raw `|` (no escaped-pipe handling), so an escaped pipe in that file's columns would false-red; the census file is plain (spot-confirmed via the same split the counter uses).
- **Witness comparison** (:434) compares `(rc, stdout)` only, ignoring stderr — a mutant differing only in stderr reads `same`, failing `witnessed` (safe direction).
