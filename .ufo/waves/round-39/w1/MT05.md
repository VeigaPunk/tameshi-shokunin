## Verdict

**SURVIVED (copy configuration) — coverage finding, not a contract change.**

- The mutant is invisible to the detector whenever its bytes are a copy: `r38_regex_hits` stays 0
  on the live lane (run A/B) and on a git copy whose *measured rev* predates the mutant (run C2).
  The term is a read of `git show <lane>:<rev>:tools/mutate-and-run.sh`, not a function of any copy.
- The regex is not blind by itself: the same mutant **committed** into a repo the counter can read
  yields `r38_regex_hits=1` and `C1_R39_PASS=false` with every other conjunct green
  (`live_agree=1 stripped_agree=1 mismatches=0`, run C3). The kill is real, but it requires the
  mutant to be inside the measured git object at REV.
- Consequence for the claim: within this seat's bounds (the live runner and the lane's git object
  must not be touched), no runner-copy mutation can move `r38_regex_hits`; the conjunct is a
  REV-pinned read, not a mutation-tested behavior. A copy-based "would the control catch a leg
  line?" experiment can only answer 0, because the counter has no file/runner input. Moving it
  would require committing a `^\s*leg` line into the lane runner — exactly the write the no-harm
  control forbids.
- Secondary depth: the regex is over-broad, not just vacuous — no word boundary and `\s*` spans
  newlines, so a line beginning `legacy…` also counts (run D, `r38_regex_hits=1`). Today's 0 is an
  accident of bytes (0/2080 lines begin with `leg*`), not a guarantee: any future line whose first
  token starts with `leg` (e.g. `legacy`, `legend`) would break the after-target without any ledger
  change.

No predicate was rewritten, and no change to the contract or the counter is proposed.
