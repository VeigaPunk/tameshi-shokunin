## What the tool is

Generator/oracle pair for the sibling gate `tools/staged-id-guard.py` (docstring
`tools/pbt-staged-id.py:2-44`). It draws seeded cases (13 recipes × 12 frozen classes), writes each
case as three files into a private `mkdtemp` case dir, runs the guard as a subprocess through its
frozen CLI (`run_guard`, `tools/pbt-staged-id.py:767-799`, argv
`<sys.executable> -I GUARD --registry … --staged … [--map …] --json`, cwd = case dir), and compares
the guard's exit code plus JSON fields against an oracle written from the guard's documented
contract (`oracle_case` line 257, `check` line 307). The oracle never reads the guard's source
(docstring line 7). Reads: only its own `--guard` path (mode/readability via `guard_problem`,
line 878-889) and the case files it writes. Writes: the caller's `--dump` file, the private work
root, and (selftest) a private `pbt-selftest-*` scratch under `TMPDIR`; nothing in the lane.
It can fail — a disagreement with the oracle is exit 1 with `VIOLATION index=…` (line 862-866) — so
per PROTOCOL §Gate standard ("A tool that cannot fail is a probe") it registers as `gate`.

## Findings

**D1 (defect, declared but semantically wrong).** A hung guard becomes `failed`, never
`could-not-evaluate`: `run_guard` maps `subprocess.TimeoutExpired` to observed exit 124
(`tools/pbt-staged-id.py:786-788`), `check` compares that against the oracle's expected exit and
returns a reason (`tools/pbt-staged-id.py:309-311`), so the run stops with `VIOLATION` and exits 1.
Worst case 400 cases × `GUARD_TIMEOUT` 60 s (line 70) ≈ 6.7 h of ladder before the false verdict.
The row therefore declares 1 as `failed (violation)` and cannot distinguish a hang; that is the
tool's behaviour, not a row choice.

**D2 (defect).** The declared distribution floor is advisory: `CLASS_MIN = 20` (line 69) only appends
` SHORT` to the `CLASS` lines (line 869) and never touches the return code (line 875). Observed: a
40-case run exits 0 with 10 of 12 classes `SHORT`, including the documented 12-class coverage claim.

**D3 (defect, platform-conditional).** Two selftest assertions are skipped rather than failed where
their precondition is absent: `unreadable-guard-is-setup` under uid 0 (line 1038) and
`dump-write-failure-is-setup` without `/dev/full` (line 1071) print `CASE … SKIP` (line 1021-1022)
and are not counted in `failed`, so exit 0 does not cover them. On this host both ran PASS (no SKIP
line in `T51Row09-selftest.stdout`).

**D4 (defect, unexercised).** Two selftest probes sit at absolute paths outside the private
`TMPDIR` scratch: `/proc/self/pbt-selftest-no-such-dir` (line 1064) and `/dev/full` (line 1078).
`workspace()` joins them onto the work root, and `os.path.join(work, '/proc/…')` keeps the absolute
path, so on a host without `/proc` and with write privilege the failure-path case would create
directories at the filesystem root instead of failing. `[INFERENCE]` — not exercised here (this host
has `/proc`), no `/tmp` is hardcoded anywhere (work root is `mkdtemp(prefix='pbt-staged-id-')`,
line 807; selftest redirects `tempfile.tempdir` at line 1030 and restores/removes at 1084-1091).

**D5 (conformance gap, not a tool exit bug).** PROTOCOL §Gate standard "Two evidences" is not
satisfied for this gate: it ships no committed guard snapshot with a committed expected verdict and
no digest pin of the graded file, so its verdict depends entirely on the mutable
`tools/staged-id-guard.py`. The row's Pinned values cell says `none` for exactly this reason; a
later round that freezes a guard snapshot plus `expected.json` digests would let this cell name real
pinned paths.

**D6 (not a defect, checked).** No lane write: `--dump` is caller-chosen, work dirs are private, and
`guard_problem` only consults `os.path.isfile`/`os.access` (line 878-889). `--cases 0` and missing
arguments both exit 2 via `_setup_error` (lines 1107-1109), already in the verdict map as
`could-not-evaluate`.
