## Defects and limits of the tool observed while reading

1. **Hardcoded `/tmp`, `TMPDIR` ignored** — `tools/mutate-and-run.sh:482` (run workdir),
   `:1360` (`--regression` root), `:1477` (selftest root) call `mktemp -d /tmp/tameshi-r4-2-*.XXXXXX`
   directly. The frozen C3 counter runs the selftest with `TMPDIR=WORK/tmp`; the tool writes under `/tmp`
   regardless. Harmless for the counter (unique dirs, removed on PASS) but it breaks the caller's ability to
   confine scratch (host policy for this round: scratch under `/fast/scratch`).
2. **Run-mode `exit 1` is `DEGRADED`, not "failed"** (`:574`, printed as
   `MUTATE: DEGRADED (… inconclusive=…)`). PROTOCOL pins `1 = failed` fleet-wide, so the row maps 1 → failed
   and says so in the cell; a reader who treats 1 as "the tool broke" misreads a measurement that merely had
   an inconclusive suite. This is the only exit-semantics subtlety in the map.
3. **`--regression` only works next to a fleet checkout** — `FLEET_ROOT` is derived as three `dirname`s above
   `$SELF` (`:1358`) and is not overridable (assigned unconditionally, `:632` only initializes it). Run from a
   clone outside the fleet (including the counter's own `WORK/tameshi-shokunin`), every leg resolves to a
   missing repo → `exit 2` SETUP. The row's Entry command therefore names `--workdir DIR` and the Pinned
   values cell says the leg pins are literals in the tool; a reader must run it from the fleet.
4. **Two finding ids on the same stdout stream** (`MUTATE_SELFTEST:` tally at `:2046`, `VERDICT:` at `:2048`)
   — see the note above; only the last one is the registry's finding id.
5. `--regression` writes a `specs/` tree and one sub-sweep dir per leg inside `--workdir`, and keeps that
   root on FAIL/SETUP (`:1444`, `:1450`, `:1459`) — write scope is caller-chosen but can be large (nine legs ×
   up to 15 mutants); the row's Write scope cell states the caller-chosen dir plus the auto-mktemp case.
