## Findings / defects of the tool (none block the row; the row declares what the tool does)

1. **Usage code is not what the tool's docstring promises.** `:12` and `:23` declare `64 usage`, but the usage error a caller actually hits — an unknown or malformed flag — comes from argparse at `:357` and exits `2`, the same code as `could-not-evaluate` (`:207`, `:211`). Command: `python3 tools/receipt-window.py --r51-no-such-flag; echo $?` → `2`, stderr `error: unrecognized arguments`. `64` is reachable only via the missing-flag branch `:361-362`. The row maps `2 → could-not-evaluate` (conforming to PROTOCOL "an undeclared nonzero code reads as could-not-evaluate"), but a caller cannot separate "you typed it wrong" from "inputs unreadable".
2. **`--help` exits 0 and therefore reads as `clean`** under this row's map (observed `RC: 0`). Harmless for the counter, worth knowing when reading receipts.
3. **The selftest re-implements the contract index instead of loading it.** `:257` ("Build the contract index without the filesystem") duplicates the index/window construction of `load_contract` (`:61-119`); only the last 2 of 20 cases (`:327-342`) exercise the file loaders. Bug-compatible drift in `load_contract`'s index logic would stay green. The repo does hold independent expectations (`.ufo/evidence/round-20/public-cli-cases.json`), but the selftest never reads that file (`grep -n "public-cli-cases" tools/receipt-window.py` → no match).
4. **The gate cannot detect its own drift.** `check()` (`:134-201`) compares receipts only against the shas written in the contract; nothing hashes `tools/receipt-window.py` at run time. Drift there is caught by the contract's `measurement` command, not by this gate.
5. **The committed contract embeds an absolute host path**: `.ufo/evidence/round-20/contract.json` `measurement` = `python3 .ufo/evidence/round-20/stage/measure.py --repo /home/vgpnk/Projects/shokunin/tameshi-shokunin --rev REV --check`. Pinned evidence, but not portable.
