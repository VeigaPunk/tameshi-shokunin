## Kind reasoning (`gate`, not `probe`)

- `--check-entry PATH` reads a committed surface and returns a verdict against expected structure: the
  three outcome class names (`OUTCOMES`, `:24`; regex `:81-82`) and the explicit update-flag rule
  (`:83`). Missing class or missing rule → `:90` returns 1. `python3 tools/golden-verdict.py
  --check-entry corpus/knowledge/no-such-entry.md` exits 1 — the tool fails on a real input.
- The expected values are persisted in the owning repo, but as literals in the committed tool rather than
  a separate `expected.json`; the frozen run over the committed entry with its committed expected verdict
  is `.ufo/evidence/round-38/golden/measure.py` (`ENTRY = 'corpus/knowledge/golden-comparison-verdict.md'`,
  `:30`), which is why that path is pinned in the row. The selftest asserts both the exit code and the
  stable finding id `GOLDEN_VERDICT_SELFTEST:` (`:66-69`).
- `--classify-exit` on its own only reports (`:103-105`) — that mode would be a probe; the tool as a whole
  is a gate because of `--check-entry`.

## Defects and limits seen

1. **Could-not-evaluate is conflated with `failed`.** `check_entry`'s `except OSError` path (`:77-79`)
   returns 1 for an unreadable/missing entry — but nothing was compared there, which is the error class
   this very tool defines (`corpus/knowledge/golden-comparison-verdict.md`, "error" row). Under PROTOCOL
   §Gate standard only `1 = failed` is fleet-fixed, so a missing entry reads as a red gate rather than
   could-not-evaluate. Shown by: `python3 tools/golden-verdict.py --check-entry
   corpus/knowledge/no-such-entry.md` → `GOLDEN_VERDICT_ENTRY: unreadable ...` exit 1. Consequence for
   the row: `1` is declared `failed` truthfully as the tool stands; a future fix to exit 2 (or a distinct
   code) would require the Verdict map to grow that code.
2. **`--classify-exit` can never fail** (`:103-105`): it prints `error` for 2, 42 and -1 and still exits 0.
   A reader who wires it as the entry command would get a green exit on an error-class comparison. Not a
   row defect (the row's entry command is `--check-entry`), but it is why the kind argument rests on
   `--check-entry` alone.
3. **Latent uncaught `FileNotFoundError` in `compare()`** (`:40`): if the `diff` binary is absent, the
   `subprocess.run` raises, the interpreter exits 1, and that 1 reads as `failed`, not could-not-evaluate.
   Not reachable through any CLI mode (`compare` is only called by the selftest), so not declared as a
   separate code in the row.
4. **Not a row defect, reported for the C3 owner:** the two pre-existing registry rows fail this counter's
   own row rules —
   `C3_TOOL tools/repeat-control.py: MISSING (line 1504 pinned-path-missing:mismatch/expected.json)` and
   `C3_TOOL tools/bash-witness-study.py: MISSING (line 1505 finding-id-not-in-row (VERDICT:))`, with line
   numbers shifted by the scratch insertion (real `SKILL.md:1503` and `:1504`). Both cells' claims are
   outside my item; flagged only because `C3_R51_PASS` needs all 30.
5. No hardcoded `/tmp`, no undeclared exit code beyond those in the table above (0, 1, 2 only; verified by
   exercising every mode and argparse's two error paths).
