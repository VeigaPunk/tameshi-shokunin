## Findings by severity

### Medium

- **F1 — Malformed input exits 1 with a traceback and no receipt, violating the documented exit-2 contract.** Both confirmed by execution in scratch:
  - `--seed zz` → `ValueError: invalid literal for int() with base 16: 'zz'` at line 219 (`rng = random.Random(int(seed, 16))`); process exit code 1; no `C1_R32` line anywhere.
  - `--work notadir` (a regular file) → `NotADirectoryError: [Errno 20] Not a directory` at line 209 (`os.listdir(work)`); exit code 1; no receipt.
  The docstring (line 27) and the exit-code logic promise exit 2 on counter error. Under the contract's `kill_rule`, a run that prints no receipt is not an evaluated false, so the damage is limited to misclassification by scripts that test `$?` (exit 1 looks like "evaluated, not passed"). The same uncaught-exception class covers `OSError` from `os.makedirs` (212, 244) and any exception from `fu.result()` (263) — e.g. an unwritable work parent. Smallest safe correction: parse the seed in try/except and print a `C1_R32:` stderr line with `return 2`; use `os.path.isdir(work)` instead of `exists` + `listdir`.

### Low

- **F2 — Set-membership side channel through copy creation order.** Copies are written kill-set first, then accept-set, in fixed order (245–249). The audited tool receives only one opaque path, but it learns its own directory from that path and can enumerate siblings ordered by mtime/inode (first 18 created are must-kill, last 8 must-accept). Names themselves leak nothing; execution order is shuffled (259) but creation order is not. A hostile tool exploiting this could steer toward a false PASS by treating early files as kill targets. Correction: write bodies in a shuffled order, or normalize mtimes after writing.
- **F3 — B3-decoys does not carry N01's new text, against the contract's "carrying every frozen mutant's new text".** The decoy tuple (141–148) carries the new text of T08, N05, H03, H04, H05, N02, N03, D01 — eight of the nine frozen kills. N01 is a pure deletion of runner line 2027, and no decoy line represents the post-deletion vector list (either the bare `for tvec in \` continuation form or the `'; do` merged form that `generated_kill` v3 produces). A tool keyed on the N01 shape is therefore not decoy-tested by B3. Correction: add one decoy comment reproducing the N01-surviving list, or narrow the wording in the contract/docstring.

### Informational

- **F4 — The predicate sentence under-describes the actual invocation.** Both sentences say `python3 tally-audit.py --runner COPY`; the code runs `[sys.executable, '-I', tool, '--runner', copy]` with an absolute argv[0], cwd set to an empty per-run directory, and a five-variable environment (183–184). This is hardening in the anti-keying direction (no cwd-relative reads, no PYTHONPATH, no git env), it cannot help a bad tool pass, and the contract's `code_conditions` — the authoritative code-level predicate — match the code exactly. Also the docstring usage line adds `[--jobs N]`, which the contract's `counter` string does not mention. No change required; worth one docstring clause.
- **F5 — Generated families can byte-duplicate their frozen counterpart for a drawn seed.** gN05 form 0 equals frozen N05, gH03 form 0 equals H03, gH04 tail `rc=$?` equals H04, gN02(or) equals N02, gN03(or) equals N03, gN01 vector=2 equals N01 (e.g. replay seed `fc9d575b…`: `gH03(form=0)` sha `2ac4ce53…` equals frozen H03; `gN01(vector=2)` sha `c0a32ec4…` equals frozen N01). Expected ≈2 of 9 generated kills duplicate frozen content per seed. Duplicates remain genuine must-kill copies and counting is unaffected, but a run's independent anti-overfit coverage is smaller than 9. Consistent with the contract's `not_claimed`; no change required.
- **F6 — "Not knowable when the tool is written" overstates, and receipts disclose the generated space.** The contract itself lists all nine family structures, and every COPY line prints the family id with drawn parameters (273), so wave-1 control receipts hand the tool author the generated space ahead of time. What stays unknown is only the drawn instance under the measurement run's fresh seed, and byte/hash keying stays defeated. Mitigated by the protocol (fresh seed at the measurement revision; every observed run reported). Residual risk, not a code defect.
- **F7 — Timeout orphans and unbounded tool writes.** On `TimeoutExpired` (184–187) `subprocess.run` kills only the direct child; a hung tool's grandchildren (the runner copy's bash/node descendants) survive. Also a hostile tool can write unboundedly into its per-run HOME for up to 600 s at `--jobs`-fold parallelism. Seats auditing junk controls should use a modest `--jobs` and watch `/fast` (99 GiB free at review time). The printed `sha256=` (273, computed at write time, 250) is a write-time digest, not a post-run re-hash, so sibling-file tampering by a hostile tool would not show in the receipt — but no tampering path to a false PASS exists (it can only force OTHER outcomes, i.e. fail closed).
- **F8 — `--seed ''` is treated as absent.** `a.seed or secrets.token_hex(8)` (218) makes an explicitly empty seed mean "draw fresh", so that invocation is not replayable. Sane, worth knowing.

## Residual risk

- The counter trusts that a correct tool exists; nothing in it can validate the tool's oracle quality beyond the 26 copies. The 8 real MutateHead survivors are frozen and public, so a tool overfit to those exact bytes plus the listed families could pass without auditing runners in general — that limitation is exactly what the contract's `not_claimed` states, and the generated families narrow it only for drawn instances.
- A tool that passes by luck (e.g. `--jobs`-dependent timing, environment probing) is not excluded by design; the receipt's per-copy `exit=` and `last=` columns are the only audit trail. Enough to spot-check, not to prove.
