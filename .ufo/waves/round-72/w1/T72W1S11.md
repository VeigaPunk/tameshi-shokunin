# T72W1S11 — probe: does cold-read credit key on the RECORDED INPUT PINS?

Seat: leaf probe (verification-fixture craft), wave `w1`, round 72.

## Judgment

**SUPPORT** — the credit rule keys on the recorded input pins, all-or-nothing per
crediting ledger entry, not on section bytes alone. Observed with the frozen
decision code unchanged:

- ledger unchanged at base → `sections_covered=64/64`;
- one recorded input hash replaced by 64 zeros in one section's sole/newest
  crediting entry → **only that section** becomes uncredited, with reason
  `input-drift:<path>` (the exact single token when it is the entry's only
  drifted pin), and the entry itself flips `entry_reason: None → input-drift:…`
  and `entry_is_stale: False → True` while `vetoed=False`.

Scope of the support (observed, not inferred): section coverage is
**existential over the entries whose `sha256` equals the base section sha**.
A mutated pin in one crediting entry of a multi-entry section does **not**
uncredit the section when a sibling entry still verifies (arm R3). Entries with
a drifted pin are *stale*, so they neither credit nor veto. Keys in
`IGNORED_INPUTS` (`SKILL.md`, the ledger paths) are filtered before the pin
check and their recorded values are never verified (arm R6) — documented rule 4,
not a divergence.

## Divergences / instrument notes (no lane instrument broken)

1. **Attribution is not local to the mutation.** An uncovered section's `reason`
   is the `;`-joined, sorted union of *all* matching entries' first failures, so
   it repeats tokens per entry (R4 shows `input-drift:PROVINCE.md` four times and
   `input-drift:corpus/SOURCES.md` four times) and names sibling entries' drift,
   not only the mutated pin. This matches `measure.py`'s documented contract
   ("deterministic, `;`-joined, sorted union of the entries' first failure") and
   the precheck's `LOST` line dedupes via a set, so it is a readability limit,
   not a correctness divergence.
2. **`vetoed=False` on every drift arm.** Drift makes an entry stale, so it
   cannot block a sibling's credit — observed consistently (R2/R2b/R4).
3. **Newest is not privileged.** R3 mutates the newest entry and the section
   still credits; R4 mutates the newest when it is the only crediting entry and
   the section drops. The rule has no notion of "newest"; it is disjunctive over
   all entries that share the section sha. `R2`'s single-entry section makes the
   probe's "newest" wording trivially satisfied.
4. **Confinement.** Only sections whose `sha256` equals the mutated entry's
   section sha can change (R5: none; R2/R2b/R4: exactly one).
