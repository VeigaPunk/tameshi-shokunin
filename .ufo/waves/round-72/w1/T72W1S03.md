## Defects in the lane's own instruments

### D1 (high) — the ledger merge rewrites the whole file on this host (CRLF→LF)

`read_text(encoding='utf-8')` / `write_text(text, encoding='utf-8')` (r67 driver
lines 279 and 302; r72 driver identical) apply universal-newline translation. The
committed ledger is CRLF (produced on the win32 host); on a POSIX host the merge
rewrites every line.

Byte evidence (git blobs, `git show <rev>:<path>`):

```
f20ba48 ledger   36,388,098 bytes   CRLF 281,925   LF 281,925
bc7dc2fb ledger  37,510,854 bytes   CRLF       0   LF 293,268
4f01e28c (r71)   36,388,098 bytes   CRLF 281,925   LF 281,925
```

Commit shapes (`git diff --numstat <c>~1 <c> -- …/ledger.json`):

```
bc7dc2fb  round-72  293268  281925     <- this host
4f01e28c  round-71   11197       0
44f61fba  round-70   11197       0
b59ca7fe  round-69   11197       0
```

The landed r72 commit is `23 files changed, 317824 insertions(+), 281925 deletions(-)`.
My isolated rehearsal reproduces it exactly from the same base (`293122 / 281925`,
13 entries), so the cause is the driver, not the lane state.

Lane tool verdict on the landed commit:

```
ADDITIVITY file=.ufo/evidence/round-21/coldread/ledger.json base=f20ba482c744 tip=bc7dc2fb \
  raw_old_only=54597 raw_new_only=54635 norm_cr_old_only=0 norm_cr_new_only=38 \
  verbatim_prefix=false eol_rewrite_disclosed=true            exit 0
same command with --require-raw                               exit 1
r71 for contrast: raw_old_only=0 raw_new_only=29 … eol_rewrite_disclosed=false  exit 0
```

So the plan's "ledger checked old-bytes-only (insertions disclosed)" is only true
under CR normalisation. The instrument *does* disclose it (`eol_rewrite_disclosed=true`)
— the round record must cite that flag, not `raw_old_only=0`, or the additivity claim
is false on the bytes. Fix: read/write the ledger in binary or with `newline=''`
(the same fix also makes the driver host-independent; on win32 it currently forces
LF→CRLF in the other direction).

### D2 (medium) — `--traces-dir` is accepted, mkdir'd, and then ignored

`trace_rel` is hardcoded to `repo/.ufo/evidence/round-<N>/rekey/traces/section-%02d.json`
(r67 line 138; r72 line 141). Driving the committed r67 driver verbatim overwrote all
**13 tracked** round-67 receipts (`git status --porcelain` in the clone: 13 ` M`), while
the requested scratch directory stayed empty. The r72 rebind fixes this by rebinding the
constant, but any caller that believes it is writing traces to `--traces-dir` is wrong.

### D3 (medium) — `--entries-out` is a dead argument

Declared `required=True` (line 92) and never read anywhere else in the file. No file was
produced at either run (`ls <S>/entries-*.json` → `No such file or directory`, twice).
Entries exist only through `--merge-ledger`, so an operator cannot inspect the entries
without mutating the ledger first.

### D4 (low, receipt fidelity) — the trace `argv` claims `--merge-ledger` unconditionally

Line 203 writes `'--merge-ledger'` into every receipt's `argv` even when the flag was
not passed; my no-merge run's `section-01.json` carries
`[..., '--traces-dir', 'TRACES', '--merge-ledger']`. The receipt therefore misstates
the invocation it documents. (Also unchanged by `make-rebind-r71.diff` and
`make-rebind-r72.diff`.)

### D5 (low) — `--pin` and the working-tree ledger are not cross-checked

The merge appends to the **working tree** ledger (line 279) while all reads use
`--pin`. If the two diverge, entries are appended to one ledger generation and pinned
against another, with only the entry-count assertion guarding it.
