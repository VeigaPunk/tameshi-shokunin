## How the pages were obtained (read this before trusting the bytes)

`www.gnu.org:443` is **unreachable from this host**: IPv4 `209.51.188.116` and IPv6
`2001:470:142:5::116` both time out (direct `curl` attempts recorded below). The peer
seat recorded the same failure independently in
`.ufo/evidence/round-90/sources/gnu-unreachable.txt` (`curl: (28) Failed to connect to
www.gnu.org:443 after 133212 ms`). Other hosts are reachable (`git-scm.com` → 200,
`stryker-mutator.io` → 200, `ftp.gnu.org` → 200), so this is a route-level block on
`www.gnu.org`, not a general network outage.

Consequence: the three bodies were fetched through the public `allorigins` relay, which
re-requests the exact upstream URL server-side. Two independent receipts back each page:

1. **upstream status block** — the relay's JSON API reports, for the same URL, the
   upstream `http_code`, `content_type`, `content_length` and `response_time`
   (`.upstream-status.json`). All three pages report `http_code 200`,
   `content_type text/html`, and the upstream `url` field equals the requested URL.
2. **body bytes** — the relay's raw endpoint returns the upstream body verbatim; the
   fetched body is a complete Texinfo HTML page (`<!DOCTYPE html>`, `Created by GNU
   Texinfo 7.1`, the GNU Awk User's Guide copyright block, `Edition 5.4`), not a relay
   error page. `T90S1-fetch.sh` only promotes a candidate body over a good body when it
   parses as a doctype page, so a relay `error code: 522` body can never be promoted.

**Known limitation (not worked around):** the upstream *response header set* (Server,
Date, Last-Modified, ETag) is not obtainable here — the relay's JSON API reports the
upstream status block but its `headers` member is `null`, and the direct route is down.
The `.headers` files saved beside each page are therefore the **relay's** response headers
(the transport actually used), and each is labelled as such by its content. The upstream
status fields that *are* attested (200 / text/html / content_length / url) are in the
`.upstream-status.json` files. Stated plainly: **the upstream header bytes are unverified**.

Note on `content_length`: the upstream `content_length` (2457 / 5381 / 12155) is the
compressed transfer size; the saved body byte counts (6845 / 21645 / 49950) are the
decompressed bodies the relay delivered. Both numbers are recorded; neither is a
mismatch of content.

## What each page teaches for the C1 survivors

- **`{n,m}` (page 2) and interval expressions (page 1)** ground mutant **C03**
  (`teaches !~ /supersedes S[0-9]{3}/` → `{4}`) and mutant **C07**
  (`if (line !~ /^ {0,3}\|/) next` → `{0,2}`). The manual states that `{n,m}` repeats the
  preceding regexp *n to m times* and that gawk matches interval expressions **by
  default** since version 4.0 — the two facts that make those two edits change what the
  gate accepts rather than merely how it is spelled. C03 widens the accepted id width
  from exactly three digits to exactly four; C07 narrows the accepted indent from 0–3
  spaces to 0–2. Both are *semantic* edits of the gate's parser, which is why the frozen
  spec predicts SURVIVED for both.
- **`&` in the replacement string (page 3)** grounds mutant **C09**
  (`sub(/#[^ ]*$/,"",u)` → `sub(/#[^ ]*$/,"&",u)`). The manual states that `&` in the
  replacement stands for the precise substring matched by the regexp, so the mutant does
  not strip the URL fragment but re-inserts it verbatim — a URL-normalisation change, not
  a no-op.

Both the `{n,m}` page and the `&` page are also what makes the gate's own use of
`{0,3}` and `sub(...)` well-defined in the first place, so the case note can cite them
for the arms it describes rather than only for the mutants.
