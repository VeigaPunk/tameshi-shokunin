## Findings

### F1 — S324's digest is not reproducible from the URL; it is reproducible from the JSON

The committed snapshot `.ufo/evidence/round-99/sources/s324.json` (6409 B,
sha256 `346dcf46d3e6ccfe20d269b5b74ca4d21df98c8731c57858808d4c856d0f0349`) is one of **two** byte
sequences the Europe PMC REST endpoint returns for the same query. Over **41 refetches** of the identical
URL I observed **two distinct raw digests** — `346dcf46…` (29×) and `6a2f294a44ec753c…` (12×) — while
**all 41 samples are 6409 bytes long and all 41 parse to JSON equal to the committed snapshot**.

The difference is confined to the **key order of two sibling keys** inside `journalInfo.journal`:
`"nlmid"` and `"isoabbreviation"` swap positions (52 differing bytes at offsets 2880–2934). Sorting
the JSON keys canonically collapses both variants onto **one** digest,
`41ef1a7b6d998d3778145aef0da33215c34f2c271d7baf2a49b189145ec06d02`, identical across all 41 samples.

Consequence for the lane: a re-open that compares the *raw* sha256 of a fresh fetch against the pinned
`346dcf46…` would report a mismatch about 30% of the time while the document is semantically unchanged.
The pin as committed is correct — it is the digest of the committed bytes — but it is a property of *one
response*, not of the source. This is the same class the round's own C1 is about (a recorded figure that
does not re-derive from what it names), one level down: the recorded digest does not re-derive from the
documented fetch. A `recheck:` on S324 that re-fetches and re-hashes should compare the canonical
(sorted-key) JSON digest, or should re-hash the committed snapshot rather than a live fetch.

The S324 row's own `teaches` cell and the knowledge entry's `recheck: 365d; reopen S324/S325` instruction
are what make this live: the entry says to *reopen* S324/S325, i.e. to fetch again. Note the row also
claims the fetch's HTTP date (`Sun, 08 Nov 2026 22:55:22 GMT`) — a date a re-fetch cannot reproduce either.

### F2 — the Springer landing page is a JS-challenge page under a browser UA, and is byte-unstable under any UA

`https://link.springer.com/article/10.3758/s13428-015-0664-2`:
- **default curl UA**: HTTP 200, **467680–467714 bytes** (varies between fetches), real article page,
  `<title>The prevalence of statistical reporting errors in psychology (1985–2013) | Behavior Research Methods | Springer Nature Link</title>`,
  and the S324 sentence *is* present in the tag-stripped text. But the bytes are **not stable**: three
  fetches gave three different digests (`f57938fb…`, `d410039a…`, `443b953f…`) with the same length class;
  the difference is the per-response `_csrf` hidden-input value.
- **browser UA** (Chrome/128 on Linux): HTTP 200, **3038 bytes**, `<title>Client Challenge</title>` — a
  JavaScript interstitial (`/_fs-ch-…/script.js`, "Please enable JavaScript to proceed", 7 challenge
  markers), and the S324 sentence is **absent**.

So the browser UA is *worse* than the default UA here: the default UA reaches the article, the browser UA
is challenged. Either way the Springer page is unusable as a digest-pinned snapshot for the same reason
as F1 plus a per-response token. The Europe PMC record the round actually used is the better anchor.

### F5 — reject candidate: nbval (IPython Notebook Validation for py.test)

**URL** `https://nbval.readthedocs.io/en/latest/` · **HTTP 200** · **34947 bytes** ·
**sha256 `004918d670ee39964a8f520a9d7b483a1e0e8eeffc8d23e269afe6ea31dd272e`** (identical on a second
fetch; 0 hits for `nbval` across every fleet `corpus/SOURCES.md`).
**Quote** (22 words, tag-stripped line 96):
> "Validating the notebook means to rerun the notebook and make sure that it is generating the same output as has been stored."

**Reason to reject.** nbval reconciles a *notebook's stored outputs* against a *re-execution of that same
notebook*. The tameshi lane's C1 binds a figure to a receipt that was produced by a *different* artifact
(a committed record line vs. a committed `.out` file) — the two live in different places and drift apart
because they are edited at different times. nbval's binding is intra-artifact: the stored output and its
recomputation are the same file, so there is nothing for a "recorded figure vs. its cited receipt" check
to catch; the checker cannot see the failure mode the lane cares about, and it needs a Jupyter runtime to
run, which the lane's plain-Python tools do not have. It is also a *notebook* checker, not a *statistics
reporting* checker: it says nothing about p-values, test statistics, degrees of freedom, or a declared
reporting grammar, which is the whole of S324/S325's contribution.

**Flip condition.** Admit if the lane ever records a figure whose authoritative artifact is *itself
re-executable* and whose recomputation is expected to differ across environments (a notebook or script
whose stored output a reader would re-run) — i.e. a lane artifact where the claim and its
recomputation live in one file, so the binding is intra-artifact. Until then it teaches nothing the
reconciler does not already get from S324/S325.

(For completeness: the lane's own working tree already drafts **S326 = GRIM (Brown & Heathers)**, marked
`REJECTED`, with a flip condition of its own. I re-fetched its Crossref record independently — HTTP 200,
4679 B, sha256 `4bfd47c2baad3e68d2765f58909b53993287dd1ef07fdbe4baa6353a772b7b0c`, byte-identical to the
committed `s326.json` — and its 25-word quote is present verbatim in the `abstract` field. GRIM is a
*different* reject shape than nbval: it is a feasibility test on a reported statistic with no binding to
the artifact that produced the figure, whereas nbval is a binding mechanism for a different artifact
class. My candidate is nbval; GRIM was already drafted by the lane author and I only confirm its
snapshot.)

### F6 — the mined mistake named in the plan is real and fixed

The plan claims the round-98 audit's `loop-site-count` arm "indexes `SELFTEST_CASES[7]`, which is
`augassign`, a fixture with no loop". Confirmed in `tools/control-assertion-audit.py`: the arm is
`sites, _, _ = audit_text(SELFTEST_CASES[7][1])` and `SELFTEST_CASES[7]` is `augassign` — the eighth case,
no loop in it, so the arm never exercised a loop. v2 replaces it with
`audit_text(CASE["loop-site"])` **and** asserts `"for " in CASE["loop-site"]`, i.e. it checks the fixture
actually contains a loop, not just that it has one site.
