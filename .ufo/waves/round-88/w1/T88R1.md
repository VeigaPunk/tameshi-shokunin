## Findings

### F1 — minor (counter, docstring-vs-code; would NOT let a counterfeit reach the predicate)
Docstring line 29 says "INCONCLUSIVE fails the leg". Code: `verdict()` (measure.py:162-167) maps 124/126/127
to INCONCLUSIVE, and `replay_leg` (measure.py:248-254) counts agreement with `if v == table[d["id"]]` — an
INCONCLUSIVE replay **agrees** when the recorded `TABLE_` row is also INCONCLUSIVE, and table values are never
validated against `{KILLED,SURVIVED}`; the leg still counts if the other rows agree and ≥1 row is KILLED.
Unreachable for R88-C1: the spec bytes are sha-bound to `PREREG_SHA` (verified: worktree == 6998726f ==
runner-embedded heredoc == `724beed3…2689e`), none of the 10 prereg mutants is slow (probe: all exits 0/1 in
seconds; measured sweep 10/10 definitive), the honest `TABLE_KAKEGUARD` holds only KILLED/SURVIVED, and the
runner's own leg band is `inconclusive=0` — so any real inconclusive flips the counter row AND fails the
runner's leg; exploiting the latitude would additionally need the forged-PASS cheat the pre-freeze `forged`
control already refuses. Latent robustness gap only.

### F3 — note (counter design boundary, documented)
`runner_state` trusts the REV runner's exit code and the **last** `REGRESSION:` line regex-matched
(`PASS \(cases=(\d+) passed=(\d+);`; any cases number accepted, compared to 11 only in `ok`). A runner can
print `PASS(cases=11 passed=11)` without executing cases. This is the docstring's "necessary, never
sufficient" and is bounded: `declared/legs/python_legs/prereg` come from the counter's independent replay of
the runner bytes, so a fabricated line alone can never satisfy `ok` (pre-freeze `forged` receipt agrees).

### F4 — note (fail-safe direction)
Docstring says "every `regression_case_git` call"; the counter counts only calls in the exact 4-line
continuation shape (`LEG_RE`). A differently formatted leg is invisible → under-count → `declared<11` → no
predicate. Cannot inflate the count; worst case refuses a real leg.

### F5 — note (prereg binds spec bytes, not target identity)
`prereg=ok` checks only the embedded spec's sha256; the target (kake gate @ e8d3a924, pin `0c12838e…8514067`)
is enforced by the per-leg pin check and exposed on the `C1_LEG` line, not inside the prereg predicate. A
different `.py` target carrying the prereg spec cannot count (the 10 kake-specific `@old` strings must occur
exactly once in its pinned blob — verified count==1 only for the kake gate), so no predicate path.

### F6 — note (diagnostics only)
`git()` failures inside the replay phase (e.g. `log -1` on a corrupted repo) raise `Setup` outside `main`'s
try/except → traceback, exit 1, no summary line. Fail-safe (never prints `C1_R88_PASS=true`), just loud.
