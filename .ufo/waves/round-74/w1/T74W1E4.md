## Method (definitions are frozen in the script header)

`scan.py` walks `git rev-list --reverse --first-parent a3dd3574..3d6ea1ee`
(24 commits, `git rev-list --merges a3dd3574..3d6ea1ee | wc -l` = `0`) and for
each commit × file compares the blob OIDs at `rev` and the first parent
`rev^`; a differing blob is measured from `git cat-file blob <rev>:<path>`:

```
line set (raw)        = set(raw.split(b"\n")) - {b""}
line set (norm_cr)    = same after CRLF->LF and CR->LF
raw_old_only          = |raw old \ raw new|
raw_new_only          = |raw new \ raw old|
norm_cr_old_only      = |norm old \ norm new|
verbatim_prefix       = CR-stripped, empty-dropped old content, as an ordered
                        list, is a prefix of the tip's CR-stripped content
eol_rewrite_disclosed = raw_old_only != norm_cr_old_only
```

`raw_old_only` counts **distinct non-empty committed lines** (line-set
semantics) — the convention the round-73 numbers were stated in. Blank-line
changes are invisible in both views. Multiset cross-checks are reported
separately below.

Exhaustiveness: 24 revs × 4 paths = 96 candidates; 10 (commit, file) rows have
a blob differing from the first parent (the rest are byte-identical).

### Why the QUALITY range total is 1588 while the named commit is 1593

`base ∩ parent` is not the same set: `|base_raw \ tip_raw| = 1588`,
`|parent_raw \ tip_raw| = 1593`, and
`|parent_raw \ base_raw| = 0` (verified: `not (ls(base)-ls(parent))` is true),
`|(parent\base) \ tip| = 5`. The five extra lines are exactly the five
CR-stripped re-pin fragments listed above (`extra(CR-stripped) == pair
normalized old-only` is true), which entered after base (`be1199d3` appended
them) and were re-pinned at `21a7332f`. A pair-kind row on QUALITY
`a3dd3574..3d6ea1ee` therefore prints **1588**, not 1593; the status is still
`violated`. The LOG total equals the commit number (3484) because every base
raw line carries `\r` and none survives at the LF tip; the tip blob is not the
`862e8844` blob (two later LOG appends), but that does not change the set
difference.

## Findings the L1 must freeze around (evidence, not verdicts)

1. **The 3484/1593 numbers are line-set numbers, not multiset numbers.** Raw
   multiset differences are 3759 (LOG `862e8844`) and 1920
   (QUALITY `21a7332f`); range totals are 3759 and 1915. If
   `additivity-range.py` counts duplicate occurrences, the same rows will print
   different numbers. Both frozen values only reproduce under "distinct
   non-empty lines, empty lines dropped".
2. **The class control is not satisfiable for the QUALITY rewrite row as
   worded.** Under the plan's class mapping, `21a7332f` reads
   `raw_old_only=1593` (append-only-raw → violated) but
   `norm_cr_old_only=5` (append-only-content → still **violated**, because the
   declared re-pin removes five content lines). Only the LOG row flips
   (3484 → 0 → hold). Plan control 4 / kill rule (iv) says the content class
   "reads hold for both"; the bytes say otherwise for QUALITY. This is a plan
   expectation inconsistency the L1 must resolve in the frozen text, not a
   measurement uncertainty.
3. **`raw_old_only = 0` does not imply a tail append.** `8b6e1bbe` inserts 63
   SCORECARD lines mid-file (`verbatim_prefix=false`, first divergence at old
   line 261 of 4405) while removing none. A row kind judged only on
   `raw_old_only` reads `hold` for it; the prefix property is the stricter
   statement.
4. **QUALITY pair-kind rows must print 1588, not 1593** for
   `a3dd3574..3d6ea1ee` (five re-pin lines were added after base). The status
   remains `violated`. The plan's six-row manifest has no QUALITY total row, so
   this matters only if one is added.
5. **`corpus/SOURCES.md` has two one-line mid-file removals** (`be1199d3`,
   `1d118c14`, both diverging at old line 71 of ~502) and `SCORECARD.md` has a
   zero-removal mid-file insert set; neither file is in the plan's six-row
   manifest. Extra evidence for whatever coverage the L1 freezes.
6. **Manifest wording mismatch in the frozen plan:** the table is introduced
   as "six rows" but control 4 refers to "the same eight-row manifest". Not
   resolvable from committed bytes; flagged so the L1 can fix the frozen text.
7. `verbatim_prefix` is a content-order property, not an EOL property:
   QUALITY `base→tip` is `prefix=true` (content survives) while the pair
   `21a7332f^..21a7332f` is `prefix=false` (re-pin). Both are correct.
