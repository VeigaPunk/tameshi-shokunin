# DevStatusEdge — status-edge sweep of the frozen tally-audit-v2 (round 33, wave 1)

## Verdict

**Two survivors with differing vectors, both outside the tool's vector set.** The frozen tool
(`tools/tally-audit-v2.py`, sha256 `9dbbce62…f33a4`) audits the pinned runner
(`tools/mutate-and-run.sh`, sha256 `a7d3f2dd…2eb9`) and **PASSed** 6 of 30 status-edge mutants:

- **S1 (mixed-status blind spot):** a status ≥3 co-occurring with another non-zero status is never
  swept. Mutant m18 (status 255 on the last leg clears an existing fail) passes every check;
  witness `1 0 0 0 0 0 0 0 255` → pristine `1:REGRESSION: FAIL (cases=9 passed=7 failed=1 setup=1)`,
  mutant `2:REGRESSION: SETUP (cases=9 passed=7 cannot-verify=1)`.
- **S2 (stress blind spot):** the dup/drop operand stress only runs the all-zero vector, so a FAIL
  path weakened under overcount survives. Mutant m26 (`FAIL only when the tally is complete`)
  passes; with the first operand duplicated and status vector `1 0 0 0 0 0 0 0 0` → pristine
  `1:REGRESSION: FAIL (cases=9 passed=8 failed=2 setup=0)`, mutant
  `2:REGRESSION: SETUP (case-tally mismatch: cases=9 counted=10)`.

The other 3 PASSes are behavior-preserving (m13/m14/m15, no differing vector over 2322 vectors),
and m27 is a side-effect-only escape (the audited exit + first stdout line are unchanged).
21 mutants were killed (exit 1) and 3 runs were refused with `TALLY_AUDIT: SETUP` (exit 2):
two behavior-preserving `case` rewrites (m21, m22) and one driver-count injection (m30). Baseline on pristine: `TALLY_AUDIT: PASS`, exit 0.

The tool's own result-counting is sound: writing an extra `R\t` result line to the driver shell's
stdout through `/proc/$$/fd/1` makes `run_vectors` see 4754 results for 2377 vectors and the tool
refuses with `TALLY_AUDIT: SETUP` (m30, exit 2); a write that lands inside the substitution only
replaces the compared first line, which the oracle does compare (m29, 2377/2377 mismatched, exit 1).
The two holes below are vector coverage, not driver arithmetic.

## S1 — mixed-status blind spot (m18)

Edit (`diff -u pristine.sh mutants/m18-lastpos-255-clears-fail.sh`), one inserted line immediately before pristine line 1441:

```
+  if (( st_citecheck == 255 && nfail > 0 )); then nfail=0; fi
   if [[ $nfail -gt 0 ]]; then
```

Why the sweep misses it (`tool.py:317-339`): the single-status sweep sets every other leg to 0
(`tool.py:318, 320-324`), the count-pair sweep uses only statuses 1 and 2 (`count_vectors`,
`tool.py:299-306`), and the placement mixes also use only 1 and 2 (`tool.py:328-339`). **No vector
ever combines a status ≥3 with another non-zero status**, and the mutation only fires on
`255 ∧ nfail>0`.

Differential run (`witness.py`, `witness.log`; 2322 vectors, one bash process per block, recipe
`out=$(tally …); rc=$?; ${out%%$'\n'*}`):

The tool's own record is `CHECK runtime PASS vectors=2395 mismatched=0` for this mutant

## S2 — stress blind spot (m26)

Edit (`diff -u pristine.sh mutants/m26-fail-requires-complete-tally.sh`), line 1441:

```

+  if (( nfail > 0 && npass + nfail + nsetup == nlegs )); then
```

The tool's stress (`tool.py:346-354`) duplicates and drops one operand at each position but runs
**only** the all-zero status vector (`run_vectors(sb, names, [[0] * n], tmp)`), where `nfail` is 0
and the weakened condition behaves like the original. With a failing status present and the first
operand duplicated (`stress-witness.py`, same duplication as `with_operands`):

DUP-OPERAND m26 -> 2:REGRESSION: SETUP (case-tally mismatch: cases=9 counted=10)

A miscount that pristine reports as FAIL is silently downgraded to SETUP by the mutant — the
round-29 routed defect class (a FAIL hidden behind a tally refusal). The tool records
`CHECK runtime PASS vectors=2395 mismatched=0` here too.

## m27 — writes escape the capture, verdict unchanged

m27 inserts `printf 'R\t0\tINJECTED\n' > /proc/$PPID/fd/1` after the tally declaration. In bash,
`$PPID` inside a command-substitution subshell is the process that started the script, not the
driver shell, so the write goes to the auditor's stdout. Observed in
`mutants/m27-driver-inject.tool.out`: 2395 injected lines, then the normal four CHECK lines and
`TALLY_AUDIT: PASS` (exit 0). Control probe (`probe/ppid.sh`): under `capture_output=True` the
injected line appears in the *outer* captured stdout, while the function's `out` stays empty.

The audited interface (exit code + first stdout line) is unchanged, so this is a scope limitation,
not an equivalence claim: the runner's total stdout changes and the audit cannot see it. The
driver's result count is not perturbed because the write lands outside the substitution
(`tool.py:219-233`); a write *inside* the substitution only replaces the compared first line, which
the oracle does compare.

## PASSes that are genuinely equivalent (m13, m14, m15)

No differing vector over 2322 vectors for each (`witness.log`); each is dead at the guard:

- m13 `npass != nlegs` — the FAIL and SETUP branches exit before the guard, so at the guard
  `nfail = nsetup = 0` and both expressions are identical.
- m14 `"$npass"` instead of the sum — same reason: the sum equals `npass` at the guard.
- m15 literal `9` instead of `$nlegs` — `nlegs=9` in both the reference and the runner.

These are correct PASSes (no false rejection).

## Refused, not passed (m21, m22)

`case $((st)) in` and `case ${st:-0} in` are exit-code-equivalent rewrites (leg values are always
numeric), but `CASE_RE` (`tool.py:154`) matches only the literal `case $st in`, so the tool prints
`TALLY_AUDIT: SETUP (counting "case $st in" not found)` and exits 2. That is an honest refusal, not
a wrong PASS, and it does not affect the measured claim; it is recorded here as an operability cost
for refactor-shaped held-out copies.

## Smallest safe correction (for the L1; not applied to the frozen tool)

Verified on a copy, `tool-fix-probe.py` (sha256 `9e3ebe0f…0865`; the frozen `tool.py` is untouched):

1. **Close S1:** add a pair sweep to `check_runtime` — for each ordered pair `i != j` and each `s`
   in `(3, 127, 255)`, the vectors `v[i]=1, v[j]=s` and `v[i]=2, v[j]=s` (432 vectors).
2. **Close S2:** run the dup/drop stress against three base vectors instead of one:
   `[0]*n`, `[1]+[0]*(n-1)`, `[2]+[0]*(n-1)`.
