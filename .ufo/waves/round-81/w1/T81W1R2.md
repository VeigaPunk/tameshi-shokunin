## 1. Semantic review

**Does `settled` mean what the predicate says?** Yes, exactly. `pin_audit`
(tools/selfstate-freshness.py:1224-1244) computes
`settled = reader.blob(row_rev, path) == reader.blob(pin_rev, path)` — byte
equality of the instrument blob at the row's pinned revision vs the blob at
`--pin-rev` (the plan's predicate sentence, verbatim). It compares bytes, not
figures and not commit identity: a row pinned at an older rev with identical
bytes reads `settled` (measured: `mutation-runner-selftest pin=5bcb13ea`
settled), which is the correct D3 semantics ("the figures happened to agree;
the pin did not"). Rows come from the same `validate_manifest` the sweep uses
(zero-rows / instrument-rev-unresolvable / instrument-path-invalid refusals,
ARM19); an unresolvable pin rev or a path absent at a rev raises
`SetupError` → `SELFSTATE error=setup …` exit 2 (main handler :414-416),
fail-closed before any row effect. Measured run of the counting command at
1b115ba: `rows=23 settled=20 stale=3` exit 1, naming exactly
`receipt-exists-selftest` (pin 21ef81e9), `receipt-bind-selftest` and
`registry-bind-selftest` (pin ae591d5a) — the plan's before-population. The
manifest pins no row on `selfstate-freshness.py` or `wave-reconcile.py`, so
this round's own tool edits add no new stale rows.

**Does a legitimate future arm addition break the digest arm until the
constant is recomputed?** Yes — and it is a dual gate: adding an arm edits
`selftest`'s source (digest mismatch → ARM21/arm25 fails; measured by the
in-function-comment probe) and leaves the executed-arm count ≠
`SELFTEST_ARMS` (module-level, outside the digest) unless bumped. Both edits
are deliberate and outside the single-edit mutant class, so the cost is the
declared one ("any arm-text edit fails an arm until the pin is recomputed
deliberately"); what the plan does not spell out is that the duty recurs every
future round that touches the selftest, plus the registry-figure refresh. That
is a consequence of the declared mechanism, not a divergence from it.

**Is the digest region the whole selftest function, and is the constant
outside it?** Yes and yes, both verified empirically: an inserted comment
inside `selftest` fails only the pin arm (ss: rc=1 fails={ARM21}, 20/21; wr:
rc=1 fails={arm25}, 24/25); a comment appended at module level passes clean
(21/21 and 25/25, rc=0); flipping one hex char of the pinned constant fails
only the pin arm (the digest itself is unchanged — the comparison fails). So
any arm edit anywhere inside the function is caught — including edits to the
digest arms themselves, which are self-guarding for single edits — and the
constant (plus `SELFTEST_ARMS`) sits outside the digested region.

Boundary worth stating: the pin does **not** cover assertion text outside
`selftest` (helpers like `_leftover`, `_record_span`, `delimited`,
`validate_manifest`, `GitReader`, `main`, or module constants). That matches
the declared surface ("the suite's own assertion text" — the arms live in
`selftest`), and every non-selftest defect in both specs is killed by a
behavior arm, so no gap is exercised. A mutant that weakens an assertion
expressed in a helper would not trip the pin; that class is not declared
covered.

## Findings by severity

- **Defect (blocking/correctness): none.** The mechanism matches the plan; all
  frozen FAIL-set claims reproduce to the digit; no existing killer regressed;
  the one matrix change is the disclosed one.
- **Minor (craft): recompute-recipe asymmetry.** `tools/wave-reconcile.py:83-92`
  documents the exact constant-recompute command in-source;
  `tools/selfstate-freshness.py:101-110` does not. The lane's own convention
  (every pinned figure carries its re-derivation) is unmet for the selfstate
  pin; a future round must reconstruct the recipe. Suggest adding the same
  three-line recipe comment.
- **Minor (wording): the selfstate tool comment says "any edit to an arm's
  assertion text", but the implemented region is the whole `selftest` text —
  any byte, including comments and fixture code (measured). Broader than the
  comment, harmless to the claim; the plan's "any arm-text edit" wording is
  the accurate one.
- **Observation (fail-closed, undocumented prefix):** `pin_audit` checks path
  existence at the tip but not at the row's pinned rev; a path absent at the
  pin raises `SetupError('blob-unresolvable:…')` → exit 2. Conservative and in
  the declared refusal family, but that prefix is not among the named
  refusals (ARM19 names `pin-path-absent`, i.e. absent at the tip).
